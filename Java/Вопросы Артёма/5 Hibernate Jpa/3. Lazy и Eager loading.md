Разница между `LAZY` (ленивой) и `EAGER` (жадной) загрузкой — это фундамент, без которого работать с Hibernate просто опасно. Именно здесь рождается 90% проблем с производительностью и самая известная ошибка в Java-мире: `LazyInitializationException`.

Давай разберем, как они работают под капотом, какие у них дефолтные значения и в какие ловушки попадают разработчики.

## 1. Суть: КОГДА загружать данные

Эти стратегии отвечают только на один вопрос: **в какой момент времени нужно сделать запрос в базу данных?**

- **`EAGER` (Жадная):** Загрузить связанные данные **немедленно**, прямо в момент загрузки родительской сущности. Даже если они тебе никогда не понадобятся в текущем бизнес-процессе, Hibernate всё равно пойдет за ними в базу.
    
- **`LAZY` (Ленивая):** Отложить загрузку **до момента первого обращения**. Hibernate не будет делать запрос в базу, пока ты явно не вызовешь метод-геттер (например, `department.getEmployees().size()`).
    

## 2. Дефолтные значения (Любимый вопрос на собеседовании)

Если ты не укажешь параметр `fetch` явно, спецификация JPA применяет следующие правила:

- Связи **«Ко-Многим»** (`@OneToMany`, `@ManyToMany`) по умолчанию **`LAZY`**. Это логично: в коллекции может быть миллион записей, грузить их сразу — самоубийство.
    
- Связи **«К-Одному»** (`@ManyToOne`, `@OneToOne`) по умолчанию **`EAGER`**. И вот это — огромная архитектурная подстава, о которой мы поговорим чуть ниже.
    

## 3. Как работает LAZY? Магия прокси-объектов

Многим кажется, что при ленивой загрузке в поле коллекции просто лежит `null`, а потом откуда-то появляются данные. Это не так.

Если ты достал сущность из БД, Hibernate подкладывает на место ленивых связей **Прокси-объекты (сгенерированные классы-заглушки)**, используя библиотеки вроде ByteBuddy или Hibernate Proxy.

Java

```
Department dept = repository.findById(1L).get();
// Внутри dept.employees лежит не обычный ArrayList, а PersistentBag (прокси)

// Никакого запроса в БД нет!
System.out.println("Департамент: " + dept.getName()); 

// В ЭТУ СЕКУНДУ прокси перехватывает вызов, понимает, что он пустой, 
// приостанавливает твой код, делает SQL-запрос, заполняет себя данными 
// и только потом возвращает размер.
System.out.println("Сотрудников: " + dept.getEmployees().size()); 
```

### 🚨 Главная засада LAZY: `LazyInitializationException`

Прокси-объект умеет делать запрос в БД **только тогда, когда открыта транзакция** (то есть жива сессия Hibernate / Persistence Context). Если ты достал Департамент в сервисном слое (где висит `@Transactional`), транзакция закрылась, а затем контроллер попытался превратить этот объект в JSON (библиотека Jackson начинает вызывать все геттеры подряд), прокси попытается сходить в базу, увидит, что сессии нет, и выкинет фатальный `LazyInitializationException`.

## 4. Почему EAGER — это почти всегда зло?

Правило хорошего тона в современных энтерпрайз-приложениях звучит так: **Абсолютно все связи (даже `@ManyToOne`) должны быть явно переопределены в `LAZY`.** Использование `EAGER` — это код-смелл (признак плохого кода).

Вот две причины, почему EAGER убивает систему:

### Причина А: Эффект «Снежного кома» (God Object)

Допустим, ты оставил `@ManyToOne` по умолчанию (EAGER).

- У `Заказа` есть EAGER ссылка на `Пользователя`.
    
- У `Пользователя` есть EAGER ссылка на `Компанию`.
    
- У `Компании` есть EAGER ссылка на `Страну`.
    

Тебе нужно было просто достать Заказ, чтобы изменить его статус (тебе не нужны ни юзер, ни компания). Но как только ты вызываешь `orderRepository.findById(1)`, Hibernate тянет за ниточку и **автоматически выкачивает полбазы**, генерируя кучу джоинов или дополнительных селектов. Память сервера забивается ненужными объектами.

### Причина Б: Невозможность отменить EAGER

Если связь настроена как `LAZY`, у тебя есть полный контроль. В одном методе ты можешь оставить её ленивой, в другом — написать `@EntityGraph` или `JOIN FETCH` и подгрузить данные одним запросом. Если связь настроена как `EAGER`, у тебя **нет способа сказать Hibernate: "В этот раз не грузи её"**. Она будет грузиться всегда и везде, в каждом запросе, хочешь ты этого или нет.

## 5. Итог: Как писать правильно

1. Всегда вешай `fetch = FetchType.LAZY` на **все** аннотации связей без исключения.
    
    Java
    
    ```
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "user_id")
    private User user;
    ```
    
2. Если для конкретной бизнес-логики (например, для отображения профиля) тебе нужны связанные данные, используй `@EntityGraph` на уровне репозитория, чтобы разово и эффективно подгрузить граф.
    
3. Никогда не возвращай Entity-классы из контроллера наружу. Превращай их в DTO (Data Transfer Object) **внутри слоя сервиса** (пока жива транзакция и прокси могут безопасно сработать), а наружу отдавай уже плоские, «глупые» объекты без логики.
