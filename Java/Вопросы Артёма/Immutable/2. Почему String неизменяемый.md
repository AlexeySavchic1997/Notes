### Часть 2. Почему класс `String` сделали Immutable?

Мы уже частично затрагивали этот вопрос, когда говорили про кэширование `hashCode`, но давай соберем полную картину. Это 4 столпа, на которых держится безопасность и производительность всей JVM.

#### 1. Пул строк (String Pool) и экономия памяти

Это паттерн проектирования _Flyweight (Приспособленец)_. Если в твоем приложении 10 000 раз встречается слово `"ERROR"`, JVM хранит в памяти **ровно один** такой объект. Все 10 000 переменных ссылаются на этот единственный участок памяти.

- **Что было бы, если бы String был изменяемым?** Если бы один поток решил изменить `"ERROR"` на `"WARNING"`, это слово моментально изменилось бы у всех остальных 9 999 потребителей по всей программе. Кэширование стало бы невозможным.
    

#### 2. Безопасность (Security) и уязвимость TOCTOU

Аббревиатура TOCTOU расшифровывается как _Time of Check to Time of Use (Время проверки — Время использования)_. Представь код аутентификации базы данных:

Java

```
String dbUrl = "jdbc:postgresql://localhost:5432/safe_db";
if (securityManager.checkAccess(dbUrl)) {
    // Подключение разрешено, открываем соединение
    database.connect(dbUrl);
}
```

- **Что было бы, если бы String был изменяемым?** Злоумышленник в параллельном потоке мог бы дождаться, пока пройдет проверка `checkAccess(dbUrl)`, и ровно в ту же миллисекунду сделать `dbUrl.replace("safe_db", "hacker_db")`. Приложение подключилось бы к вражеской базе. Неизменяемость `String` делает этот хак невозможным.
    

#### 3. Потокобезопасность (Thread Safety) из коробки

Неизменяемые объекты по своей природе **абсолютно потокобезопасны**. Тебе не нужно использовать `synchronized`, `volatile` или `ReentrantLock`, когда ты передаешь строку из одного потока в другой. Если объект невозможно изменить, значит, потоки никогда не подерутся за право его перезаписать (Race Condition просто не может возникнуть).

#### 4. Идеальный ключ для HashMap (Кэширование хэша)

Внутри класса `String` есть скрытое поле `private int hash;`. Когда ты первый раз вызываешь `myString.hashCode()`, строка прогоняет математический алгоритм, вычисляет свой хэш и сохраняет его в эту переменную. Все последующие вызовы вернут готовое число за _О(1)_.

- **Что было бы, если бы String был изменяемым?** Ты положил строку в `HashMap`. Она легла в корзину (bucket) №5 на основе своего хэша. Затем ты изменил строку. Её хэш изменился. Теперь она должна лежать в корзине №12. Но `HashMap` об этом не знает! Ты навсегда потерял доступ к своему значению в мапе (утечка памяти).
