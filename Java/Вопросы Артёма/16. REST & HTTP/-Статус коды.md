Все HTTP статус-коды жестко стандартизированы и делятся на 5 классов (по первой цифре). Для проектирования грамотного REST API нужно знать не все 60+ кодов, а только ключевой костяк.

Здесь собраны основные статусы с архитектурными пометками о том, как и когда их нужно использовать на практике.

### 1xx: Информационные (Informational)

Они используются на уровне сетевых прокси и балансировщиков. В бизнес-логике (в коде Java/Spring) ты с ними практически никогда не работаешь вручную.

- **`100 Continue`**: Клиент отправляет тяжелый файл и сначала спрашивает заголовком `Expect: 100-continue`: "Сервер, ты вообще готов принять 5 ГБ?". Сервер отвечает `100`, и клиент начинает передачу тела.
    
- **`101 Switching Protocols`**: Используется при апгрейде обычного HTTP-соединения в двунаправленный **WebSocket**.
    

### 2xx: Успех (Success)

Это главные статусы для возврата успешного результата. В REST API недостаточно всегда возвращать `200`.

- **`200 OK`**: Дефолтный ответ для `GET`, `PUT` или `PATCH`, если вместе со статусом ты возвращаешь тело (например, обновленный JSON ресурса).
    
- **`201 Created`**: Обязательный ответ для успешного `POST` запроса (создание ресурса).
    
    - _Senior-правило:_ Вместе с `201` сервер обязан вернуть HTTP-заголовок `Location`, в котором лежит URL только что созданного ресурса (например, `Location: /api/users/42`).
        
- **`202 Accepted`**: Асинхронная обработка. Говорит клиенту: "Я принял твою задачу (например, сгенерировать сложный отчет), она поставлена в очередь, но еще не готова". Часто возвращается со ссылкой, по которой можно проверять статус задачи.
    
- **`204 No Content`**: Запрос выполнен успешно, но **тела ответа не будет**. Это классический и самый правильный статус для метода `DELETE`, а также для `PUT`, если ты не хочешь гонять по сети только что обновленный JSON.
    

### 3xx: Перенаправления (Redirection)

Сервер говорит клиенту: "То, что ты ищешь, находится в другом месте" или "Возьми это из своего кэша".

- **`301 Moved Permanently`**: Ресурс перемещен навсегда.
    
    - _Опасность:_ Браузеры кэшируют этот ответ намертво. Если ты ошибочно вернешь `301`, браузеры пользователей больше никогда не отправят запрос на старый URL, даже если ты исправишь сервер.
        
- **`302 Found` / `307 Temporary Redirect`**: Временное перенаправление (например, при оплате заказа редирект на шлюз банка).
    
- **`304 Not Modified`**: **Святой Грааль оптимизации и кэширования.** Клиент присылает запрос: "Дай мне список городов, но только если он изменился с прошлой среды (заголовок `If-Modified-Since`)". Сервер видит, что города те же, и возвращает пустой `304`. Клиент берет данные из своего локального кэша. Экономия трафика 100%.
    

### 4xx: Ошибки клиента (Client Errors)

Как мы разбирали ранее, вина лежит на том, кто отправлял запрос.

- **`400 Bad Request`**: Нарушен синтаксис (кривой JSON) или провалена базовая валидация (email без `@`).
    
- **`401 Unauthorized`**: Проблема с токеном (его нет, он протух, он подделан). "Я не знаю, кто ты".
    
- **`403 Forbidden`**: С токеном всё отлично, но у пользователя (например, роль `USER`) нет прав на удаление администратора. "Я знаю, кто ты, но тебе туда нельзя".
    
- **`404 Not Found`**: Ресурс не найден в БД.
    
- **`405 Method Not Allowed`**: Клиент попытался сделать `POST` на URL, который поддерживает только `GET`.
    
- **`409 Conflict`**: Конфликт бизнес-логики. Например, попытка зарегистрировать пользователя с email, который уже есть в базе.
    
- **`415 Unsupported Media Type`**: Твой API ждет `application/json`, а клиент прислал `application/xml`.
    
- **`429 Too Many Requests`**: Сработал Rate Limiter (защита от DDoS). Клиент превысил лимит, например, 100 запросов в минуту.
    

### 5xx: Ошибки сервера (Server Errors)

Виноват бэкенд или инфраструктура.

- **`500 Internal Server Error`**: Приложение выбросило `RuntimeException` (баг в коде).
    
- **`502 Bad Gateway`**: Обычно отдает Nginx (или API Gateway). Означает, что Nginx попытался передать запрос твоему Java-приложению, но приложение либо мертво (процесс упал), либо ответило полным бредом.
    
- **`503 Service Unavailable`**: Сервер перегружен и не может обработать запрос (например, переполнен пул потоков или БД упала). Часто сопровождается заголовком `Retry-After: 60` (попробуй через минуту).
    
- **`504 Gateway Timeout`**: Nginx передал запрос в Java-приложение, но приложение "думало" слишком долго (например, зависло в Deadlock), и Nginx принудительно разорвал соединение по таймауту.

Работа со статус-кодами — это то место, где API превращается из простого интерфейса в предсказуемый контракт. Главное архитектурное правило REST гласит: **статус-коды — это словарный запас вашего API**. Не заставляйте клиента парсить текст ошибки, чтобы понять, что делать дальше.

Давай разберем философию распределения ошибок и современный стандарт их оформления.

## 1. Философия: 4xx против 5xx (Кто виноват?)

Самая частая ошибка джуниоров — возвращать `500 Internal Server Error` на любое исключение (например, если пользователь ввел неверный пароль или запросил несуществующий ID).

Разделение строгое:

- **4xx (Client Error):** Виноват клиент. Запрос составлен неверно или нарушает бизнес-логику. Клиенту **нет смысла повторять этот же запрос** — он снова упадет. Ему нужно изменить входные данные.
    
- **5xx (Server Error):** Виноват сервер (баг, упала БД, таймаут). Запрос клиента был идеальным. Клиент **может попробовать повторить (Retry)** тот же самый запрос через несколько секунд.
    

## 2. Маппинг бизнес-исключений на статус-коды

Вот шпаргалка Senior-разработчика по правильному маппингу исключений в глобальном перехватчике (`@ControllerAdvice` в Spring):

|**HTTP Статус**|**Когда возвращать**|**Примеры Java-исключений**|
|---|---|---|
|**400 Bad Request**|Синтаксическая ошибка в запросе, невалидный JSON, нарушена валидация полей (`@NotNull`, `@Size`).|`MethodArgumentNotValidException`, `HttpMessageNotReadableException`|
|**401 Unauthorized**|Клиент не предоставил токен авторизации или токен протух. (Кто ты?)|`BadCredentialsException`, `ExpiredJwtException`|
|**403 Forbidden**|Мы знаем, кто ты, но у тебя нет прав на эту операцию, ИЛИ нарушено жесткое бизнес-правило.|`AccessDeniedException`, `AccountLockedException`|
|**404 Not Found**|Запрошенный ресурс по URL не существует.|`EntityNotFoundException`, `UserNotFoundException`|
|**409 Conflict**|Конфликт состояний. Попытка создать дубликат или конфликт версий при конкурентном обновлении (Optimistic Locking).|`DataIntegrityViolationException`, `OptimisticLockException`|
|**422 Unprocessable Entity**|Запрос синтаксически верен, но семантически ошибочен (специфичная бизнес-ошибка). Например, недостаточно денег на счете.|`InsufficientFundsException`, `InvalidOrderStatusException`|
|**500 Internal Server Error**|Любой неожиданный RuntimeException (баги).|`NullPointerException`, `IndexOutOfBoundsException`|
|**502 / 503 / 504**|Ошибки инфраструктуры (обычно их отдает балансировщик или Gateway, а не само приложение).|`ConnectException`, `QueryTimeoutException` (иногда мапят на 503)|

> **Архитектурный спор (400 vs 422):**
> 
> Куда мапить ошибки бизнес-логики (например, "Нельзя отменить уже доставленный заказ")? Многие используют `400 Bad Request`. Но семантически правильнее использовать `422 Unprocessable Entity` (введен в WebDAV, но стал стандартом REST), так как синтаксис запроса (JSON) был правильным, подвела именно бизнес-семантика.

## 3. RFC 7807 (Problem Details for HTTP APIs)

До 2016 года царил хаос. Каждая компания придумывала свой формат тела ошибки. У одних был `{"error": "message"}`, у других `{"code": 404, "msg": "..."}`, у третьих сложный вложенный JSON. Клиентам приходилось писать разные парсеры для разных API.

**RFC 7807** — это официальный интернет-стандарт, описывающий, как должен выглядеть JSON с ошибкой. В Spring Framework (начиная со Spring Boot 3) он поддерживается "из коробки" через класс `ProblemDetail`.

Его формат (Content-Type: `application/problem+json`) строго специфицирован пятью базовыми полями:

JSON

```
{
  "type": "https://api.example.com/errors/insufficient-funds",
  "title": "Недостаточно средств",
  "status": 422,
  "detail": "На счете пользователя 123 осталось только 50 рублей, запрошено 100.",
  "instance": "/users/123/transactions",
  "balance": 50 
}
```

**Разбор полей:**

1. **`type`** (Обязательное) — URI, который уникально идентифицирует тип ошибки. Если разработчик клиента перейдет по этой ссылке, он должен увидеть документацию о том, как эту ошибку исправить.
    
2. **`title`** — Короткое, человекочитаемое название ошибки (не должно меняться от запроса к запросу).
    
3. **`status`** — Дублирует HTTP-статус код (удобно, если ошибка прошла через прокси, который исказил заголовки).
    
4. **`detail`** — Человекочитаемое объяснение конкретно _этого_ инцидента.
    
5. **`instance`** — URI конкретного ресурса, на котором произошел сбой (или ID трейса для логов).
    
6. _Кастомные поля (Extensions):_ RFC 7807 позволяет добавлять любые свои поля в корень JSON (например, `balance`), чтобы передать клиенту контекст ошибки.
    

### Как это реализовать в Spring Boot 3?

Вам больше не нужно создавать свои классы `ApiError`. Вы просто возвращаете стандартный класс `ProblemDetail`:

Java

```
@ExceptionHandler(InsufficientFundsException.class)
public ResponseEntity<ProblemDetail> handleFundsError(InsufficientFundsException ex, HttpServletRequest request) {
    ProblemDetail problem = ProblemDetail.forStatusAndDetail(HttpStatus.UNPROCESSABLE_ENTITY, ex.getMessage());
    problem.setType(URI.create("https://api.mybank.com/docs/errors/insufficient-funds"));
    problem.setTitle("Недостаточно средств");
    problem.setInstance(URI.create(request.getRequestURI()));
    
    // Добавляем кастомное поле
    problem.setProperty("current_balance", ex.getCurrentBalance());
    
    return ResponseEntity.status(HttpStatus.UNPROCESSABLE_ENTITY).body(problem);
}
```
