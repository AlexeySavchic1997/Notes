В архитектуре REST HTTP-методы (или "глаголы") играют роль действий, которые мы хотим совершить над ресурсом.

Чтобы ответить на этот вопрос на уровне Senior, нужно сначала определить два фундаментальных термина из спецификации HTTP:

1. **Безопасный метод (Safe):** Метод, который **только читает** данные и не изменяет состояние сервера. Клиент может вызывать его сколько угодно раз, не боясь что-то сломать.
    
2. **Идемпотентный метод (Idempotent):** Метод, многократное выполнение которого приводит к **точно такому же состоянию системы**, как и однократное. (Внимание: статус-коды ответа при этом могут отличаться, главное — состояние базы данных).
    

Вот как распределяются основные методы:

### 1. GET (Чтение)

- **Когда использовать:** Для получения списка ресурсов или одного конкретного ресурса по ID.
    
- **Характеристики:** 🟢 **Безопасный** | 🟢 **Идемпотентный**
    
- **Архитектурное правило:** В `GET` запросах **никогда не должно быть тела (Body)**. Все параметры передаются либо в пути (`/users/123`), либо в Query-параметрах (`/users?status=active&page=2`).
    
- **Ловушка:** Никогда не используйте `GET` для действий, меняющих состояние (например, `GET /users/123/delete` или `GET /logout`). Это огромная дыра в безопасности (поисковики или браузерные предзагрузчики могут случайно "прокликать" эти URL и удалить вам данные).
    

### 2. POST (Создание / Выполнение)

- **Когда использовать:**
    
    1. Для создания **нового** ресурса, когда сервер сам генерирует ему ID (клиент не знает ID заранее). `POST /users`.
        
    2. Как "универсальный солдат" для сложных бизнес-операций, которые не ложатся на CRUD (например, `POST /orders/123/pay` или `POST /calculate-tax`).
        
- **Характеристики:** 🔴 **Не безопасный** | 🔴 **НЕ идемпотентный**
    
- **Архитектурное правило:** Если клиент из-за лагов сети отправит один и тот же `POST` запрос дважды, в базе создадутся два пользователя (или спишутся две оплаты). Поэтому на фронтенде блокируют кнопки после нажатия, а на бэкенде вводят механизмы вроде `Idempotency-Key` для критичных операций.
    

### 3. PUT (Полная замена)

- **Когда использовать:** Для **полной замены** существующего ресурса, либо для его создания, если клиент **сам задает ID**.
    
- **Характеристики:** 🔴 **Не безопасный** | 🟢 **Идемпотентный**
    
- **Архитектурное правило:** `PUT /users/123` означает: "Возьми вот этот JSON и сделай так, чтобы ресурс 123 выглядел _ровно так же_". Если в базе у пользователя было 10 полей, а клиент в PUT-запросе прислал только 3, остальные 7 полей бэкенд обязан затереть (записать туда `null`).
    
- **Идемпотентность:** Если отправить этот JSON 1 раз или 100 раз, пользователь в базе будет выглядеть одинаково.
    

### 4. PATCH (Частичное обновление)

- **Когда использовать:** Когда нужно изменить только 1-2 поля ресурса, не трогая остальные. Клиент присылает только то, что изменилось.
    
- **Характеристики:** 🔴 **Не безопасный** | 🟡 **Зависит от реализации (По стандарту НЕ идемпотентный)**
    
- **Архитектурный нюанс:** Почему PATCH по стандарту RFC 5789 не идемпотентен? Если PATCH отправляет просто JSON с новым именем (`{"name": "Ivan"}`), то он идемпотентен. Но по стандарту PATCH может принимать команды модификации. Например, `{"$inc": {"balance": 100}}` (увеличить баланс на 100). Если отправить такой PATCH дважды, баланс увеличится на 200. Состояние изменилось! Поэтому формально PATCH не гарантирует идемпотентности.
    

### 5. DELETE (Удаление)

- **Когда использовать:** Для удаления ресурса по его URL (`DELETE /users/123`).
    
- **Характеристики:** 🔴 **Не безопасный** | 🟢 **Идемпотентный**
    
- **Нюанс идемпотентности:** Многие спорят: "Если я отправлю DELETE первый раз, я получу `204 No Content` (успех). Если отправлю второй раз — получу `404 Not Found`. Ответы разные, значит метод не идемпотентный!". _Это ошибка._ Идемпотентность описывает **состояние сервера**, а не ответ. И после первого, и после сотого запроса состояние БД одинаково: ресурса `123` там нет. Следовательно, DELETE идемпотентен.
    

### Вспомогательные методы

- **HEAD:** Работает точно как `GET`, но сервер возвращает **только заголовки** (без Body). Нужен для проверки: существует ли ресурс, когда он был изменен или какой у него размер (Content-Length), не скачивая сам гигабайтный файл.
    
- **OPTIONS:** Используется браузерами под капотом для CORS (Cross-Origin Resource Sharing). Браузер делает "Preflight" запрос: "Сервер, а ты разрешишь мне с домена `a.com` сделать `POST` на `b.com`?".

### Сводная таблица (Шпаргалка)

|**Метод**|**Действие**|**Безопасный (Только чтение)**|**Идемпотентный (Можно повторять)**|
|---|---|---|---|
|**GET**|Прочитать|Да|Да|
|**POST**|Создать / Выполнить|Нет|**Нет**|
|**PUT**|Полностью заменить|Нет|Да|
|**PATCH**|Частично изменить|Нет|Нет (зависит от логики)|
|**DELETE**|Удалить|Нет|Да|
