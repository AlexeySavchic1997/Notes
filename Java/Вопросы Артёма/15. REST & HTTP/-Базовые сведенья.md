Отличный сдвиг фокуса. Переход от внутренностей JVM к сетевому взаимодействию — это классический путь развития от Middle к Senior.

Главная архитектурная проблема, с которой сталкиваются на проектах: **разработчики путают HTTP и REST**. Они считают, что если их API возвращает JSON и работает по порту 80/443, то это REST. На самом деле это совершенно разные концепции.

Давай заложим строгий технический фундамент, разделив транспорт и архитектуру.

## 1. HTTP: Двигатель (Протокол передачи данных)

**HTTP (HyperText Transfer Protocol)** — это прикладной протокол обмена данными. Это просто набор строгих текстовых правил о том, как клиент и сервер должны переговариваться друг с другом.

У HTTP есть две важнейшие технические характеристики:

1. **Клиент-серверная модель:** Клиент всегда инициирует запрос, сервер всегда отвечает. Сервер не может сам "пнуть" клиента по голому HTTP (для этого нужны WebSockets или Server-Sent Events).
    
2. **Stateless (Без состояния):** Сервер не запоминает предыдущие запросы клиента. Каждый новый запрос должен содержать абсолютно всю информацию для его выполнения (например, токены авторизации). Это главное условие горизонтального масштабирования (балансировщик может отправить второй запрос клиента на совершенно другой сервер).
    

**Анатомия HTTP-запроса:**

Plaintext

```
POST /api/users HTTP/1.1         <-- Стартовая строка (Метод + Путь + Версия протокола)
Host: api.example.com            <-- Заголовки (Headers) метаданных
Authorization: Bearer xyz...
Content-Type: application/json

{"name": "Ivan", "role": "dev"}  <-- Тело (Body)
```

**Анатомия HTTP-ответа:**

Plaintext

```
HTTP/1.1 201 Created             <-- Стартовая строка (Протокол + Статус-код)
Content-Type: application/json   <-- Заголовки
Content-Length: 45

{"id": 105, "name": "Ivan"}      <-- Тело
```

## 2. REST: Философия (Архитектурный стиль)

**REST (Representational State Transfer)** — это не протокол. Это набор жестких ограничений (констрейнтов), придуманных Роем Филдингом в 2000 году для проектирования распределенных систем.

REST _использует_ HTTP как транспорт, но заставляет нас смотреть на API не как на набор функций (вызови метод `getUsers()`), а как на **набор Ресурсов**.

### Главные законы REST API:

- **Всё есть ресурс (Существительные, а не глаголы).**
    
    В REST мы не обращаемся к действиям. URL должен указывать на объект.
    
    - _Плохо (RPC-стиль):_ `POST /createUser`, `GET /getAllUsers`, `POST /deleteUser?id=5`
        
    - _Хорошо (REST-стиль):_ `GET /users`, `POST /users`, `DELETE /users/5`
        
- **Действия определяются HTTP-методами.**
    
    - `GET` — получить (безопасный метод, не меняет данные).
        
    - `POST` — создать новый ресурс.
        
    - `PUT` — полностью заменить ресурс (или создать с заранее известным ID).
        
    - `PATCH` — частично обновить ресурс.
        
    - `DELETE` — удалить ресурс.
        
- **Идемпотентность (Idempotency).**
    
    Это критическое понятие для Senior'а. Идемпотентность означает, что если клиент выполнит один и тот же запрос 1 раз или 100 раз подряд (например, из-за лагов сети), состояние сервера будет **одинаковым**.
    
    - `GET`, `PUT`, `DELETE` — **идемпотентны**. Если ты удалил пользователя 100 раз, его в базе всё равно нет.
        
    - `POST` — **не идемпотентен**. Если ты отправишь POST 100 раз, в базе создастся 100 одинаковых пользователей с разными ID.
        

## 3. Модель зрелости Ричардсона (Richardson Maturity Model)

Чтобы оценить, насколько ваше API действительно "RESTful", Леонард Ричардсон придумал 4 уровня зрелости. Большинство современных "REST API" застревают на уровне 2.

- **Уровень 0 (The Swamp of POX):** Использование HTTP только как туннеля. Один URL (например, `/api`) и один метод (`POST`). Внутри передается XML или JSON с указанием того, что нужно сделать (классический SOAP).
    
- **Уровень 1 (Resources):** Появление разных URL для разных объектов (`/users`, `/orders`), но метод всё еще один — обычно POST или GET.
    
- **Уровень 2 (HTTP Verbs):** Правильное использование HTTP-методов (`GET`, `POST`, `PUT`, `DELETE`) и HTTP статус-кодов (`200 OK`, `201 Created`, `404 Not Found`). Именно это большинство разработчиков называет REST.
    
- **Уровень 3 (HATEOAS):** Святой Грааль REST. Hypermedia As The Engine Of Application State. Ответ сервера содержит не только данные, но и **ссылки на следующие возможные действия** (как ссылки на веб-странице). Клиенту не нужно хардкодить URL-ы, он "путешествует" по API, читая ссылки в ответах сервера.
