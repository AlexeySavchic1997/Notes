На уровне Junior разработчик думает: _"Мой код компилируется, тесты зеленые, значит, задача выполнена"_. На уровне Senior задача считается невыполненной, если код выкачен на прод, но он "слепой". Метрики — это твои глаза и уши в production-среде. Без них ты узнаешь о падении базы данных от разгневанных клиентов, а не от системы алертинга.

В современной архитектуре (особенно в микросервисах) метрики — это один из трех столпов **Observability (Наблюдаемости)** наряду с логами и распределенными трейсами.

Давай разберем, как они устроены, какие бывают, и — самое главное — как неосторожное использование метрик может "положить" весь сервер.

### 1. Что такое метрики? (Логи vs Метрики)

Частая ошибка — путать метрики и логи.

- **Логи** — это текст о конкретном событии: _"В 12:00 юзер Ivan купил товар ID=5"_. Логи тяжелые, их дорого хранить, по ним медленно искать.
    
- **Метрики** — это агрегированные числа во времени (Time-Series Data): _"С 12:00 до 12:01 у нас было 500 покупок, 3 ошибки БД, среднее время ответа 45 мс"_. Метрики весят копейки, и по ним строятся графики в Grafana.
    

**Золотой стандарт типов метрик (на примере Prometheus / Micrometer):**

1. **Counter (Счетчик):** Число, которое может только расти (или сбрасываться в ноль при рестарте). _Пример:_ Количество HTTP-запросов, количество `NullPointerException`.
    
2. **Gauge (Измеритель):** Число, которое может идти вверх и вниз. Это "моментальный снимок" текущего состояния. _Пример:_ Размер пула соединений с БД (HikariCP), количество занятой памяти JVM (Heap), количество элементов в очереди Kafka.
    
3. **Histogram / Summary (Гистограмма):** Самый сложный тип. Он не просто считает количество, но и распределяет данные по "корзинам" (buckets), чтобы мы могли понять время выполнения (Latency). _Пример:_ Время выполнения SQL-запроса, время обработки HTTP-запроса.
    

### 2. Главная фишка Senior'а: Почему Среднее время (Average) врет?

На собеседовании тебя могут спросить: _"Как ты будешь измерять время ответа твоего API?"_ Если ты ответишь: _"Буду считать среднее время (Average / Mean)"_ — это провал.

**Почему среднее врет:** Представь, что у тебя 99 запросов выполнились за 10 мс, а один запрос завис на таймауте и выполнялся 10 000 мс. Среднее время будет: `(99 * 10 + 10000) / 100 = 109 мс`. Глядя на график в 109 мс, ты подумаешь, что всё более-менее нормально. Но на самом деле один конкретный клиент только что получил ужасный опыт (ждал 10 секунд).

**Решение — Перцентили (Percentiles):** Метрики-гистограммы позволяют считать квантили: **p95, p99, p99.9**.

- **p99 = 10 000 мс.** Это значит, что 99% всех запросов уложились в 10 000 мс.
    
- Увидев на графике скачок p99 до 10 секунд, дежурный инженер сразу забьет тревогу. В серьезных компаниях SLA (договоры об уровне обслуживания) пишутся только в перцентилях (например, "p99 < 200ms").
    

### 3. Как метрики влияют на код? (Архитектура)

В экосистеме Spring Boot стандартом является библиотека **Micrometer** (это как SLF4J, только для метрик). Она позволяет писать метрики абстрактно, а под капотом они могут улетать в Prometheus, Datadog или New Relic.

#### А. Засорение бизнес-логики (Антипаттерн)

Джуниор будет инжектить `MeterRegistry` в каждый сервис и руками вызывать `timer.record()`, превращая чистую бизнес-логику в спагетти из мониторинга.

_Решение Senior'а:_ Использование **AOP (Aspect-Oriented Programming)** или фильтров. Для HTTP-запросов метрики собираются на уровне фильтров Tomcat/Spring Web (из коробки). Для кастомных методов используется аннотация `@Timed` из Micrometer, которая под капотом через AOP замеряет время выполнения метода, не загрязняя сам код.

#### Б. High Cardinality (Убийца мониторинга) — Ловушка на проде

Метрики имеют **Теги (Tags/Labels)**. Например, счетчик `http_requests_total` может иметь теги `method="GET"`, `status="200"`.

В базе данных временных рядов (Time-Series DB, как Prometheus) каждая **уникальная комбинация тегов создает новый временной ряд в оперативной памяти**.

**Катастрофа в коде:** Разработчик решает добавить в метрику тег `user_id`, чтобы видеть, какой юзер сколько запросов делает:

Java

```java
// ПЛОХО! Убьет сервер Prometheus
registry.counter("user.purchases", "user_id", user.getId().toString()).increment();
```

Если у тебя 1 миллион пользователей, метрика `user.purchases` размножится на 1 миллион уникальных временных рядов (Time Series). Prometheus исчерпает оперативную память (OOM) и упадет. Этот эффект называется **High Cardinality (Высокая кардинальность)**.

> **Правило Архитектора:** В теги метрик можно класть ТОЛЬКО перечисления (Enum) с ограниченным набором значений. Статус ответа (200, 404, 500), название метода, имя эндпоинта. **Никогда** не клади туда динамические данные (UUID, user_id, email, параметры поиска). Если нужно отследить действия конкретного юзера — это задача для Логов или Трейсов, а не для Метрик.

#### В. Нагрузка на GC (Garbage Collector)

Сбор метрик происходит на каждый запрос. Если при формировании тегов для метрики ты делаешь конкатенацию строк (`"user_" + status`) или тяжелые вычисления, на 10 000 RPS ты создашь гигантскую нагрузку на Garbage Collector, выделяя миллионы короткоживущих строковых объектов. Инструменты вроде Micrometer специально спроектированы так, чтобы использовать кэшированные теги и избегать аллокации памяти.

Чтобы разобраться в метриках с самого начала и до уровня Senior, нужно понять одну главную архитектурную концепцию: **мы больше не пишем код под конкретную систему мониторинга**.

Раньше разработчики брали библиотеку от Prometheus и хардкодили ее прямо в бизнес-логику. Если компания переходила на Datadog, приходилось переписывать половину приложения.

Сегодня стандартом индустрии (в мире Java/Spring) является фасад. Давай разберем этот стек снизу вверх.

### 1. Фундамент: Библиотека Micrometer (SLF4J для метрик)

В Java есть SLF4J — абстракция над логами. Ты пишешь `log.info()`, а под капотом работает Logback или Log4j. **Micrometer** — это то же самое, но для метрик.

Твое приложение знает только про Micrometer. Ты говоришь ему: _"Увеличь счетчик ошибок на 1"_. А уже сам Micrometer, имея нужный плагин (Registry), переводит эту команду в текстовый формат для Prometheus, в JSON для Datadog или в бинарный формат для Graphite.

### 2. Точка входа в Spring Boot: Actuator

**Spring Boot Actuator** — это модуль, который отвечает за «готовность приложения к продакшену» (production-ready features). Он берет Micrometer, автоматически собирает кучу стандартных метрик (память, процессор, база данных) и открывает HTTP-эндпоинты (например, `/actuator/health` и `/actuator/prometheus`), чтобы внешние системы могли эти метрики забрать.

### 3. Как внедрить метрики в проект (Пошаговый гайд)

Представим, мы создаем микросервис с нуля. Нам нужно настроить связку **Spring Boot + Micrometer + Prometheus**.

#### Шаг 1: Зависимости и Настройки

В `pom.xml` добавляем два стартера:

XML

```xml
<!-- Открывает эндпоинты мониторинга -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
<!-- Транслирует метрики Micrometer в формат Prometheus -->
<dependency>
    <groupId>io.micrometer</groupId>
    <artifactId>micrometer-registry-prometheus</artifactId>
</dependency>
```

В `application.yml` открываем доступ для Prometheus:

```yaml
management:
  endpoints:
    web:
      exposure:
        include: "health,prometheus" # Открываем нужные пути
  metrics:
    tags:
      application: "my-service" # Глобальный тег, чтобы отличать сервисы в Grafana
```

_Уже на этом этапе_, если запустить приложение и перейти на `localhost:8080/actuator/prometheus`, ты увидишь простыню текста. Это метрики JVM (Heap, GC), пула потоков Tomcat и пула соединений HikariCP, которые Actuator собрал **бесплатно, из коробки**.

#### Шаг 2: Внедрение в бизнес-логику (3 уровня)

Теперь мы хотим измерять нашу собственную бизнес-логику. Есть три способа сделать это, от худшего к лучшему.

**Уровень 1: Ручное внедрение (Programmatic)** Мы инжектим главный класс Micrometer — `MeterRegistry`. Это полезно, когда нужна сложная динамическая логика.

Java

```java
@Service
@RequiredArgsConstructor
public class OrderService {
    
    // Внедряем реестр метрик
    private final MeterRegistry meterRegistry;

    public void createOrder(Order order) {
        try {
            // ... логика сохранения ...
            
            // Инкрементируем счетчик (Counter). Указываем тег статуса.
            meterRegistry.counter("business.orders.created", "status", "SUCCESS").increment();
        } catch (Exception e) {
            meterRegistry.counter("business.orders.created", "status", "FAILED").increment();
            throw e;
        }
    }
}
```

_Минус:_ Код засоряется служебными вызовами. Нарушается принцип единой ответственности (SRP).

**Уровень 2: Декларативное измерение времени (AOP)** Для измерения времени выполнения (Таймеры/Гистограммы) используют аннотацию `@Timed`. _Ловушка для собеседования:_ Сама по себе `@Timed` ничего не делает! Чтобы она заработала, нужно зарегистрировать AOP-аспект, который идет в комплекте с Micrometer, но выключен по умолчанию.

_1. Включаем Аспект (в конфигурации):_

Java

```
@Configuration
public class MetricsConfig {
    @Bean
    public TimedAspect timedAspect(MeterRegistry registry) {
        return new TimedAspect(registry);
    }
}
```

_2. Вешаем аннотацию на метод:_

Java

```
@Service
public class ReportService {

    // Micrometer сам засечет время старта, время конца, запишет в гистограмму 
    // и учтет исключения, если они вылетят.
    @Timed(value = "business.report.generation.time", description = "Time taken to generate report")
    public byte[] generateHeavyReport() {
        // ... тяжелая логика ...
    }
}
```

**Уровень 3: Измерение состояний (Gauge)** Джуниоры часто пытаются использовать Gauge (Измеритель) неправильно — руками прибавляя и убавляя значение. **Gauge в Micrometer работает на коллбэках (Pull-модель).** Ты не пушишь в него значение, ты "привязываешь" его к какому-то объекту, и метрика сама опрашивает этот объект в момент сбора данных.

Java

```
@Component
public class ActiveCartMonitor {

    private final Map<String, Cart> activeCarts = new ConcurrentHashMap<>();

    public ActiveCartMonitor(MeterRegistry registry) {
        // Мы говорим Micrometer: "Создай метрику 'carts.active'. 
        // Когда Prometheus придет за данными, вызови activeCarts.size() и отдай результат."
        Gauge.builder("business.carts.active", activeCarts, Map::size)
             .description("Number of active shopping carts")
             .register(registry);
    }
}
```

Это невероятно эффективно: мы не тратим процессорное время на обновление метрики при каждом добавлении/удалении корзины. Значение вычисляется только раз в 15-30 секунд, когда Prometheus запрашивает данные.

### 4. Как Prometheus забирает эти данные? (Pull Model)

Большинство старых систем (например, Graphite/StatsD) работали по **Push-модели**: приложение само каждую секунду отправляло по сети UDP/TCP пакеты с метриками на сервер мониторинга. Это тратило ресурсы приложения и приводило к потере пакетов.

Prometheus работает по **Pull-модели**:

1. Твое приложение просто держит метрики в своей оперативной памяти (в структурах данных `MeterRegistry`). Это работает со скоростью света, никаких сетевых вызовов при `counter.increment()`.
    
2. Сервер Prometheus раз в 15 секунд делает обычный HTTP `GET /actuator/prometheus` к твоему приложению.
    
3. Actuator быстро сериализует память `MeterRegistry` в текст и отдает ответ.
    
4. Prometheus сохраняет это в свою Time-Series БД.
    

Если сервер Prometheus упадет, твое приложение даже не заметит этого (просто метрики будут накапливаться и перезаписываться в RAM приложения, пока Prometheus не поднимется). Это делает систему невероятно отказоустойчивой.
