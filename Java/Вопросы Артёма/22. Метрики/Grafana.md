Для разработчика Grafana — это не просто "красивые графики для менеджеров". Это твое главное алиби на проде («мой код работает быстро, тормозит база данных») и твой главный инструмент для дебага во время ночных инцидентов.

Связь между ними простая: **Prometheus — это backend (БД), а Grafana — это frontend (UI)**. Каждый раз, когда ты открываешь дашборд, Grafana под капотом отправляет десятки PromQL-запросов в Prometheus и отрисовывает результаты.

На уровне Senior/Architect от тебя ждут понимания **четырех архитектурных концепций** работы с Grafana.

### 1. Подход RED (Что именно мы выводим на графики)

Джуниор выведет на дашборд всё подряд: количество потоков, размер кэша, температуру процессора. В итоге во время аварии на экране будет 50 графиков, и никто не поймет, что сломалось.

Senior Java-разработчик строит дашборды для микросервисов по стандарту **RED (Rate, Errors, Duration)**. Тебе нужно знать, как метрики Spring Boot маппятся на эти три графика:

- **R (Rate — Нагрузка):** Сколько запросов в секунду (RPS) обрабатывает сервис.
    
    - _Метрика Spring:_ `rate(http_server_requests_seconds_count[1m])`
        
- **E (Errors — Ошибки):** Процент запросов, завершившихся с HTTP 5xx.
    
    - _Метрика Spring:_ Та же самая, но с фильтром `status~="5.."` (регулярное выражение).
        
- **D (Duration — Задержка):** Тот самый p95 и p99 перцентиль времени ответа, о котором мы говорили.
    
    - _Метрика Spring:_ `histogram_quantile(0.99, rate(http_server_requests_seconds_bucket[1m]))`
        

Если эти три графика зеленые — с твоим кодом всё отлично. Всё остальное (GC, Heap, CPU) — это уже вторичные метрики (USE method) для поиска _причины_, если RED-графики покраснели.

### 2. Шаблонизация (Variables) — Никакого хардкода

На проде у тебя один и тот же микросервис крутится в 3 окружениях (Dev, Stage, Prod), а на проде работает 20 его копий (подов).

**Junior:** Создаст 3 разных дашборда для каждого окружения. **Senior:** Создаст один дашборд и настроит в Grafana **Variables (Переменные)**. В левом верхнем углу дашборда будут выпадающие списки: `Environment`, `Data Center`, `Pod Name`. Ты выбираешь `$env = prod`, и Grafana динамически подставляет эту переменную во все PromQL запросы. Твой дашборд становится универсальным.

### 3. Dashboards as Code (Инфраструктура как код)

Никто не настраивает графики мышкой на продакшене. Если сервер Grafana упадет, все твои труды исчезнут.

В серьезных компаниях дашборды хранятся **в Git-репозитории в виде JSON-файлов** (или описываются через Terraform). Как это выглядит для Java-разработчика:

1. Ты поднимаешь Grafana локально через Docker.
    
2. Мышкой собираешь красивый график для своей новой фичи.
    
3. Нажимаешь "Export to JSON".
    
4. Кладешь этот JSON в репозиторий твоего микросервиса (например, в папку `grafana/dashboards`).
    
5. CI/CD пайплайн при релизе сам загрузит этот JSON на боевой сервер Grafana.
    

### 4. Магия Senior'а: Exemplars (Связь метрик и трейсов)

Это самая крутая фича современных систем Observability (поддерживается в Spring Boot 3 / Micrometer 1.10+).

**Проблема:** Ты смотришь в Grafana и видишь, что на графике Duration (Время ответа) есть пик — один из запросов выполнялся 15 секунд. Но графики анонимны. Как найти логи _именно этого_ долгого запроса?

**Решение (Exemplars):** Micrometer умеет "приклеивать" к некоторым значениям гистограммы уникальный **Trace ID** (идентификатор конкретного запроса). В Grafana этот пик на графике будет подсвечен маленькой точкой (Exemplar). Ты кликаешь на эту точку мышкой, и Grafana мгновенно открывает тебе систему логирования, отфильтрованную ровно по тому самому запросу, который тормозил! Ты за одну секунду переходишь от абстрактного графика к логам с конкретным `NullPointerException` или медленным SQL.

> **Итог:** Тебе не нужно уметь администрировать Grafana. Тебе нужно уметь собирать из метрик твоего приложения **RED-дашборды**, экспортировать их в **JSON** и понимать, как с помощью переменных переключаться между нодами, чтобы быстро находить виновника аварии.
