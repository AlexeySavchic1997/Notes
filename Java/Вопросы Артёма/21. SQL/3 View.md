На уровне Senior отношение к `VIEW` (Представлениям) сильно отличается от базового понимания "это просто сохраненный запрос". В архитектуре баз данных представления делятся на два абсолютно разных типа, которые решают разные задачи: **Виртуальные (Standard Views)** и **Физические (Materialized Views)**.

Давай разберем их механику, ловушки производительности и то, как их используют для рефакторинга старых баз данных.

### 1. Standard View (Обычное представление)

Обычная View — это виртуальная таблица. Она **не хранит никаких данных на диске**. Это просто синтаксический сахар, закладка на SQL-запрос.

**Как это работает под капотом (Rule System):** Когда ты делаешь `SELECT * FROM active_users_view`, планировщик PostgreSQL не идет искать такую таблицу. Работает подсистема **Query Rewriter (Переписыватель запросов)**:

1. Он берет твой внешний запрос.
    
2. Подставляет вместо названия View ее исходный SQL-код (макроподстановка).
    
3. "Склеивает" их вместе и только потом строит план выполнения (`EXPLAIN`).
    

**Главное заблуждение (Ловушка на собеседовании):** _Ускоряет ли обычная View запрос?_ **НЕТ.** Если внутри View написан JOIN пяти таблиц, а ты делаешь `SELECT * FROM view LIMIT 10`, базе все равно придется выполнять тяжелую логику. View нужна только для инкапсуляции сложности (чтобы бэкендеры не писали 50 строк SQL в коде) и для безопасности.

**Обновляемые View (Updatable Views):** Джуниоры часто говорят, что во View нельзя делать `INSERT` или `UPDATE`. Это неправда.

- **Автоматически:** Если View ссылается строго на одну таблицу, не содержит `GROUP BY`, `DISTINCT` или `LIMIT`, Postgres сам транслирует твой `UPDATE my_view` в `UPDATE my_table`.
    
- **Через INSTEAD OF Triggers:** Если View сложная (склеена из 3 таблиц), ты можешь повесить на нее триггер `INSTEAD OF UPDATE`. Когда приложение попытается обновить View, сработает триггер, который под капотом аккуратно разложит новые данные по нужным реальным таблицам. Это гениальный паттерн для рефакторинга Legacy-баз, когда нельзя ломать старый API.
    

### 2. Materialized View (Материализованное представление)

Вот здесь начинается настоящая производительность (System Design). `MATERIALIZED VIEW` **физически сохраняет результат выполнения запроса на жесткий диск**.

**Где это применяется:** Тяжелые аналитические отчеты, дашборды. Например, запрос, считающий выручку магазина за каждый день по всем городам, работает 40 секунд. Если 100 менеджеров откроют дашборд, база "ляжет". Мы создаем мат. вью:

SQL

```
CREATE MATERIALIZED VIEW daily_sales AS 
SELECT date, city, SUM(amount) ... GROUP BY date, city;
```

Теперь запрос выполняется мгновенно, потому что Postgres просто читает готовые данные с диска, как из обычной таблицы. На материализованные представления **можно и нужно вешать индексы** (B-Tree, BRIN).

**Как решается проблема "Протухания" данных:** Данные в мат. вью не обновляются сами при изменении оригинальных таблиц (в отличие от Oracle, в Postgres это нужно делать явно). Для этого вызывают команду: `REFRESH MATERIALIZED VIEW daily_sales;`

**Фишка Senior'а (Блокировки и CONCURRENTLY):** Обычный вызов `REFRESH` берет жесткую блокировку (`AccessExclusiveLock`). Пока новые данные считаются (а это может занять минуты), **все SELECT-запросы к дашборду зависнут**. На проде это катастрофа. _Решение:_

SQL

```
REFRESH MATERIALIZED VIEW CONCURRENTLY daily_sales;
```

Эта команда обновляет данные в фоне. Пользователи продолжают читать старую версию, пока не достроится новая, и потом база мгновенно подменяет их без простоя. _Важное условие:_ Чтобы `CONCURRENTLY` сработал, на мат. вью должен быть предварительно создан уникальный индекс (`UNIQUE INDEX`), чтобы Postgres мог точечно сравнивать старые и новые строки.

### 3. Зачем View нужны архитектурно? (Data Masking)

Кроме аналитики, View — это главный инструмент безопасности. Если у тебя есть таблица `employees` с полями `id, name, department, salary, ssn`, ты не должен давать аналитикам или сторонним сервисам прямой доступ к ней.

Ты создаешь View:

SQL

```
CREATE VIEW public_employees AS 
SELECT id, name, department FROM employees;
```

И выдаешь права (`GRANT SELECT`) только на эту View. Оригинальная таблица остается скрытой, и утечка персональных данных (зарплат и паспортов) невозможна на уровне самого движка СУБД.
