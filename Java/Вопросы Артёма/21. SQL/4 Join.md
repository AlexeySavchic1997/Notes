Когда на собеседовании просят рассказать про JOIN-ы, джуниоры начинают рисовать круги Эйлера (INNER, LEFT, RIGHT). Но круги Эйлера — это _логический_ уровень (то, **что** мы хотим получить).

На уровне Senior спрашивают про _физический_ уровень — **как именно** база данных будет искать и склеивать эти строки на жестком диске.

Планировщик PostgreSQL (Query Planner) при построении `EXPLAIN` плана выбирает один из трех физических алгоритмов. Давай разберем их механику, плюсы и главные узкие места.

### 1. Nested Loop (Вложенные циклы) — Классика

Это самый базовый и "интуитивный" алгоритм. База берет одну таблицу (внешнюю/ведущую) и для каждой её строки бежит по второй таблице (внутренней/ведомой), ища совпадения.

- **Как это выглядит в коде:**
    
    Java
    
    ```
    for (Row outerRow : tableA) {
        for (Row innerRow : tableB) {
            if (outerRow.id == innerRow.a_id) return result;
        }
    }
    ```
    
- **Худший сценарий (Без индексов):** Если в таблице A — 10 000 строк, и в таблице B — 10 000 строк, базе придется сделать 100 миллионов сравнений ($O(N \times M)$). Это убьет производительность.
    
- **Лучший сценарий (Index Nested Loop):** База идет по первой таблице, берет `id` и **делает точечный поиск по B-Tree индексу** второй таблицы. Никакого полного перебора! Сложность падает до $O(N \log M)$.
    

**Когда планировщик выбирает Nested Loop:**

1. Когда одна из таблиц (после фильтрации `WHERE`) **очень маленькая** (например, 5-100 строк), а на второй таблице есть индекс по колонке соединения.
    
2. **Вынужденно:** Если условие JOIN построено **НЕ на равенстве** (например, `ON a.date < b.date` или `ON a.name LIKE b.name`). Другие алгоритмы не умеют работать с неравенствами.
    

### 2. Hash Join (Хэш-соединение) — Убийца памяти

Это самый популярный алгоритм в современных базах данных для соединения средних и больших таблиц, на которых нет удобных индексов.

**Как он работает (Две фазы):**

1. **Build Phase (Фаза сборки):** Планировщик берет _меньшую_ из двух таблиц и строит из нее хэш-таблицу прямо в оперативной памяти. Ключом выступает колонка из `JOIN ON`.
    
2. **Probe Phase (Фаза зондирования):** База начинает построчно читать вторую (большую) таблицу, вычисляет хэш для каждой строки и мгновенно (за $O(1)$) проверяет, есть ли совпадение в хэш-таблице.
    

**Фишка Senior'а (Узкое место — `work_mem`):**

Hash Join невероятно быстрый, **НО** он требует оперативной памяти для хранения хэш-таблицы. Лимит этой памяти задается настройкой **`work_mem`** (по умолчанию часто 4 МБ).

- Если меньшая таблица не влезает в `work_mem`, происходит катастрофа: **Spill to Disk (сброс на диск)**.
    
- Postgres разбивает данные на "батчи" и начинает сохранять куски хэш-таблицы во временные файлы на жестком диске. Запрос замедляется в 10-50 раз. В логах `EXPLAIN ANALYZE` это будет видно как `Hash Join ... (Batches: 16, Memory Usage: 4096kB, Disk Usage: 52000kB)`.
    

**Когда планировщик выбирает Hash Join:**

- Для оператора равенства (`=`).
    
- Когда обе таблицы достаточно большие, и полное сканирование (Seq Scan) + хэширование обойдется дешевле (в "попугаях" cost), чем миллионы прыжков по индексам в Nested Loop.
    

### 3. Merge Join (Сортировка слиянием) — Для тяжеловесов

Этот алгоритм вступает в игру, когда таблицы настолько огромные, что Hash Join гарантированно вывалится на жесткий диск и умрет.

**Как он работает (Алгоритм двух указателей):**

Он требует, чтобы **обе таблицы были заранее отсортированы** по колонке соединения.

1. У нас есть два отсортированных списка.
    
2. База ставит два указателя на начало каждого списка.
    
3. Сравнивает значения. Если левое меньше правого — двигает левый указатель вниз. Если правое меньше — двигает правый. Если равны — выдает результат и двигает оба.
    
4. Процесс идет "змейкой" и требует ровно **одного** прохода по каждой таблице.
    

**Откуда берется сортировка?**

- _Худший вариант:_ Базе приходится делать узел `Sort` для обеих таблиц перед джойном. Это тяжелая операция, но она лучше оптимизирована для работы с диском, чем Hash Join.
    
- _Идеальный вариант:_ Данные читаются прямо из **B-Tree индексов**! Индексы уже отсортированы. База просто читает листья двух B-Tree деревьев и сливает их на лету без затрат CPU и памяти.
    

**Когда планировщик выбирает Merge Join:**

- Для огромных таблиц (миллионы строк).
    
- Только для оператора равенства (`=`).
    
- Когда данные **уже отсортированы** (например, мы джойним две таблицы по их Primary Key, под которыми лежат B-Tree).
    

### Шпаргалка для собеседования (Резюме)

Если интервьюер спросит: _"Как заставить запрос работать быстрее, если я вижу в EXPLAIN тормозящий Hash Join?"_

Твой ответ:

> "Если я вижу медленный Hash Join, который сбрасывает данные на диск (Spill to Disk), у меня есть два пути.
> 
> Первый — временно увеличить **`work_mem`** для этой транзакции (`SET LOCAL work_mem = '256MB'`), чтобы хэш-таблица влезла в RAM.
> 
> Второй — создать **B-Tree индексы** на колонках соединения для обеих таблиц. Тогда планировщик увидит, что данные можно получить уже отсортированными, и переключится на **Merge Join**, который потребляет минимум оперативной памяти, либо на **Index Nested Loop**, если одна из таблиц сильно отфильтруется условием WHERE."
