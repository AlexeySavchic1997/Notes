Принципы ООП — это фундамент, и на собеседованиях уровня Middle о них спрашивают не для того, чтобы услышать книжные определения. Интервьюер хочет понять, умеешь ли ты применять их на практике и знаешь ли ты их **недостатки**.

Обычно выделяют четыре главных принципа (хотя иногда абстракцию опускают, лучше называть все четыре). Давай разберем каждый из них вместе с любимыми «вопросами на засыпку».

## 1. Инкапсуляция (Encapsulation)

**Книжное определение:** Сокрытие внутренней реализации объекта и предоставление доступа к нему только через публичный интерфейс (методы). Объект сам управляет своим состоянием.

**Подводные камни и вопросы-ловушки:**

- **Ловушка геттеров и сеттеров:** Интервьюер может спросить: _"Если я сделал все поля `private` и написал к каждому `public` геттер и сеттер — это инкапсуляция?"_
    
    **Правильный ответ:** Нет, это фикция. Если любой другой класс может свободно прочитать и изменить любое твое поле, инкапсуляции здесь нет. Это просто структура данных (Anemic Domain Model). Настоящая инкапсуляция — это когда ты предоставляешь бизнес-методы (например, `withdrawMoney(amount)` вместо `setBalance(balance - amount)`).
    
- **Утечка мутабельного состояния:** _"У меня есть `private List<Order> orders` и метод `public List<Order> getOrders() { return orders; }`. Нарушена ли инкапсуляция?"_
    
    **Правильный ответ:** Да, фатально нарушена. Вызывающий код получит ссылку на твой приватный список и сможет сделать `orders.clear()`. Правильно возвращать неизменяемую копию: `return Collections.unmodifiableList(orders);`.
    

## 2. Наследование (Inheritance)

**Книжное определение:** Способность одного класса (наследника) расширять функционал другого класса (родителя), перенимая его поля и методы. Описывает отношение **"is-a"** (является).

**Подводные камни и вопросы-ловушки:**

- **Композиция вместо наследования (Composition over Inheritance):** Это любимая мантра интервьюеров. Наследование создает очень жесткую связь. Если ты изменишь родительский класс, это может непредсказуемо сломать всех наследников (проблема хрупкого базового класса). Поэтому часто лучше использовать композицию — отношение **"has-a"** (содержит).
    
- **Проблема ромба (Множественное наследование):** _"Почему в Java запрещено множественное наследование классов?"_
    
    **Правильный ответ:** Чтобы избежать "Diamond Problem". Если класс наследует два родительских класса, и у обоих есть метод `print()`, компилятор не будет знать, какую реализацию вызвать.
    
- **Но в Java 8 появились default-методы в интерфейсах!** _"А что будет, если реализовать два интерфейса с одинаковыми дефолтными методами?"_
    
    **Правильный ответ:** Код не скомпилируется. Компилятор заставит тебя переопределить этот метод в твоем классе и явно указать, какую реализацию ты выбираешь: `InterfaceA.super.method()`.
    

## 3. Полиморфизм (Polymorphism)

**Книжное определение:** Способность системы использовать объекты с одинаковым интерфейсом без информации о типе и внутренней структуре объекта. Простыми словами — один интерфейс, множество реализаций.

**Подводные камни и вопросы-ловушки:**

- **Полиморфизм полей (Его не существует!):** Это классическая задача на чтение кода.
    
    Java
    
    ```
    Parent p = new Child();
    System.out.println(p.x); // x есть и в Parent, и в Child
    p.print();               // print() переопределен в Child
    ```
    
    **Правильный ответ:** Методы полиморфны (вызовется метод `Child`), а **поля — нет**. Переменная `x` возьмется из класса `Parent`, потому что тип ссылки `Parent`. В Java поля не переопределяются (override), они скрываются (hide).
    
- **Статические методы:** _"Можно ли переопределить `static` метод?"_
    
    **Правильный ответ:** Нет. Статические методы привязаны к классу, а не к объекту. Метод можно "скрыть" (Method Hiding), написав такой же в наследнике, но полиморфизм (позднее связывание во время выполнения) для них не работает.
    

## 4. Абстракция (Abstraction)

**Книжное определение:** Выделение значимых характеристик объекта и отбрасывание незначимых. Мы создаем модель реального объекта, подходящую для решения конкретной задачи.

**Подводные камни и вопросы-ловушки:**

- **Абстрактный класс против Интерфейса:** _"Начиная с Java 8, в интерфейсах можно писать код (default методы) и создавать static переменные. Зачем тогда нужны абстрактные классы?"_
    
    Это фундаментальный вопрос. Вот главные отличия для ответа:
    

|**Характеристика**|**Абстрактный класс**|**Интерфейс (Java 8+)**|
|---|---|---|
|**Состояние (Поля)**|Может иметь любое состояние (не `final` поля).|Не может хранить состояние (все поля неявно `public static final`).|
|**Наследование**|Класс может наследовать только **один** абстрактный класс.|Класс может реализовать **сколько угодно** интерфейсов.|
|**Конструкторы**|Имеет конструкторы (вызываются при создании наследников).|Не имеет конструкторов.|
|**Смысловая нагрузка**|Отношение "является" (is-a).|Отношение "умеет делать" (can-do / behavior).|

> **Главный совет на интервью:** Когда рассказываешь про ООП, всегда старайся вывести разговор на **SOLID**. Если ты скажешь: _"Наследование — это круто, но я стараюсь применять принцип подстановки Барбары Лисков (Liskov Substitution Principle), чтобы не сломать систему"_, — это сразу прибавит тебе +100 очков в глазах интервьюера.
