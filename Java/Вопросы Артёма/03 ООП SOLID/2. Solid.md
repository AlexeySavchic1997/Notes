Принципы SOLID — это «Библия» объектно-ориентированного проектирования. На собеседованиях уровня Middle от тебя ждут не просто расшифровки аббревиатуры, а понимания того, какую **боль** решает каждый принцип.

Давай разберем каждый из них максимально просто, с примерами того, за что на код-ревью обычно бьют по рукам.

## 1. S: Single Responsibility Principle (Принцип единственной ответственности)

**Простыми словами:** У класса должна быть только одна задача, а значит, только одна причина для изменения. Класс не должен быть «швейцарским ножом».

**Как выглядит нарушение (Антипаттерн "Божественный объект"):**

Java

```java
public class EmployeeService {
    
    public void calculateSalary(Employee employee) {
        // бизнес-логика расчета зарплаты
    }
    
    public void saveToDatabase(Employee employee) {
        // SQL запросы к БД (нарушение! сервис работает с базой)
    }
    
    public void sendEmailNotification(Employee employee) {
        // работа с SMTP сервером (нарушение! сервис рассылает письма)
    }
}
```

**В чем проблема:** Если изменится формат email-уведомлений или мы переедем с PostgreSQL на MongoDB, нам придется менять класс `EmployeeService`, который изначально вообще-то про бизнес-логику. **Как исправить:** Разбить на три класса: `SalaryCalculator`, `EmployeeRepository` и `EmailSender`.

## 2. O: Open/Closed Principle (Принцип открытости/закрытости)

**Простыми словами:** Код должен быть открыт для расширения, но закрыт для модификации. Когда приходит новая бизнес-фича, ты должен писать **новый** код, а не переписывать (или дописывать `if-else` в) **старый** работающий код.

**Как выглядит нарушение:**

Java

```java
public class DiscountCalculator {
    public double calculate(String customerType, double amount) {
        if (customerType.equals("REGULAR")) {
            return amount * 0.9;
        } else if (customerType.equals("VIP")) {
            return amount * 0.8;
        }
        // Завтра появится "SUPER_VIP", и нам придется снова лезть в этот метод и дописывать else if!
        return amount; 
    }
}
```

**В чем проблема:** Метод будет бесконечно разрастаться. **Как исправить:** Создать интерфейс `DiscountStrategy` с методом `calculate()`. Реализовать классы `VipDiscount` и `RegularDiscount`. Если появится новый тип, мы просто напишем новый класс, не трогая старый калькулятор (это классический паттерн **Strategy**).

## 3. L: Liskov Substitution Principle (Принцип подстановки Барбары Лисков)

**Простыми словами:** Класс-наследник должен уметь делать всё то, что делает класс-родитель, и не преподносить сюрпризов. Если в метод, ожидающий родителя, передать наследника, программа не должна сломаться.

**Как выглядит нарушение:**

Java

```java
public class Bird {
    public void fly() {
        System.out.println("Лечу!");
    }
}

public class Penguin extends Bird {
    @Override
    public void fly() {
        // Пингвины не летают! Сюрприз для вызывающего кода.
        throw new UnsupportedOperationException("Я не умею летать!"); 
    }
}
```

**В чем проблема:** Если где-то в коде есть цикл `for (Bird bird : birds) { bird.fly(); }`, он внезапно упадет с исключением, как только наткнется на пингвина. Наследник нарушил контракт родителя. **Как исправить:** Выделить интерфейс `Flyable`. Пингвин будет просто `Bird` (или `SwimmingBird`), но не будет реализовать `Flyable`.

## 4. I: Interface Segregation Principle (Принцип разделения интерфейса)

**Простыми словами:** Лучше много мелких, узкоспециализированных интерфейсов, чем один огромный. Не заставляй классы реализовывать методы, которые им не нужны.

**Как выглядит нарушение:**


```java
public interface SmartDevice {
    void print();
    void scan();
    void fax();
}

public class SimplePrinter implements SmartDevice {
    @Override
    public void print() {
        System.out.println("Печатаю");
    }

    @Override
    public void scan() {
        // Заглушка. Обычный принтер не умеет сканировать.
        throw new UnsupportedOperationException();
    }

    @Override
    public void fax() {
        throw new UnsupportedOperationException();
    }
}
```

**В чем проблема:** `SimplePrinter` зависит от методов, которые ему абсолютно не нужны, и засоряет кодовую базу заглушками. **Как исправить:** Разбить `SmartDevice` на `Printer`, `Scanner` и `Fax`. Обычный принтер реализует только `Printer`, а МФУ (многофункциональное устройство) реализует все три.

## 5. D: Dependency Inversion Principle (Принцип инверсии зависимостей)

**Простыми словами:** Модули верхнего уровня (бизнес-логика) не должны зависеть от модулей нижнего уровня (базы данных, API, железо). Оба должны зависеть от абстракций (интерфейсов).

**Как выглядит нарушение:**

```java
public class OrderService {
    // ЖЕСТКАЯ зависимость от конкретной реализации (низкоуровневого модуля)
    private MySQLOrderRepository repository = new MySQLOrderRepository(); 

    public void createOrder(Order order) {
        repository.save(order);
    }
}
```

**В чем проблема:** `OrderService` намертво прибит гвоздями к MySQL. Если бизнес решит перейти на PostgreSQL, придется переписывать класс `OrderService`. Кроме того, этот класс невозможно покрыть Unit-тестами, так как мы не можем подменить `new MySQLOrderRepository()` на Mock-объект. **Как исправить:** Передавать **интерфейс** `OrderRepository` через конструктор. Именно на этом принципе построена работа всего фреймворка **Spring (Dependency Injection)**.
