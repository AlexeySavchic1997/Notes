
Паттерн **Factory (Фабрика)** — это фундамент, на котором строится слабосвязанная архитектура.

Главное правило уровня Senior: **Ключевое слово `new` — это клей.** Когда ты пишешь `new PostgreSQLConnection()`, ты намертво приклеиваешь свой бизнес-код к конкретной реализации. Фабрика решает эту проблему: она забирает на себя грязную работу по вызову `new` и отдает тебе готовый объект через абстрактный интерфейс.

Давай разберем Фабрику от простого к реальному Spring-продакшену.

### 1. Как это выглядит на чистой Java (Суть паттерна)

Представь, что мы пишем сервис генерации отчетов. У нас есть интерфейс `Report` и две реализации: `PdfReport` и `ExcelReport`.

**Плохой код (Без фабрики):**

Java

```
public void downloadReport(String type) {
    Report report;
    if ("PDF".equals(type)) {
        report = new PdfReport(); // Жесткая привязка!
    } else if ("EXCEL".equals(type)) {
        report = new ExcelReport(); // Жесткая привязка!
    }
    report.generate();
}
```

Если завтра добавятся форматы CSV или HTML, тебе придется изменять этот класс бизнес-логики, нарушая принцип OCP (Open-Closed Principle).

**Хороший код (С фабрикой):** Мы выносим создание в отдельный класс `ReportFactory`.

Java

```
public class ReportFactory {
    public Report createReport(String type) {
        return switch (type) {
            case "PDF" -> new PdfReport();
            case "EXCEL" -> new ExcelReport();
            default -> throw new IllegalArgumentException("Неизвестный тип отчета");
        };
    }
}
```

Теперь наша бизнес-логика выглядит так:

Java

```
public void downloadReport(String type) {
    // Бизнес-логика вообще не знает о PDF или Excel. Она знает только интерфейс Report.
    Report report = reportFactory.createReport(type);
    report.generate();
}
```

### 2. Зачем это нужно? (Ответ для собеседования)

1. **Слабая связанность (Loose Coupling):** Клиентский код работает только с абстракциями (интерфейсами).
    
2. **Инкапсуляция логики создания:** Иногда чтобы создать объект, нужно передать ему 10 параметров, заинжектить подключение к БД и прочитать конфиг. Клиентский код не должен всё это уметь. Фабрика прячет эту сложность.
    
3. **Соблюдение Single Responsibility (Единственная ответственность):** Класс отчета отвечает за генерацию байтов. Фабрика отвечает за сборку класса отчета.
    

### 3. Фабрика в мире Spring (Как пишут на проде)

В Spring есть нюанс: **Spring сам по себе является гигантской Фабрикой**. Его главный интерфейс так и называется — `BeanFactory`. Spring сам вызывает `new` и складывает бины в контейнер.

Но что делать, если выбор того, _какой именно_ бин использовать, происходит динамически (например, в зависимости от JSON, который прислал пользователь)?

Здесь мы используем **мощнейшее комбо: Factory + Spring IoC**.

Представь, что у нас есть интерфейс `NotificationSender` и реализации `EmailSender` и `SmsSender`. Нам нужна Фабрика, которая отдаст нужный бин по ключу.

Java

```
// 1. Интерфейс (Абстракция)
public interface NotificationSender {
    String getType(); // Возвращает "EMAIL" или "SMS"
    void send(String message);
}

// 2. Фабрика, управляемая Spring
@Component
public class NotificationFactory {
    
    // Spring МАГИЧЕСКИ соберет все классы, реализующие NotificationSender, в этот список!
    private final List<NotificationSender> senders;
    
    // Делаем кэш для мгновенного поиска (O(1)) вместо перебора if-else
    private final Map<String, NotificationSender> senderCache = new HashMap<>();

    public NotificationFactory(List<NotificationSender> senders) {
        this.senders = senders;
        // Заполняем кэш при старте приложения
        for (NotificationSender sender : senders) {
            senderCache.put(sender.getType(), sender);
        }
    }

    // Тот самый фабричный метод
    public NotificationSender getSender(String type) {
        NotificationSender sender = senderCache.get(type);
        if (sender == null) {
            throw new IllegalArgumentException("Тип уведомления не поддерживается: " + type);
        }
        return sender;
    }
}
```

**В чем гениальность этого подхода?** Если завтра бизнес попросит добавить отправку уведомлений в Telegram, ты просто создаешь класс `TelegramSender implements NotificationSender`, вешаешь на него `@Component`, и... **всё!** Тебе не нужно трогать ни Фабрику, ни бизнес-логику. Spring сам найдет новый класс, положит его в список `senders`, Фабрика положит его в мапу, и всё заработает само. Это чистейшее соблюдение принципов SOLID.

> _Примечание для собеседования:_ Строго говоря, то, что мы сейчас написали, является мостом между паттернами **Factory** (механизм получения нужного объекта) и **Strategy** (набор взаимозаменяемых алгоритмов). В Spring они почти всегда ходят парой.
