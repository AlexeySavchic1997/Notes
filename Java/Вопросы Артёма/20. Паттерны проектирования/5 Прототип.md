Паттерн **Prototype (Прототип)** завершает наш список. Суть паттерна проста: вместо того, чтобы создавать объект с нуля (вызывая конструктор, лезя в базу данных за справочниками, тратя CPU на вычисления), мы берем уже существующий, полностью "настроенный" объект и просто **копируем его**.

На собеседованиях по этому паттерну почти всегда задают один и тот же вопрос, связанный с архитектурной ошибкой самих создателей языка Java.

### 1. Почему встроенный `Cloneable` — это провал?

В Java есть интерфейс `java.lang.Cloneable` и метод `clone()` в классе `Object`. Джуниоры часто думают, что это и есть идеальная реализация Прототипа.

**Senior должен знать 4 причины, почему Джошуа Блох (создатель коллекций Java) призывает никогда не использовать `Cloneable`:**

1. **Ловушка Поверхностного копирования (Shallow Copy):** По умолчанию метод `Object.clone()` копирует только примитивы. Если у твоего объекта `User` есть поле `List<Role> roles`, то при клонировании оба объекта (оригинал и копия) будут ссылаться на **один и тот же список в памяти**. Если ты удалишь роль у копии, она исчезнет и у оригинала. Это источник страшных багов.
    
2. **Интерфейс-пустышка:** Интерфейс `Cloneable` не содержит метода `clone()`. Метод `clone()` определен в классе `Object` как `protected`. Это ломает логику полиморфизма.
    
3. **Обход конструктора:** Метод `clone()` создает объект магическим образом на уровне JVM, **не вызывая конструктор класса**. Если у тебя в конструкторе была важная логика валидации или счетчик созданных объектов, всё это не сработает. Также это ломает работу с `final` полями (ты не сможешь переназначить их при глубоком клонировании).
    
4. **Ужасный Checked Exception:** Метод `clone()` заставляет тебя везде писать блок `try-catch` для обработки `CloneNotSupportedException`, даже если ты точно знаешь, что класс поддерживает клонирование.
    

### 2. Как правильно реализовать Прототип на Проде?

Вместо сломанного `Cloneable` в современной Java используют три надежных подхода.

#### Подход А: Конструктор копирования (Copy Constructor)

Это самый правильный, быстрый и рекомендуемый (тем же Блохом) способ с точки зрения чистого ООП.

Java

```
public class User {
    private String name;
    private Address address;

    // Обычный конструктор
    public User(String name, Address address) {
        this.name = name;
        this.address = address;
    }

    // КОНСТРУКТОР КОПИРОВАНИЯ (Паттерн Прототип)
    public User(User prototype) {
        this.name = prototype.name; // Строки иммутабельны, их можно просто присвоить
        
        // ГЛУБОКОЕ КОПИРОВАНИЕ: мы создаем новый объект Address, 
        // чтобы не делить ссылку с оригиналом!
        this.address = new Address(prototype.address); 
    }
}

// Использование:
User original = new User("Ivan", new Address("Moscow"));
User copy = new User(original); // Идеально чисто и безопасно
```

#### Подход Б: Сериализация (Ленивое глубокое копирование)

Если у тебя огромный, сложный объект со вложенностью в 10 уровней, писать конструкторы копирования для каждого класса — это ад. В таких случаях используют трюк с JSON. Мы превращаем объект в строку, а потом сразу же читаем строку обратно в новый объект.

Java

```
@Service
@RequiredArgsConstructor
public class PrototypeService {
    
    private final ObjectMapper objectMapper; // Из библиотеки Jackson

    public User deepCopy(User prototype) {
        try {
            // Превращаем в JSON (теряем связи со старой памятью)
            String json = objectMapper.writeValueAsString(prototype);
            // Читаем в новый объект (100% глубокая копия)
            return objectMapper.readValue(json, User.class);
        } catch (JsonProcessingException e) {
            throw new RuntimeException("Ошибка клонирования", e);
        }
    }
}
```

_Минус:_ Это работает медленнее (из-за Reflection и парсинга текста). Используется, когда объектов не очень много (не миллионы в секунду).

#### Подход В: MapStruct

На современных проектах для клонирования и маппинга используют кодогенераторы (например, MapStruct). Он на этапе компиляции сам напишет за тебя все геттеры и сеттеры для глубокого копирования, и это будет работать со скоростью чистого Java-кода.

### 3. Прототип в контексте Spring (Scope)

Не забывай, что в Spring есть прямое воплощение этого паттерна — **Scope `prototype`**.

Если ты повесишь над бином аннотацию `@Scope("prototype")`, то IoC-контейнер Spring перестанет вести себя как Singleton-реестр. Каждый раз, когда ты будешь просить этот бин (через `@Autowired` или `context.getBean()`), Spring будет **создавать для тебя абсолютно новый экземпляр этого класса**.
