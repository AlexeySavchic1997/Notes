Эти три паттерна — скрытые герои энтерпрайз-разработки. Если Singleton и Builder мы пишем руками, то Proxy, Observer и Adapter — это то, на чем построен сам фундамент Spring Framework и микросервисных интеграций.

Давай разберем их так, как ожидают услышать на собеседовании уровня Senior.

### 1. Proxy (Заместитель) — Сердце магии Spring

_Это структурный паттерн, который предоставляет объект-заглушку (обертку) для контроля доступа к другому объекту._

**Боль:** У тебя есть чистый бизнес-метод `transferMoney()`. Бизнес требует добавить: логирование, проверку прав (Security), открытие и закрытие транзакции в БД. Если написать всё это прямо в методе, бизнес-логика утонет в инфраструктурном коде (нарушение Single Responsibility).

**Решение (Паттерн Proxy):** Мы создаем класс-обертку, который имеет _тот же самый интерфейс_, что и наш сервис.

**Как это работает на проде (Spring AOP):** Ты не пишешь прокси руками. Когда ты вешаешь аннотацию `@Transactional` или `@Cacheable`, Spring при старте приложения динамически генерирует Proxy-класс.

Java

```
// Твой оригинальный класс
public class OrderService {
    public void createOrder() {
        // Чистая бизнес-логика (3 строчки)
    }
}

// То, что Spring генерирует под капотом в рантайме (Псевдокод)
public class OrderServiceProxy extends OrderService {
    private final OrderService target; // Ссылка на твой реальный класс

    @Override
    public void createOrder() {
        try {
            transactionManager.begin(); // 1. Логика ДО
            
            target.createOrder();       // 2. Вызов твоей логики
            
            transactionManager.commit(); // 3. Логика ПОСЛЕ
        } catch (Exception e) {
            transactionManager.rollback();
        }
    }
}
```

**Ловушка на собеседовании:** _"В чем разница между JDK Dynamic Proxy и CGLIB?"_ _Ответ Senior'а:_ JDK Proxy может обернуть только классы, реализующие интерфейс. CGLIB (дефолт в Spring Boot) генерирует прокси путем наследования от твоего класса (поэтому методы с `@Transactional` нельзя делать `private` или `final` — прокси не сможет их переопределить).

### 2. Observer (Наблюдатель) — Развязываем монолит

_Это поведенческий паттерн (Издатель-Подписчик), позволяющий одному объекту оповещать другие об изменениях своего состояния._

**Боль:** Происходит регистрация пользователя. В методе `registerUser()` тебе нужно: сохранить юзера в БД, отправить приветственный Email, начислить бонусные баллы, отправить метрику в аналитику. Если `UserService` будет напрямую вызывать `EmailService`, `BonusService` и `AnalyticsService`, он превратится в неподдерживаемого монстра, жестко связанного с половиной системы.

**Решение (Observer в Spring):** Используем встроенный механизм событий — `ApplicationEventPublisher`.

**Шаг 1: Публикуем событие (Издатель)**

Java

```
@Service
@RequiredArgsConstructor
public class UserService {
    private final ApplicationEventPublisher eventPublisher;

    public void registerUser(User user) {
        userRepository.save(user);
        // Бизнес-логика ничего не знает про Email или Бонусы. Она просто "кричит" в космос.
        eventPublisher.publishEvent(new UserRegisteredEvent(user.getId()));
    }
}
```

**Шаг 2: Слушаем событие (Подписчики/Наблюдатели)** Другие сервисы просто подписываются на это событие.

Java

```
@Component
public class EmailService {
    
    @EventListener // Spring сам вызовет этот метод, когда произойдет событие
    public void onUserRegistered(UserRegisteredEvent event) {
        // Отправляем письмо
    }
}
```

**Фишка Senior'а:** В Spring есть аннотация **`@TransactionalEventListener`**. Она гарантирует, что Email отправится _только после того_, как транзакция сохранения юзера в БД успешно закоммитится. Если произойдет Rollback в БД, письмо не уйдет.

### 3. Adapter (Адаптер / Wrapper) — Защита чистоты архитектуры

_Это структурный паттерн, который оборачивает несовместимый объект, чтобы он мог работать с вашим кодом._

**Боль:** Твой проект интегрируется со старой банковской SOAP-системой (Legacy). Банк возвращает данные в ужасном формате XML с непонятными полями вида `<TX_AMT_99>`, а твоя бизнес-логика работает с красивыми и понятными Java-объектами (`PaymentInfo` с полем `BigDecimal amount`). Если пустить этот XML-объект напрямую в твою бизнес-логику, грязный код заразит весь проект.

**Решение:** Мы пишем Адаптер (в Domain-Driven Design это часто называют **Anti-Corruption Layer** — Антикоррупционный слой).

Java

```
// 1. Интерфейс, с которым хочет работать ТВОЯ система (Чистый код)
public interface PaymentProvider {
    PaymentInfo getPayment(String id);
}

// 2. Ужасный класс от банка, который нельзя изменять (Legacy)
public class OldSoapBankClient {
    public XmlBankTx getTx(String txId) { ... } 
}

// 3. Наш Адаптер
@Component
@RequiredArgsConstructor
public class BankAdapter implements PaymentProvider {
    private final OldSoapBankClient legacyClient;

    @Override
    public PaymentInfo getPayment(String id) {
        // Адаптер берет на себя грязную работу
        XmlBankTx dirtyData = legacyClient.getTx(id);
        
        // Транслирует (адаптирует) грязный формат в наш чистый Domain-объект
        return new PaymentInfo(
            new BigDecimal(dirtyData.getTxAmt99()),
            dirtyData.getCurrencyCode()
        );
    }
}
```

**Реальный пример из Java:** Библиотека **SLF4J** (Simple Logging Facade for Java) — это гигантский Адаптер. Твой код пишет `log.info()`, а SLF4J адаптирует этот вызов под Logback, Log4j или `java.util.logging`, позволяя менять систему логирования без изменения кода приложения.
