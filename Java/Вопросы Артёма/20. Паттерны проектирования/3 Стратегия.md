Грань между Фабрикой и Стратегией действительно тонкая, и на собеседованиях часто просят объяснить разницу.

Если отвечать коротко:

- **Фабрика (Порождающий паттерн):** Отвечает на вопрос _"КТО будет выполнять работу?"_ (Она создает и выдает нужный инструмент).
    
- **Стратегия (Поведенческий паттерн):** Отвечает на вопрос _"КАК мы будем выполнять работу?"_ (Это сам алгоритм).
    

Фабрика прячет логику _создания_, а Стратегия прячет логику _исполнения_. В Spring они сливаются воедино благодаря IoC-контейнеру (Spring сам выступает Фабрикой, а мы только пользуемся Стратегиями).

Давай посмотрим, как Стратегия убивает бесконечные `if-else` на примере системы оплаты.

### 1. Боль: Процессинг без Стратегии (Код Джуниора)

Представь класс `CheckoutService`, который обрабатывает покупки. Пользователь на фронтенде выбирает способ оплаты (Карта, PayPal, Крипта).

Java

```
@Service
public class CheckoutService {
    
    public void processPayment(String paymentMethod, double amount) {
        if ("CARD".equals(paymentMethod)) {
            // 50 строк логики валидации CVV, похода в API банка...
            System.out.println("Оплата картой: " + amount);
        } else if ("PAYPAL".equals(paymentMethod)) {
            // 40 строк логики OAuth авторизации, редиректов...
            System.out.println("Оплата PayPal: " + amount);
        } else if ("CRYPTO".equals(paymentMethod)) {
            // 60 строк логики проверки блокчейна, смарт-контрактов...
            System.out.println("Оплата Криптой: " + amount);
        } else {
            throw new IllegalArgumentException("Неизвестный метод");
        }
    }
}
```

**Почему за это увольняют (или не берут на работу):**

1. **Нарушение OCP (Open-Closed Principle):** При добавлении ApplePay тебе придется модифицировать этот класс. Он будет расти бесконечно и в итоге превратится в "Божественный объект" (God Object) на 5000 строк.
    
2. **Слияние контекстов:** Класс оформления заказа (`CheckoutService`) внезапно знает, как работают смарт-контракты крипты. Это нарушение Single Responsibility.
    
3. **Невозможность тестирования:** Чтобы написать Unit-тест на логику заказа, тебе придется мокать API всех банков мира сразу.
    

### 2. Решение: Паттерн Strategy в Spring (Код Senior'а)

Мы выносим _алгоритм оплаты_ в отдельный интерфейс.

**Шаг 1: Создаем абстракцию (Стратегию)**

Java

```
public interface PaymentStrategy {
    void pay(double amount);
}
```

**Шаг 2: Создаем конкретные реализации (Алгоритмы)** Здесь мы используем **фичу Spring**: мы можем задать бину конкретное имя в аннотации `@Component`.

Java

```
@Component("CARD")
public class CardStrategy implements PaymentStrategy {
    @Override
    public void pay(double amount) {
        // Только логика работы с картами
    }
}

@Component("PAYPAL")
public class PayPalStrategy implements PaymentStrategy {
    @Override
    public void pay(double amount) {
        // Только логика PayPal
    }
}
```

**Шаг 3: Внедряем Стратегии в бизнес-логику (Убиваем if-else)** Мы просим Spring заинжектить нам `Map<String, PaymentStrategy>`. Spring обладает встроенной магией: он соберет все бины, реализующие этот интерфейс, положит их в мапу, где **ключом будет имя бина, а значением — сам объект**.

Java

```
@Service
@RequiredArgsConstructor
public class CheckoutService {
    
    // Spring сам заполнит эту мапу: 
    // {"CARD" -> CardStrategy, "PAYPAL" -> PayPalStrategy}
    private final Map<String, PaymentStrategy> strategies;
    
    public void processPayment(String paymentMethod, double amount) {
        // 1. Получаем нужный алгоритм за O(1)
        PaymentStrategy strategy = strategies.get(paymentMethod);
        
        if (strategy == null) {
            throw new IllegalArgumentException("Метод не поддерживается: " + paymentMethod);
        }
        
        // 2. Выполняем алгоритм! Бизнес-логика вообще не знает, ЧТО сейчас произойдет.
        strategy.pay(amount);
    }
}
```

### Архитектурный итог (Что сказать на собесе)

Применяя Стратегию через `Map` в Spring, мы достигаем абсолютной "отвязанности": Если завтра бизнес потребует добавить оплату через `ApplePay`, ты **вообще не будешь трогать старый код**. Ты просто создашь новый класс:

Java

```
@Component("APPLE_PAY")
public class ApplePayStrategy implements PaymentStrategy { ... }
```

Spring при старте сам найдет этот класс, добавит его в `Map` под ключом `APPLE_PAY`, и `CheckoutService` начнет обрабатывать такие платежи автоматически, без единого нового `if`. Это идеальное соблюдение SOLID.
