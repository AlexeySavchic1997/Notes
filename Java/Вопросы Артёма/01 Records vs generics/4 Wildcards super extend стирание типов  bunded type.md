
Когда ты создаешь класс или метод с дженериком, по умолчанию вместо `<T>` можно подставить любой объект (даже `String` или `Object`). Но часто нам нужно **ограничить** этот тип.

Для этого используется ключевое слово `extends` (даже если мы ограничиваем интерфейсом, а не классом).

```Java
// T может быть только классом Number или его наследниками (Integer, Double и т.д.)
public class MathBox<T extends Number> {
    private T value;

    public MathBox(T value) {
        this.value = value;
    }

    public double doubleValue() {
        // Благодаря extends Number, компилятор знает, что у T точно есть этот метод
        return value.doubleValue(); 
    }
}
```
> **Нюанс для собеседования:** В Java можно сделать множественное ограничение (Multiple Bounds). Записывается это через амперсанд `&`. Класс всегда должен идти первым, а интерфейсы потом: `<T & Comparable<T Number extends>>`.

Представь, что ты пишешь универсальный метод. Тебе нужно, чтобы объект, который передадут в этот метод, умел делать сразу **две (или больше) разные вещи**.

Например: ты пишешь метод для сохранения данных по сети, и тебе нужно, чтобы передаваемый объект был одновременно и числом (`Number`), и чтобы его можно было сравнивать (`Comparable`), чтобы отсортировать перед отправкой.

В Java нет множественного наследования классов, но класс может реализовывать сколько угодно интерфейсов. С помощью символа `&` мы можем сказать компилятору: _"Эй, мне нужен тип T, который наследует класс X **И** реализует интерфейс Y"_.

## Синтаксис и жесткие правила

Синтаксис выглядит так: `<T & extends Тип1 Тип2 Тип3>`.

Здесь есть два строгих правила, которые любит проверять компилятор (и интервьюеры):

1. **Класс может быть только один.** Так как в Java нельзя наследоваться от двух классов одновременно, в этом списке может быть максимум один класс (остальное — интерфейсы).
    
2. **Класс всегда идет первым.** Если в твоем списке ограничений есть класс, он обязан стоять на первом месте перед знаком `&`.
    

**Пример в коде:**

// Правильно: Number (класс) идет первым, Comparable (интерфейс) вторым
public <T extends Number & Comparable<T>> void processNumbers(List<T> list) {
    for (T item : list) {
        // Мы можем вызывать методы Number
        double val = item.doubleValue(); 
        
        // И мы можем вызывать методы Comparable
        int result = item.compareTo(list.get(0)); 
    }
}


**Wildcard (`?`)** означает «какой-то неизвестный тип». Он используется, когда мы передаем коллекции в методы.

Главная проблема, которую решают wildcards: **дженерики в Java инвариантны**. Это значит, что `List<Integer>` **не является** наследником `List<Number>`. Если метод ждет `List<Number>`, ты не сможешь передать туда список интов. Чтобы это обойти, придумали `? extends` и `? super`.

Запомни аббревиатуру PECS: Producer Extends, Consumer Super.


Разбор ? extends T (Producer)
Мы используем это, когда коллекция является поставщиком (Producer) данных для нашего метода. Мы только читаем из нее.

Java
public void printNumbers(List  *<*<? extends Number> list) {
    // ЧИТАТЬ можно безопасно. Мы уверены, что там Number или его наследник.
    Number n = list.get(0); 
    
    // ПИСАТЬ нельзя! Ошибка компиляции. 
    // Вдруг list - это List<Double>, а мы пытаемся положить туда Integer?
    // list.add(10); 
}
### Разбор `? super T` (Consumer)

Мы используем это, когда коллекция является **потребителем (Consumer)**. Мы собираемся писать в нее данные.

Java

```
public void addNumbers(List  *<*? super Integer> list) {
    // ПИСАТЬ можно безопасно. 
    // Раз это список Integer, Number или Object, он точно примет Integer.
    list.add(10); 
    list.add(20);

    // ЧИТАТЬ нормально нельзя! 
    // Мы не знаем, кто предок. Метод get() вернет просто Object.
    // Integer i = list.get(0); // Ошибка
}

## 3. Type Erasure (Стирание типов)

Интервьюер обязательно спросит: _"А что знает JVM о дженериках во время выполнения (Runtime)?"_ Правильный ответ: **Почти ничего.**

Дженерики были добавлены в Java 5. Чтобы старый код (Java 1.4), написанный до появления дженериков, продолжал работать, разработчики языка пошли на компромисс — **стирание типов**.

Вся магия `<T>` существует **только на этапе компиляции** (для проверок типов). Когда код компилируется в байт-код, все дженерики удаляются (стираются).

**Как это работает:**

1. Если дженерик не ограничен (`<T>`), он превращается в `Object`.
    
2. Если дженерик ограничен (`<T Number extends>`), он превращается в верхнюю границу (в данном случае `Number`).
    
3. Там, где нужно, компилятор сам вставляет явное приведение типов (касты).
    

**Пример до компиляции:**


```
List<String> list = new ArrayList<>();
list.add("Hello");
String s = list.get(0);
```

**Во что это превратится в байт-коде (упрощенно):**

```
List list = new ArrayList();
list.add("Hello");
String s = (String) list.get(0); // Компилятор сам подставил каст
```

**Следствия стирания типов (ограничения):**

- Нельзя создать экземпляр дженерика: `new T()`.
    
- Нельзя создать массив дженериков: `new T[10]`.
    
- Нельзя узнать тип во время выполнения: `if (list instanceof List<String>)` вызовет ошибку компиляции (можно проверить только `list instanceof List`).
    
- Нельзя сделать перегрузку методов, если после стирания их сигнатуры станут одинаковыми.
```
