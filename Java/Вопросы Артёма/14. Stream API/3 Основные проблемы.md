Хотя Stream API — это прекрасный инструмент, на реальном продакшене он приносит ряд специфических проблем. Senior-разработчик знает, что стримы — это не серебряная пуля, и иногда старый добрый цикл `for` справляется лучше.

Вот топ-5 главных проблем Stream API, с которыми ты столкнешься на практике.

### 1. Проблема Checked Exceptions (Исключения в лямбдах)

Это самая раздражающая архитектурная проблема Stream API в Java. Функциональные интерфейсы (например, `Function` в методе `map`) не объявляют `throws Exception`.

Если внутри стрима ты вызываешь метод, который бросает проверяемое исключение (Checked Exception, например `IOException`), компилятор заставит тебя писать `try-catch` прямо внутри лямбды.

**Уродливый код на проде:**

Java

```
List<String> parsedData = files.stream()
    .map(file -> {
        try {
            return readFromFile(file); // Бросает IOException
        } catch (IOException e) {
            throw new RuntimeException(e); // Приходится заворачивать в Unchecked
        }
    })
    .toList();
```

_Как решают:_ Выносят `try-catch` в отдельные private-методы, пишут кастомные обертки-утилиты (классы типа `Try`) или используют аннотацию `@SneakyThrows` из Lombok, чтобы обмануть компилятор.

### 2. Ад отладки (Debugging) и гигантские Stack Trace

В классическом цикле `for` ты просто ставишь брейкпоинт (Breakpoint) внутри цикла и нажимаешь "Step Over". Ты видишь состояние всех переменных на каждой итерации.

Отлаживать стримы гораздо сложнее, так как это конвейер (Pipeline) из анонимных классов и ленивых вычислений. Если внутри `.map()` вылетит `NullPointerException`, твой Stack Trace в логах будет состоять из 40-50 строк внутренних кишок JDK (вызовы `ReferencePipeline`, `AbstractPipeline`, `Sink`, `Spliterator`), и только где-то на самом дне будет указана твоя строчка кода.

_Как решают:_ В IntelliJ IDEA есть специальный инструмент **Java Stream Debugger** (кнопка с иконкой конвейера при отладке), который визуализирует, как элементы проходят через каждую стадию фильтрации и маппинга.

### 3. Незакрытые ресурсы (Утечки памяти в I/O)

Большинство коллекций (List, Set) живут в оперативной памяти, и стримы по ним не нужно закрывать. Но Stream API часто используют для чтения файлов или работы с базами данных (например, `Files.lines(Path)` или `Stream<User>` из Spring Data JPA).

Такие стримы под капотом держат открытые файловые дескрипторы или соединения с БД (Курсоры). Если не вызвать терминальную операцию или не закрыть стрим, произойдет **утечка ресурсов (Resource Leak)**.

**Правильный подход (Try-with-resources):**

Java

```
// Стрим обязательно нужно оборачивать в try-with-resources!
try (Stream<String> lines = Files.lines(Paths.get("data.txt"))) {
    lines.filter(line -> line.contains("ERROR"))
         .forEach(System.out::println);
}
```

### 4. Оверхед производительности (Performance Overhead)

Стримы работают медленнее обычных циклов. Для большинства бизнес-приложений эта разница микроскопическая, но в HighLoad (миллионы вызовов в секунду) это становится проблемой.

- **На маленьких коллекциях (до 100 элементов):** Цикл `for` работает быстрее, потому что он не тратит время на создание объектов конвейера (`Pipeline`, `Sink`, лямбда-выражения).
    
- **Проблема Boxing/Unboxing:** Если ты делаешь стрим по `List<Integer>`, при математических вычислениях Java будет постоянно распаковывать объекты в примитивы `int` и обратно (создавая тысячи новых объектов `Integer` в куче, перегружая Garbage Collector). _Как решают:_ Для чисел всегда нужно переходить на специализированные примитивные стримы: `mapToInt()`, `mapToLong()`. Они работают с массивами примитивов без создания лишних объектов.
    

### 5. Синдром "Всё в одну строку" (Убийство читаемости)

Разработчики, только открывшие для себя Stream API, часто пытаются впихнуть сложнейшую бизнес-логику с условиями и вложенными коллекциями в один "неразрывный" стрим на 30 строк.

Такой код невозможно читать, тестировать по частям и поддерживать. Senior-разработчик знает: если твой стрим требует сложной логики внутри `.map()` или вложенных `.filter()`, лучше **разорвать его**, вынести логику в отдельные приватные методы со смысловыми названиями или вовсе вернуться к циклу `for`.
