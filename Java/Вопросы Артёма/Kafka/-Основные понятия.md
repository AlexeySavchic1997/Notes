Apache Kafka — это один из самых популярных инструментов в современной архитектуре. И первое, что нужно уяснить для собеседования: **Kafka — это не классическая очередь сообщений (Message Queue), это распределенный журнал событий (Distributed Commit Log).**

Классическая очередь (как RabbitMQ) работает по принципу: прочитал сообщение — оно удалилось. Kafka работает как файл логов: сообщения пишутся на жесткий диск друг за другом и **не удаляются после прочтения** (они хранятся заданное время, например, 7 дней).

Давай разберем базовый словарь и топ-3 стартовых вопроса на собеседованиях.

## 1. Базовые понятия (Словарь Kafka)

- **Message (Сообщение / Событие):** Базовая единица данных (обычно массив байтов, часто JSON или Avro). Состоит из ключа, значения, таймстемпа и заголовков.
    
- **Topic (Топик):** Логическое имя для потока сообщений. Аналог «Таблицы» в базе данных или «Папки» на диске. Продюсеры пишут в топик, консюмеры читают из него.
    
- **Partition (Партиция):** Это самое важное понятие для понимания масштабируемости! Топик физически разбивается на несколько партиций. Каждая партиция — это упорядоченный, неизменяемый файл на диске (лог).
    
- **Offset (Смещение):** Порядковый номер сообщения внутри конкретной партиции. Он строго возрастает (0, 1, 2, 3...). По оффсету консюмер понимает, какие сообщения он уже прочитал, а какие еще нет.
    
- **Producer (Продюсер):** Приложение, которое пишет данные в Kafka.
    
- **Consumer (Консюмер):** Приложение, которое читает данные из Kafka.
    
- **Consumer Group (Группа консюмеров):** Набор консюмеров, которые объединяются для совместного (параллельного) чтения данных из одного топика.
    
-**Брокер** — это один физический сервер (или виртуалка / pod в Kubernetes), на котором запущен Java-процесс Apache Kafka.

- **Кластер:** Kafka почти никогда не работает в одиночку. Несколько брокеров объединяются в **Кластер**.
    
- **Функция:** Брокер — это, по сути, глупая, но невероятно быстрая труба с жестким диском. Его главная задача:
    
    1. Принять байты от Продюсера.
        
    2. Сохранить их на свой локальный жесткий диск (записать в конец файла).
        
    3. Отдать эти байты Консюмеру по запросу.
        
- **Без бизнес-логики:** Брокер не знает, что такое JSON, заказы или пользователи. Для него сообщения — это просто массив байтов. Он не фильтрует их, не маршрутизирует (Продюсер сам решает, в какую партицию писать) и не отслеживает, какое конкретно сообщение прочитал Консюмер.
    

Вся архитектура брокера заточена под одну цель: **максимально быстрая работа с файловой системой операционной системы**.

  ### 1. Отказоустойчивость и Репликация (Replication)

- **Leader Replica (Лидер-реплика):** Главный брокер для конкретной партиции. Все Продюсеры пишут только в него, и все Консюмеры читают только из него (по умолчанию).
    
- **Follower Replica (Ведомая реплика):** Брокер, который пассивно скачивает данные у Лидера, чтобы стать Лидером в случае его падения.
    
- **ISR (In-Sync Replicas / Синхронизированные реплики):** Список брокеров (включая лидера), которые успевают за лидером и не отстают от него больше, чем на допустимое время (параметр `replica.lag.time.max.ms`). Если лидер упадет, новым лидером может стать **только** брокер из списка ISR.
    
- **High Watermark (HW / Верхняя отметка):** Оффсет (номер) последнего сообщения, которое было успешно скопировано **всеми** репликами из списка ISR.
    
    - _Зачем нужно:_ Консюмеры могут читать сообщения только до этой отметки. Это гарантия того, что консюмер не прочитает сообщение, которое может исчезнуть при падении текущего лидера.
        

### 2. Продюсеры и Подтверждения (Acks)

- **ACKS (Acknowledgements / Подтверждения):** Настройка продюсера, определяющая, когда сообщение считается успешно сохраненным.
    
    - `acks=0`: "Выстрелил и забыл" (Продюсер не ждет ответа от брокера, максимальная скорость, риск потери данных).
        
    - `acks=1`: Лидер записал сообщение на свой диск и ответил "Ок". Если Лидер упадет до того, как реплики скачают данные — сообщение потеряется.
        
    - `acks=all` (или `-1`): Лидер дождался, пока **все** реплики из списка ISR запишут данные на диск. Это гарантия того, что данные не потеряются. Стандарт для банковских и финансовых транзакций.
        

### 3. Консюмеры и Группы (Consumers & Rebalancing)

- **Consumer Lag (Лаг / Отставание):** Самая важная метрика на проде. Это разница между последним сообщением, которое пришло в партицию, и сообщением, которое сейчас читает консюмер. Если Lag постоянно растет — ваш код работает медленнее, чем поступают данные.
    
- **Offset Commit (Коммит смещения):** Процесс, при котором консюмер сообщает брокеру: _"Я успешно обработал всё до оффсета № 1500"_. Эти данные сохраняются в специальный служебный топик `__consumer_offsets`.
    
- **Rebalance (Ребалансировка):** Процесс перераспределения партиций между участниками одной `Consumer Group`. Запускается автоматически, если кто-то из консюмеров завис/упал, добавился новый, или в топике увеличилось количество партиций.
    
- **Group Coordinator (Координатор группы):** Один из брокеров Kafka (назначается под капотом), который принимает пульс (`Heartbeat`) от консюмеров. Если он не получает пульс в течение таймаута, он инициирует Ребаланс.
    

### 4. Хранение данных (Storage Policies)

- **Retention Policy (Политика удержания):** Правило, по которому Kafka удаляет старые данные. Обычно настраивается по времени (`retention.ms`, например, хранить 7 дней) или по размеру (`retention.bytes`, например, хранить 100 ГБ на партицию).
    
- **Log Compaction (Компактизация лога):** Альтернативный режим хранения (вместо удаления по времени). Kafka оставляет только **последнее актуальное значение** для каждого уникального ключа, удаляя старые исторические значения этого же ключа. Используется для хранения "Снимков состояний" (например, актуальные балансы пользователей).
    
- **Tombstone (Надгробие):** Сообщение-маркер. Имеет валидный Ключ, но в качестве Значения передается `null`. Используется в топиках с Log Compaction как команда: _"Физически удали этот ключ с диска навсегда"_.
    

### 5. Инфраструктура (Control Plane)

- **ZooKeeper (ZK):** Внешняя система (отдельное приложение), которая исторически использовалась для хранения метаданных кластера Kafka (какой брокер жив, кто лидер какой партиции).
    
- **KRaft (Kafka Raft):** Новый протокол консенсуса, встроенный прямо в саму Kafka (начиная с версий 2.8+ и полностью с 3.3+). Позволил избавиться от ZooKeeper. Теперь Kafka хранит метаданные сама в специальном служебном топике. Это сделало её быстрее, стабильнее и проще в настройке.
