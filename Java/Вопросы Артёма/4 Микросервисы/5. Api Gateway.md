
**Service Discovery** — это внутренний телефонный справочник для сотрудников. Бухгалтерия звонит в отдел кадров по внутреннему номеру, и они общаются друг с другом напрямую. Это так называемый **East-West трафик** (внутренний трафик внутри кластера).

**API Gateway** — это ресепшен с охранником на главном входе в здание. Это **North-South трафик** (трафик из внешнего мира внутрь кластера).

## Зачем нам ресепшен (API Gateway)?

Представь, что у тебя есть мобильное приложение (или frontend), а на бэкенде крутится 50 разных микросервисов: сервис юзеров, сервис заказов, сервис оплаты и так далее.

Если API Gateway нет, мобильное приложение должно знать адреса всех 50 сервисов и стучаться к каждому напрямую. Это рождает огромные проблемы:

### 1. Единая точка входа (Routing)

Без шлюза клиентскому приложению пришлось бы самому решать, по какому URL обращаться за профилем, а по какому — за корзиной.

С API Gateway мобилка отправляет все запросы на один-единственный домен (например, `api.myproject.com`). А шлюз уже смотрит на путь: если `/users/*`, он незаметно для клиента перенаправляет запрос в сервис юзеров (кстати, при этом шлюз сам идет в Service Discovery, чтобы узнать, на какой именно IP отправить запрос).

### 2. Безопасность и Авторизация (Auth)

Если клиент стучится к сервисам напрямую, тебе придется писать логику проверки JWT-токенов **в каждом из 50 микросервисов**. Если логика авторизации изменится, придется переписывать и переделывать все 50 сервисов.

API Gateway забирает эту боль на себя. Он принимает внешний запрос, проверяет валидность токена, отсеивает хакеров, и пускает внутрь кластера только «чистые» запросы. Внутренние сервисы могут даже не проверять токен — они доверяют шлюзу.

### 3. Сквозной функционал (Cross-cutting concerns)

Есть вещи, которые касаются всей системы в целом, и реализовывать их в каждом микросервисе — это дублирование кода:

- **Rate Limiting (Ограничение нагрузки):** Не даем одному IP-адресу делать больше 100 запросов в секунду.
    
- **CORS:** Настройка заголовков для браузеров.
    
- **SSL Termination:** Шлюз берет на себя расшифровку HTTPS-трафика (тяжелая математическая операция), а внутрь кластера запросы летят уже по быстрому и легкому HTTP.
    

### 4. Агрегация данных (Паттерн BFF - Backend for Frontend)

Мобильному приложению часто нужно показать на одном экране данные из трех разных сервисов (имя юзера, баланс и последние заказы). Если мобилка сделает 3 отдельных запроса по медленному 3G-интернету, экран будет грузиться вечность.

API Gateway может принять 1 запрос от телефона, сам **параллельно** сходить в 3 внутренних сервиса, склеить результат в один JSON и отдать телефону за один раз.

## Популярные инструменты в Java-мире

- **Spring Cloud Gateway:** Современный стандарт для Java. Построен на реактивном стеке (Project Reactor + Netty). Не блокирует потоки, держит огромную нагрузку.
    
- **Netflix Zuul:** Старая реализация от Netflix. Первая версия была блокирующей (на сервлетах), поэтому от нее все массово отказались в пользу Spring Cloud Gateway.
    
- **Kong / NGINX / Traefik:** Инфраструктурные решения. Они написаны не на Java (на Lua/C/Go), но часто DevOps-инженеры ставят их перед кластером, чтобы не писать свой шлюз на Java.

На архитектурных секциях и собеседованиях уровня Middle+ вопросы про API Gateway быстро уходят от простой теории к **нагрузке, безопасности и засадам в продакшене**.

API Gateway — это критический узел системы. Ошибки при его проектировании могут привести либо к падению всего приложения, либо к дырам в безопасности.

## 1. Архитектурный антипаттерн: "Жирный Шлюз" (Smart Proxy)

Это самая частая ошибка начинающих команд.

- **В чем проблема:** Разработчики начинают пихать в API Gateway бизнес-логику: хождения в базу данных, тяжелые трансформации JSON-ответов, валидацию сложных бизнес-правил или кастомную агрегацию данных из 10 сервисов.
    
- **Чем это грозит:** Шлюз мгновенно превращается в **новый распределенный монолит**. Команды начинают мешать друг другу в одном репозитории, релизы шлюза замедляются, а любой баг в бизнесе кладет всю сетевую инфраструктуру.
    
- **Как правильно:** Шлюз должен быть «тупым» прокси (Dumb Pipe). Его задачи — роутинг, проверять JWT-токены, обрезать заголовки и лимитировать трафик. Вся бизнес-логика и тяжелая агрегация должны жить либо в микросервисах, либо в отдельном слое **BFF (Backend for Frontend)**.
    

## 2. Ловушка реактивного стека: Блокирующий код

Современные шлюзы (например, **Spring Cloud Gateway**) построены на реактивном неблокирующем стеке (Spring WebFlux + Netty).

- **Как это устроено:** У Netty очень маленький пул потоков (Event Loop), обычно по количеству ядер процессора (например, 8–16 потоков). Эти потоки никогда не должны блокироваться!
    
- **Подводный камень:** Если разработчик в кастомном фильтре шлюза напишет блокирующий вызов (например, вызовет `RestTemplate.getForObject()`, сделает синхронный запрос в PostgreSQL через JDBC или вызовет `Thread.sleep()`), **поток Event Loop заблокируется**.
    
- **Катастрофа:** Всего 16 одновременных блокирующих запросов полностью заблокируют все потоки Netty. API Gateway перестанет отвечать вообще на любые запросы всех пользователей.
    

## 3. Дыра в безопасности: Подмена заголовков (Header Spoofing)

Классическая схема работы:

1. Клиент присылает запрос с JWT-токеном на API Gateway.
    
2. Шлюз проверяет подпись токена, достает оттуда `userId = 42` и роли.
    
3. Шлюз подмешивает заголовок `X-User-Id: 42` и пробрасывает запрос во внутренний микросервис.
    
4. Внутренний микросервис бездумно доверяет заголовку `X-User-Id`.
    

```
[Хакер] ---> (X-User-Id: 1) ---> [ API Gateway ] ---> (X-User-Id: 1) ---> [ Сервис Оплаты ]
```

- **В чем уязвимость:** Если хакер напрямую с улицы пришлет запрос с заголовком `X-User-Id: 1` (админ), а твой шлюз **забудет очистить/перезаписать** входящие заголовки перед отправкой во внутреннюю сеть, хакер получит доступ к чужим данным.
    
- **Как правильно:**
    
    1. Шлюз обязан удалять все чужие заголовки с префиксами `X-*` из входящего внешнего запроса.
        
    2. Внутри кластера стоит использовать **mTLS** (взаимную авторизацию по TLS) или подписывать внутренние запросы HMAC-ключом, чтобы микросервисы принимали трафик _строго_ от шлюза.
        

## 4. Распределенный Rate Limiter и падение Redis

Для ограничения количества запросов (Rate Limiting) шлюзы используют алгоритмы вроде _Token Bucket_ или _Leaky Bucket_. Так как экземпляров шлюза обычно несколько, их общий счетчик хранят в **Redis**.

```
[Gateway 1] --\
[Gateway 2] ---> ( Оценка RPS в Redis )
[Gateway 3] --/
```

- **Подводный камень:** Что делать шлюзу, если Redis упал или тормозит?
    
    - **Fail-Closed (Безопасный режим):** Шлюз начинает отбивать все запросы (429 / 500). Система полностью ложится для пользователей.
        
    - **Fail-Open (Режим доступности):** Шлюз прощает ошибки Redis и пропускает все запросы без ограничений. Пользователи довольны, но хакеры или ботнеды могут задосить внутренние сервисы.
        
- **Как правильно:** В зависимости от критичности сервиса выбирается стратегия. Чаще выбирают _Fail-Open_ с локальным фолбэком (каждый инстанс шлюза начинает считаться локально в своей памяти, пока Redis не поднимется).
    

## 5. Проблема сквозной трассировки (Correlation ID)

Когда запрос падает где-то на 5-м микросервисе, найти концы в логах невозможно, если шлюз не позаботился об идентификации запроса.

- **Правило хорошего тона:** API Gateway **на самом входе** обязан сгенерировать уникальный идентификатор (например, `X-Correlation-ID: uuid` или W3C Trace Context `traceparent`) и пробросить его во все внутренние вызовы.
    
- Все внутренние сервисы должны логировать этот ID, чтобы в OpenTelemetry / Zipkin / Jaeger можно было по одному клику увидеть весь путь запроса от шлюза до базы данных.
    

### Чек-лист для собеседования по API Gateway:

|**Проблема**|**Причина**|**Как правильно решать**|
|---|---|---|
|**Сильная связность**|Бизнес-логика внутри шлюза|Выносить в BFF или сервисы|
|**Падение RPS**|Блокирующий I/O в Event Loop (Netty)|Использовать только асинхронные/реактивные клиенты|
|**Уязвимость Auth**|Пропуск внешних `X-User-Id` заголовков|Очистка (sanitize) заголовков на входе|
|**Единая точка отказа**|Одно приложение шлюза|Несколько инстансов за внешним L4-балансировщиком (AWS ALB/Nginx)|
