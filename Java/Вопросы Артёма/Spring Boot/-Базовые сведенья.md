Переход от базовых концепций REST к Spring Boot — это логичный шаг. На собеседованиях джуниоры часто думают, что Spring и Spring Boot — это два разных фреймворка.

**Главная истина:** Spring Boot не заменяет Spring. Внутри Boot работает ровно тот же самый Spring Framework (с его Inversion of Control, Dependency Injection и AOP). Spring Boot — это просто очень умная "обертка", которая решает главную проблему классического Spring — **конфигурационный ад**.

Давай разберем 4 архитектурных отличия, которые сделали Boot стандартом индустрии.

### 1. Управление зависимостями (Dependency Hell vs Starters)

- **Классический Spring:** Чтобы поднять простой REST API с базой данных, тебе нужно было вручную собрать `pom.xml` из 20-30 библиотек. Тебе нужно было самому следить за тем, чтобы версия Spring MVC (например, 5.3.x) была совместима с версией Jackson, Hibernate и коннектором базы данных. Ошибка в версии одной библиотеки приводила к падению приложения при старте (знаменитый `NoSuchMethodError`).
    
- **Spring Boot (Starters):** Вводит понятие "Стартеров" и BOM (Bill of Materials). Ты добавляешь всего одну зависимость: `spring-boot-starter-web`. Boot сам подтягивает Spring MVC, Jackson, валидацию и сервер. Версии всех транзитивных зависимостей протестированы инженерами VMware на совместимость друг с другом.
    

### 2. Магия автоконфигурации (Auto-Configuration)

- **Классический Spring:** Не делает ничего по умолчанию. Чтобы подключиться к БД, тебе нужно написать класс с аннотацией `@Configuration` и вручную создать бины `DataSource`, `EntityManagerFactory` и `PlatformTransactionManager`, прописав в них кучу кода.
    
- **Spring Boot:** Использует философию **"Convention over Configuration"** (Соглашения важнее конфигурации).
    
    Как только Boot видит в твоем `pom.xml` библиотеку PostgreSQL, он "думает": _"Ага, разработчик хочет базу данных. Я сам создам `DataSource` и `HikariPool`, ему нужно только дать мне логин и пароль в `application.yml`"_. Это работает благодаря механизму условных бинов (аннотации вроде `@ConditionalOnClass` или `@ConditionalOnMissingBean`).
    

### 3. Модель развертывания (WAR vs Fat JAR)

Это архитектурное отличие определило победу Spring Boot в эпоху микросервисов и Docker.

- **Классический Spring:** Приложение компилировалось в архив `.war`. Тебе нужно было отдельно арендовать Linux-сервер, установить туда Java, установить веб-сервер (Tomcat или WildFly), настроить его, и только потом положить свой `.war` файл в папку `webapps`.
    
- **Spring Boot:** Вводит концепцию **Embedded Server (Встроенный сервер)**. Tomcat (или Undertow/Jetty) уже скомпилирован и лежит прямо внутри твоего приложения! Твое приложение компилируется в один большой `.jar` файл (Fat JAR). Для запуска нужен только установленный JRE и одна команда:
    
    `java -jar my-app.jar`
    
    Это идеально ложится в контейнеры Docker — один процесс, один порт.
    

### 4. Готовность к Production (Actuator)

- **Классический Spring:** Мониторинг приложения (сколько памяти потребляется, жива ли база данных, сколько HTTP-запросов приходит) нужно было писать с нуля или подключать тяжелые внешние JMX-агенты.
    
- **Spring Boot:** Имеет модуль `spring-boot-starter-actuator`. Подключив его, ты бесплатно получаешь готовые REST-эндпоинты (например, `/actuator/health` или `/actuator/prometheus`). Их используют оркестраторы (например, Kubernetes), чтобы понимать, живо ли твое приложение, и Prometheus — чтобы строить графики нагрузки в Grafana.
    

### Сводная таблица (Для собеседования)

| **Фича**           | **Классический Spring**                   | **Spring Boot**                                    |
| ------------------ | ----------------------------------------- | -------------------------------------------------- |
| **Цель**           | Фундамент (DI, IoC, AOP, MVC)             | Быстрый старт и Production-ready из коробки        |
| **Сборка проекта** | Десятки зависимостей вручную              | Starter POMs (готовые наборы)                      |
| **Конфигурация**   | Вручную (XML или `@Configuration` классы) | Автоматически (`@EnableAutoConfiguration`)         |
| **Сервер**         | Внешний Tomcat (Deploy WAR)               | Встроенный Tomcat (Run Fat JAR)                    |
| **Настройки**      | Раскиданы по коду и XML                   | Централизованы в `application.yml` / `.properties` |
