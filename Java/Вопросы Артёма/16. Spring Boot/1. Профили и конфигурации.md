Управление конфигурациями в Spring Boot строится вокруг одного из главных принципов методологии **The Twelve-Factor App** (Приложение Двенадцати Факторов): _строгое разделение кода и конфигурации_.

Один и тот же собранный `.jar` файл должен уметь запускаться и на ноутбуке разработчика, и в кластере Kubernetes на проде, просто меняя конфигурацию окружения.

Давай разберем, как Spring Boot решает эту задачу с помощью Профилей (Profiles) и иерархии свойств.

### 1. Как работают Профили (Profiles)?

**Профиль** — это именованная логическая группировка настроек и бинов. Классический набор: `dev` (разработка), `test` (тестирование), `prod` (продакшен).

Spring Boot ищет базовые настройки в файле `application.yml` (или `.properties`). Но если мы активируем профиль, Spring будет искать дополнительный файл по шаблону `application-{profile}.yml` и **переопределять** базовые настройки.

**Пример:** _Базовый `application.yml` (общий для всех):_

YAML

```
server:
  port: 8080
spring:
  application:
    name: my-cool-api
```

_Файл `application-prod.yml` (только для продакшена):_

YAML

```
spring:
  datasource:
    url: jdbc:postgresql://prod-db.internal:5432/main_db
# server.port не указан, поэтому он наследуется из базового файла (8080)
```

**Как активировать профиль?** Никогда не зашивайте активный профиль в код! На проде его передают извне:

1. Через аргумент JVM: `java -jar app.jar -Dspring.profiles.active=prod`
    
2. Через переменную окружения (в Docker/K8s): `SPRING_PROFILES_ACTIVE=prod`
    

### 2. Управление Бинами через `@Profile`

Профили управляют не только переменными в YAML, но и тем, **какие классы (бины) будут созданы в памяти**.

Частый кейс: на проде нам нужен реальный клиент для отправки SMS, а при локальной разработке мы хотим просто выводить текст SMS в консоль, чтобы не тратить деньги.

Java

```
public interface SmsSender {
    void send(String phone, String text);
}

// Создастся только если активен профиль 'prod'
@Service
@Profile("prod")
public class TwilioSmsSender implements SmsSender {
    public void send(String phone, String text) {
        // Логика вызова платного API
    }
}

// Создастся для любых профилей, КРОМЕ 'prod'
@Service
@Profile("!prod")
public class MockSmsSender implements SmsSender {
    public void send(String phone, String text) {
        System.out.println("Мок SMS на номер: " + phone);
    }
}
```

### 3. Архитектурный подход: `@Value` vs `@ConfigurationProperties`

Как правильно внедрять значения из YAML в код Java? Это частый вопрос на ревью.

**Подход Джуниора: `@Value`**

Java

```
@Service
public class PaymentService {
    @Value("${payment.gateway.url}")
    private String gatewayUrl;
    
    @Value("${payment.gateway.timeout-ms}")
    private int timeout;
}
```

_Минусы:_ Переменные размазаны по всему коду. IDE не дает автодополнение при написании YAML. Нет валидации при старте приложения (если забудешь прописать `timeout-ms`, узнаешь об этом только в рантайме, когда этот класс будет вызван).

**Подход Senior'а: `@ConfigurationProperties`** Создается специальный класс-холдер.

Java

```
@Component
@ConfigurationProperties(prefix = "payment.gateway")
@Validated // Включаем строгую проверку!
public class PaymentProperties {
    
    @NotBlank
    private String url;
    
    @Min(100)
    private int timeoutMs;
    
    // Геттеры и сеттеры обязательны
}
```

_Плюсы:_

1. Если в YAML ошибка или пропущено поле, Spring Boot "упадет" в самую первую секунду старта (Fail-Fast), защитив прод от некорректной работы.
    
2. Все свойства сгруппированы в одном типизированном объекте.
    
3. Ты просто инжектишь `PaymentProperties` в любой сервис через конструктор.
    

### 4. Иерархия источников свойств (Порядок переопределения)

Это ловушка на собеседованиях: _"У нас есть пароль к БД в `application.yml`. Как его безопасно подменить на сервере, не меняя код и не пересобирая JAR?"_

Spring Boot читает конфигурации из разных источников в строгом порядке. **То, что ниже в списке, переопределяет то, что выше:**

1. Базовый `application.yml` (упакован внутри JAR)
    
2. Профильный `application-prod.yml` (упакован внутри JAR)
    
3. Внешний файл `application.yml`, лежащий в папке рядом с `app.jar` на сервере.
    
4. Аргументы JVM (`-Dspring.datasource.password=123`)
    
5. **Переменные окружения ОС (Environment Variables).**
    
6. Аргументы командной строки (`--spring.datasource.password=123`)
    

**Магия Relaxed Binding (Гибкая привязка):** В Docker/Kubernetes не используют точки в названиях переменных. Spring Boot достаточно умен, чтобы понять, что переменная среды ОС `SPRING_DATASOURCE_PASSWORD` (в верхнем регистре через подчеркивания) — это то же самое, что `spring.datasource.password` в YAML. Именно так Kubernetes ConfigMaps и Secrets прокидывают пароли в микросервисы.
