Интервьюера интересует, понимаешь ли ты **состояние объекта в памяти (Object Header)**, **Java Memory Model (JMM)** и **оптимизации компилятора (JIT)**.

Вот топ-5 глубоких тем по `synchronized`, на которых «валят» опытных разработчиков.

### 1. Что именно мы блокируем? (Анатомия Монитора)

Ключевой вопрос: _"Где физически хранится информация о том, что объект заблокирован?"_

**Ответ Senior'а:** В Java каждый объект имеет заголовок (Object Header). В нем есть структура данных **Mark Word** (занимает 8 байт на 64-битных системах). Именно в Mark Word хранится ссылка на **Монитор (Monitor)** — внутренний механизм синхронизации. Интервьюер обязательно проверит, понимаешь ли ты разницу блокировок:

- `public synchronized void doWork()` — блокирует монитор текущего экземпляра объекта (`this`).
    
- `public static synchronized void doWork()` — блокирует монитор объекта класса (`MyClass.class`). Эти два метода **не заблокируют** друг друга, так как мониторы разные!
    

### 2. Секретная суперсила: Видимость (Visibility) в JMM

Многие думают, что `synchronized` нужен только для атомарности (чтобы потоки не перезаписали данные друг друга). Но интервьюер спросит: _"А как он влияет на кэши процессора?"_

**Ответ Senior'а:** `synchronized` строит жесткую связь **Happens-Before**. Когда поток **входит** в блок `synchronized`, он инвалидирует свой L1/L2 кэш и принудительно читает самые свежие данные из главной памяти (RAM). Когда поток **выходит** из блока (отпускает монитор), он принудительно сбрасывает все измененные переменные из кэша процессора обратно в RAM. Это гарантирует, что следующий поток увидит актуальное состояние.

### 3. Эволюция блокировок (Lock Optimizations в JVM)

Классический вопрос: _"Правда ли, что synchronized — это всегда медленное обращение к ядру ОС (OS Mutex)?"_

**Ответ Senior'а:** Нет, начиная с Java 6 это миф. JVM использует эскалацию блокировок:

1. **Biased Locking (Смещенная блокировка):** Если монитор захватывает всегда один и тот же поток, JVM вообще не использует синхронизацию, просто записывая ID потока в Mark Word. _(Важное уточнение для сеньора: в Java 15 этот механизм был признан устаревшим (JEP 374) и отключен по умолчанию, так как современные атомарные операции стали быстрее)._
    
2. **Lightweight Locking (Легковесная блокировка):** Если два потока пытаются захватить монитор, но **не одновременно** (нет жесткой конкуренции), JVM использует быструю CAS-операцию (Compare-And-Swap), избегая обращения к ядру ОС.
    
3. **Heavyweight Locking (Тяжелая блокировка):** Только если потоки столкнулись лбами в одну миллисекунду, JVM обращается к операционной системе (Mutex), и ожидающий поток "паркуется" (уходит в спящий режим), освобождая CPU.
    

### 4. Оптимизации JIT-компилятора (Escape Analysis)

Вопрос с подвохом: _"Что будет, если я напишу synchronized внутри локального метода на локальном объекте?"_

Java

```
public void doWork() {
    Object localLock = new Object();
    synchronized (localLock) { /* ... */ }
}
```

**Ответ Senior'а:** Блокировки физически не будет. В дело вступит **Lock Elision (Удаление блокировок)**. JIT-компилятор с помощью Escape Analysis поймет, что ссылка на `localLock` не покидает пределы метода. Раз объект недоступен другим потокам, конкуренция невозможна. JIT просто вырежет инструкцию `synchronized` из машинного кода.

### 5. Реентерабельность (Reentrancy)

Вопрос: _"Если поток зашел в `synchronized` метод А, а из него вызывает `synchronized` метод Б того же объекта, произойдет ли Deadlock?"_

**Ответ Senior'а:** Нет. Мониторы в Java — **реентерабельные** (повторно входимые). Внутри монитора хранится ID потока-владельца и счетчик (counter). Когда тот же поток заходит во второй `synchronized` метод, счетчик просто увеличивается (становится = 2). При выходе из методов счетчик уменьшается. Монитор освобождается для других потоков только когда счетчик равен 0.
