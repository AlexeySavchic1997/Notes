### Заблуждение 1: API Server против Service (Кто с кем общается)

Вы спросили: _"Я думал, все общаются друг с другом через сущность Service, а ты говоришь, что через API Server"_.

Оба утверждения верны, просто они относятся к разным процессам! В Kubernetes существует два параллельных "шоссе", которые никогда не пересекаются:

1. **Управляющий трафик (Control Plane):** Здесь царит **`kube-apiserver`**.
    
    - По этому шоссе ездят только "инфраструктурные грузовики".
        
    - Агент `kubelet` (на сервере) сообщает `api-server`: "Я жив, у меня свободно 2 ГБ памяти".
        
    - `kube-scheduler` спрашивает у `api-server`: "Есть ли новые поды, которым нужен сервер?".
        
    - Ваш код на Java в этом общении **не участвует**.
        
2. **Пользовательский трафик (Data Plane):** Здесь царит **`Service`**.
    
    - По этому шоссе ездят данные ваших пользователей.
        
    - Когда вашему Spring Boot (`customers-service`) нужно сохранить данные в базу, он делает запрос на внутренний домен `mysql-service`.
        
    - Сетевой компонент K8s перехватывает этот запрос и направляет его в под с базой данных.
        
    - **Самое важное:** `api-server` вообще не участвует в передаче этих данных! Если Control Plane полностью выйдет из строя (умрет `api-server`), ваши Java-сервисы продолжат успешно общаться с базой данных через `Service`.
        

### Заблуждение 2: `etcd` против `Deployment` (Хранилище против Логики)

Вы спросили: _"В etcd хранятся данные о том, сколько должно быть экземпляров, но разве этим не занимается Deployment?"_.

Здесь нужно разделить понятия **"Текст на бумаге"** (etcd) и **"Рабочий, который этот текст читает"** (Контроллер).

- **`Deployment` / `StatefulSet` — это просто концепция.** Это ваш YAML-файл, в котором написано: `replicas: 3`. Сам по себе `Deployment` ничего не делает, это просто набор пожеланий (чертеж).
    
- **`etcd` — это жесткий диск (архив).** Когда вы пишете `kubectl apply -f deployment.yaml`, API-сервер берет текст вашего манифеста и физически сохраняет его в базу данных `etcd`. `etcd` тоже ничего не делает, он просто надежно хранит байты.
    
- **`kube-controller-manager` — это прораб (активная программа).** Внутри него крутится бесконечный цикл — "Контроллер Деплойментов".
    
    1. Он постоянно читает базу `etcd`: _"Так, в базе лежит манифест Deployment, в котором написано 'хочу 3 пода'"_.
        
    2. Затем он проверяет реальность: _"А сколько подов сейчас запущено? Ого, только 1"_.
        
    3. Он принимает решение: _"Надо создать еще 2!"_ — и отправляет приказ API-серверу на создание недостающих сущностей.
        

### Архитектура: Кто за что отвечает (Итоговая картина)

Давайте пройдемся по схеме сверху вниз, чтобы закрепить картину:

#### 1. Мозг кластера (Control Plane / Master Nodes)

- **`etcd` (Память):** База данных. Знает ответы на вопросы: "Какие YAML-файлы загрузил DevOps?", "Какие пароли мы храним?", "На каком сервере физически запущен под №2?".
    
- **`kube-apiserver` (Рот и Уши):** Единственная дверь в кластер. Принимает команды от вас (kubectl) и от компонентов системы. Сохраняет всё в `etcd`.
    
- **`kube-scheduler` (Логист):** Читает из API: "Появился новый под". Ищет для него свободный Worker Node и говорит API: "Запусти его на сервере №3".
    
- **`kube-controller-manager` (Надзиратель):** Программа, реализующая логику `Deployment`, `StatefulSet`, `CronJob`. Следит, чтобы ожидаемое количество подов (из etcd) всегда совпадало с реальным.
    

#### 2. Рабочие лошадки (Worker Nodes)

Это физические серверы, где работают ваши приложения. На каждом из них установлены две критические программы:

- **`kubelet` (Бригадир):** Общается с `api-server`. Получает приказ "Запусти этот Docker-контейнер" и выполняет его на уровне операционной системы.
    
- **`kube-proxy` (Связист):** Именно эта маленькая программа реализует магию **`Service`**. Она настраивает сетевые правила (iptables) на Linux-сервере так, чтобы трафик от Java-приложения попадал точно в под с базой данных, даже если этот под вчера переехал на другой сервер.
