Разница между `flush` и `commit` — это классический вопрос на понимание того, как работают транзакции в реляционных базах данных и как с ними взаимодействует Hibernate.

Чтобы понять разницу моментально, представь работу с текстовым документом:

- **`flush()`** — это нажатие `Ctrl+S`. Текст сохранился на жесткий диск, но пока ты не закрыл файл, ты можешь нажать `Ctrl+Z` и отменить изменения. Никто другой твой черновик пока не видит.
    
- **`commit()`** — это отправка документа начальнику. Изменения зафиксированы окончательно, их видят все, и отменить их уже нельзя.
    

Давай разберем технические детали.

### 1. Как работает `flush()` (Синхронизация)

Метод `em.flush()` берет все изменения, которые накопились в оперативной памяти (в Persistence Context), генерирует для них SQL-запросы (`INSERT`, `UPDATE`, `DELETE`) и **отправляет их в базу данных**.

**Главные особенности `flush()`:**

- База данных выполняет эти SQL-запросы, но держит их во временном буфере.
    
- **Транзакция НЕ закрывается.**
    
- **Изоляция:** Другие параллельные потоки и пользователи базы данных **не видят** этих изменений (если уровень изоляции БД стандартный — `READ COMMITTED`).
    
- **Возможность отката:** Если после `flush()` в твоем коде вылетит `RuntimeException`, база данных отменит (Rollback) все эти выполненные SQL-запросы, и данные останутся нетронутыми.
    

### 2. Как работает `commit()` (Фиксация)

Метод `commit()` сообщает базе данных: _"Я закончил работу, сделай все мои изменения постоянными и видимыми для всех"_.

**Главные особенности `commit()`:**

- Перед тем как закоммитить транзакцию, Hibernate **автоматически вызывает `flush()`** (если режим сброса стоит по умолчанию — `FlushModeType.AUTO`).
    
- Транзакция закрывается. База данных снимает блокировки со строк.
    
- Изменения становятся видны всем остальным микросервисам и потокам.
    
- Отменить эти изменения (через Rollback) больше нельзя.
    

### Зачем вызывать `flush()` вручную?

Если `commit` сам вызывает `flush` в конце транзакции, зачем разработчики иногда пишут `em.flush()` (или `repository.flush()`) прямо посреди метода?

Есть три классические ситуации на проде:

#### 1. Обработка больших объемов данных (Batching)

Если тебе нужно вставить в БД 100 000 записей в одной транзакции, твой Persistence Context лопнет от нехватки оперативной памяти, пытаясь хранить 100 000 объектов. **Решение:** Ты сохраняешь объекты пачками по 50 штук, вручную вызываешь `flush()` (отправляя SQL в БД), а затем вызываешь `clear()` (очищая память Hibernate).

Java

```
for (int i = 0; i < 100000; i++) {
    em.persist(new User(...));
    if (i % 50 == 0) {
        em.flush(); // Отправили пачку в БД
        em.clear(); // Выбросили объекты из оперативной памяти
    }
}
```

#### 2. Зависимость от сгенерированного ID

Представь, что ты создаешь Заказ (`Order`). Тебе нужно получить его `ID` (который генерируется базой данных через `SEQUENCE` или `IDENTITY`), чтобы тут же создать вложенный объект — Чек (`Receipt`), который ссылается на этот `ID`. Если ты просто сделаешь `persist()`, запроса в базу не произойдет, и `ID` может быть недоступен (особенно при стратегиях генерации, отличных от `IDENTITY`). Вызов `flush()` заставляет базу сгенерировать `ID`, который ты можешь использовать дальше в том же методе.

#### 3. Перехват исключений базы данных

Это частая ошибка новичков. Разработчик пытается обернуть сохранение в `try-catch`, чтобы поймать ошибку уникального индекса (например, email уже существует):

Java

```
@Transactional
public void createUser() {
    try {
        userRepository.save(new User("test@test.com"));
    } catch (DataIntegrityViolationException e) {
        // Логика обработки ошибки
    }
}
```

**В чем баг?** Блок `catch` никогда не сработает! `save()` не отправляет SQL в БД немедленно. SQL отправится только в самом конце метода, когда Spring будет делать `commit()` (уже за пределами твоего `try-catch`). **Решение:** Если ты хочешь поймать ошибку БД прямо здесь, нужно использовать метод `saveAndFlush()` (или вручную позвать `flush()`). Тогда SQL выполнится немедленно, БД вернет ошибку, и твой `catch` её перехватит.
