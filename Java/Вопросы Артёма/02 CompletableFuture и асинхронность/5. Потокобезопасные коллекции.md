==5.1 Синхронизированные==
Тема потокобезопасных коллекций — это абсолютная классика на собеседованиях. Эволюцию коллекций в Java можно разделить на два больших лагеря: **Synchronized** (старый подход) и **Concurrent** (современный подход).

Поскольку ты просил начать с синхронизированных, давай разберем этот «старый мир», как он работает и почему на смену ему пришел `java.util.concurrent`.

## 1. Динозавры Java: Vector и Hashtable

В самых первых версиях Java (1.0) разработчики решили проблему потокобезопасности максимально в лоб. Они создали классы `Vector` (аналог `ArrayList`), `Hashtable` (аналог `HashMap`) и `Stack`.

**Как они работают?** Всё предельно просто. Абсолютно каждый метод внутри этих классов помечен ключевым словом `synchronized`.

Java

```
public synchronized boolean add(E e) {
    // логика добавления
}

public synchronized E get(int index) {
    // логика чтения
}
```

**Почему их больше не используют?** Потому что монитором (мьютексом) выступает сам объект коллекции (`this`). Это означает **глобальную блокировку (Coarse-grained locking)**. Если один поток вызвал метод `get()`, чтобы прочитать элемент, все остальные потоки (даже те, которые тоже хотят просто прочитать данные) будут заблокированы и выстроятся в очередь. В высоконагруженных многопоточных приложениях это превращается в чудовищное «бутылочное горлышко» (bottleneck).

## 2. Шаг вперед: Обёртки Collections.synchronized*

В Java 1.2 появился Java Collections Framework (`ArrayList`, `HashMap` и т.д.), которые по умолчанию были не потокобезопасными. Но разработчики добавили утилитные методы-обертки:

Java

```
List<String> list = new ArrayList<>();
List<String> syncList = Collections.synchronizedList(list);

Map<String, String> syncMap = Collections.synchronizedMap(new HashMap<>());
```

**Как это работает "под капотом"?** Здесь используется паттерн **Decorator**. Метод создает класс-обертку. Внутри этой обертки хранится ссылка на твою оригинальную коллекцию и специальный объект `mutex` (по умолчанию это сама обертка `this`).

Java

```java
// Упрощенный код из исходников Java
public void add(int index, E element) {
    synchronized (mutex) {
        list.add(index, element);
    }
}
```

По сути, это то же самое, что и `Vector`. Глобальная блокировка осталась. Но этот подход был чуть гибче, так как позволял сделать потокобезопасной любую коллекцию.

## 3. Любимые вопросы-ловушки на собеседовании

Интервьюеры любят проверять, понимаешь ли ты подводные камни синхронизированных коллекций. Вот два главных капкана:

### Капкан №1: Итерация и ConcurrentModificationException

Даже если коллекция создана через `Collections.synchronizedList()`, обход этой коллекции через `for-each` (или итератор) **не является потокобезопасным**.

Если один поток перебирает элементы, а второй в это время удаляет или добавляет элемент, первый поток упадет с ошибкой `ConcurrentModificationException` (итератор реализован по принципу fail-fast).

**Как правильно (и это нужно озвучить на интервью):** При итерации по синхронизированной коллекции ты **обязан** вручную заблокировать ее на всё время обхода:

Java

```java
List<String> syncList = Collections.synchronizedList(new ArrayList<>());

// Ручная блокировка ОБЯЗАТЕЛЬНА при итерации!
synchronized (syncList) {
    for (String s : syncList) {
        System.out.println(s);
    }
}
```

### Капкан №2: Составные операции (Check-then-act)

Синхронизированные коллекции гарантируют атомарность только **одиночных** вызовов. Если тебе нужно сделать логику «проверь и добавь», синхронизированная коллекция не спасет от состояния гонки (Race Condition).

Java

```java
// ПЛОХО: Два потока могут одновременно пройти проверку contains
if (!syncList.contains("Apple")) {
    syncList.add("Apple"); 
}

// ПРАВИЛЬНО: Опять нужна внешняя ручная блокировка
synchronized (syncList) {
    if (!syncList.contains("Apple")) {
        syncList.add("Apple");
    }
}
```

**Резюме по синхронизированным коллекциям:** Они работают через единую глобальную блокировку. Из-за этого они невероятно медленные в конкурентной среде, так как полностью убивают параллелизм. Сегодня они считаются легаси-подходом.

==5.2 Несинхронизированные==
## 1. ConcurrentHashMap (Король собеседований)

Главная проблема старой `Hashtable` (или `Collections.synchronizedMap`) — потоки выстраивались в одну общую очередь к объекту мапы. `ConcurrentHashMap` решает эту проблему за счет **гранулярных (точечных) блокировок и неблокирующих алгоритмов**.

> **Важно для интервью:** Обязательно уточни, что реализация радикально изменилась в Java 8. В Java 7 использовался механизм Segment Locking (мапа делилась на 16 независимых сегментов-кусков). Сейчас этот подход устарел.

**Как это работает в современных версиях (Java 8+):**

1. **Чтение без блокировок:** Метод `get()` вообще не использует локи! Узлы мапы (классы `Node`) устроены так, что их поля `val` и `next` помечены как `volatile`. Чтение всегда атомарно и моментально возвращает свежие данные из памяти.
    
2. **Умная запись (CAS + точечный synchronized):** Метод `put()` работает виртуозно:
    
    - Хэш-функция вычисляет нужную корзину (индекс в массиве).
        
    - Если корзина **пустая**, поток использует неблокирующую атомарную операцию **CAS (Compare-And-Swap)**, чтобы положить туда первый элемент. Никаких мьютексов!
        
    - Если в корзине **уже есть элементы** (там цепочка или дерево), поток делает `synchronized` **только на первом узле (head)** этой конкретной корзины.
        
3. **Итог:** Два потока могут одновременно писать данные в мапу, если они попали в _разные_ корзины. Блокировка происходит, только если случилась коллизия хэшей.
    

### Вопрос с подвохом: Как работает метод `size()`?

В обычной `HashMap` есть поле `size`, которое меняется при добавлении. В многопоточной среде держать одно поле `size` нельзя — все потоки будут драться за него, создавая bottleneck. В `ConcurrentHashMap` размер вычисляется с помощью массива счетчиков (`CounterCell[]`). При добавлении элемента поток увеличивает случайный счетчик в этом массиве. Метод `size()` просто суммирует значения всех счетчиков. Это гениальное решение для максимальной скорости!

## 2. CopyOnWriteArrayList (Копия при записи)

Это решение для совершенно другой проблемы. `CopyOnWriteArrayList` идеален для ситуаций, когда у нас **очень много чтений и крайне мало записей** (например, список слушателей событий).

**Как это работает:**

1. Внутри хранится обычный массив, ссылка на который помечена как `volatile`.
    
2. **Чтение (get, iterator):** Абсолютно свободно, не использует никаких блокировок.
    
3. **Запись (add, remove):** Здесь начинается магия (и плата за скорость чтения):
    
    - Поток захватывает лок (`ReentrantLock` или `synchronized`).
        
    - Создается **полная копия** текущего массива размером `n + 1`.
        
    - В конец нового массива добавляется новый элемент.
        
    - `volatile` ссылка переключается на новый массив.
        
    - Старый массив со временем удаляется сборщиком мусора.
        

### Вопрос с подвохом: А как же `ConcurrentModificationException`?

Его здесь не бывает принципиально. Когда ты создаешь итератор, он получает **снимок (snapshot)** массива в том виде, в котором он был на момент вызова `iterator()`. Если во время обхода списка другой поток добавит элемент, итератор об этом не узнает (он работает со старым массивом) и не упадет с ошибкой.

## 3. ConcurrentSkipListMap (Замена TreeMap)

Если тебе нужна **отсортированная** потокобезопасная мапа, `ConcurrentHashMap` не подойдет (он не гарантирует порядок). В старом мире ты бы использовал `Collections.synchronizedMap(new TreeMap<>())`.

В мире `concurrent` создали `ConcurrentSkipListMap`. В его основе лежит структура данных _Skip List_ (Список с пропусками). Он работает без блокировок, исключительно на `volatile` ссылках и операциях CAS. Это довольно сложная структура, и обычно достаточно просто знать о её существовании и о том, что она является неблокирующей заменой `TreeMap`.

## 4. Неблокирующие очереди (ConcurrentLinkedQueue)

Это очередь, которая не использует локов вообще. Она построена на алгоритме Майкла-Скотта. Все операции добавления в хвост и взятия из головы используют бесконечные циклы с операцией CAS. Если `Thread 1` не успел атомарно обновить хвост очереди (потому что его опередил `Thread 2`), он просто прочитает новое состояние и попробует сделать CAS еще раз (это называется _Spin-Lock_ или _Busy-Wait_).
