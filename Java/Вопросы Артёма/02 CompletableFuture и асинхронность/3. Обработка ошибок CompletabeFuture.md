В `CompletableFuture` ошибки **распространяются по цепочке (pipeline)** вниз, пропуская успешные шаги, пока не наткнутся на обработчик. Это очень похоже на блок `catch` в обычном коде.

Есть 3 главных метода для работы с ошибками. Их нужно знать наизусть.

### 1. `exceptionally()` — (Аналог `catch` с восстановлением)

Используется, чтобы перехватить ошибку и **вернуть значение по умолчанию (fallback)**. Если ошибки не было, этот блок просто игнорируется.

Java

```java
CompletableFuture<Integer> future = CompletableFuture.supplyAsync(() -> {
        return 10 / 0; // ArithmeticException
    })
    .thenApply(res -> res * 2) // Этот шаг будет ПРОПУЩЕН из-за ошибки выше
    .exceptionally(ex -> {
        System.out.println("Упс, ошибка: " + ex.getMessage());
        return -1; // Возвращаем дефолтное значение
    })
    .thenApply(res -> res + 10); // А этот шаг ВЫПОЛНИТСЯ (на вход придет -1)

System.out.println(future.join()); // Результат: 9
```

### 2. `handle()` — (Аналог `try-catch-finally`)

В `handle` всегда приходят два параметра: `result` (результат, если всё ок) и `exception` (ошибка, если всё упало). При этом один из них всегда будет `null`. Этот метод позволяет не только обработать ошибку, но и **трансформировать результат** в другой тип.

Java

```java
CompletableFuture<String> future = CompletableFuture.supplyAsync(() -> {
        // if (true) throw new RuntimeException("БД недоступна");
        return "Данные из БД";
    })
    .handle((result, ex) -> {
        if (ex != null) {
            System.out.println("Логируем ошибку: " + ex.getMessage());
            return "Ошибка загрузки"; // Возвращаем fallback строку
        } else {
            return "Успешно: " + result; // Модифицируем успешный результат
        }
    });
```

### 3. `whenComplete()` — (Аналог блока `finally` / Заглянуть и не трогать)

Как и `handle`, он принимает `(result, exception)`. Но в отличие от `handle`, он **не меняет возвращаемое значение и не "гасит" ошибку**. Он используется просто как `peek()` в стримах — чтобы залогировать результат или закрыть ресурсы, позволив ошибке лететь дальше по цепочке.

Java

```java
CompletableFuture.supplyAsync(() -> {
        throw new RuntimeException("Фатальная ошибка");
    })
    .whenComplete((result, ex) -> {
        if (ex != null) {
            System.out.println("Просто залогировали ошибку: " + ex.getMessage());
        }
    }); 
// Внимание: после whenComplete исключение полетит дальше! 
// Если никто не вызовет exceptionally, вызов join() выбросит исключение.
```

## 3. Нюансы для собеседования (Вопросы с подвохом)

**Подвох №1: Проброс ошибок в `join()` vs `get()`** В `CompletableFuture` есть два способа забрать результат синхронно: `get()` и `join()`. В чем разница при обработке ошибок?

- `get()` бросает проверяемое (checked) исключение `ExecutionException`. Заставляет писать `try-catch`.
    
- `join()` бросает **непроверяемое (unchecked)** исключение `CompletionException`. Именно поэтому в современном коде почти всегда используют `join()` — он не захламляет код `try-catch` блоками.
    

**Подвох №2: `CompletionException`** Так же как и в `ExecutionException`, реальная ошибка (например, твой `IllegalArgumentException`) будет лежать _внутри_ `CompletionException`. Поэтому внутри `exceptionally(ex -> ...)` часто приходится писать:

Java

```java
Throwable realCause = ex.getCause() != null ? ex.getCause() : ex;
```

**Подвох №3: Асинхронные обработчики** У каждого из трех методов есть брат-близнец с суффиксом `Async` (например, `exceptionallyAsync()`).

- Обычный `exceptionally` выполнится в том же потоке, который завершил предыдущую задачу (или в потоке `main`, если задача уже завершилась к моменту подписки).
    
- `exceptionallyAsync` отправит выполнение блока обработки ошибки в другой поток из пула `ForkJoinPool` (или кастомного экзекьютора).
  
==Что происходит в `CompletableFuture.allOf()`?==

Метод `allOf()` создает новый фьючер, который считается выполненным только тогда, когда завершатся **все** переданные в него задачи.

Если одна (или несколько) задач падают с `Exception`, происходит следующее:

1. **Отсутствие Short-Circuiting (Главный подвох):** Результирующий `allOf()` **не завершится сразу** при первой ошибке. Он честно дождется завершения _абсолютно всех_ остальных задач.
    
2. **Проброс ошибки:** После того как все задачи отработают (успешно или с ошибкой), сам `allOf()` завершится исключительно с `CompletionException`.
    
3. **Какая ошибка вылетит?** Внутри `CompletionException` (в методе `getCause()`) будет лежать исключение одной из упавших задач. Если упало несколько задач, остальные исключения будут просто «проглочены» (ты их не увидишь в результирующем фьючере). Остальные успешные результаты также станут недоступны через сам объект `allOf()`.
4. 
==Что происходит в `CompletableFuture.anyOf()`?==

Метод `anyOf()` работает по принципу гонки: побеждает тот, кто завершится первым.

Если падает Exception, поведение зависит исключительно от скорости:

1. **Если задача с ошибкой завершилась ПЕРВОЙ:** Результирующий `anyOf()` моментально завершается с этой ошибкой (бросает `CompletionException`). Остальные задачи продолжат выполняться в фоновом пуле потоков, но их результаты (или ошибки) будут проигнорированы.
    
2. **Если первой завершилась успешная задача:** Результирующий `anyOf()` успешно вернет этот результат. Если вторая (более медленная) задача потом упадет с ошибкой — это ни на что не повлияет, результат уже отдан.
