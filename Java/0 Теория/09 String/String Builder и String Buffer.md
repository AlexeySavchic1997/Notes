
Это классический вопрос из серии Java Core. На уровне Junior достаточно сказать: _"String неизменяемый, а эти два — изменяемые"_. Но на уровне Middle/Senior интервьюер ждет от тебя понимания того, **как они работают с памятью (под капотом)** и **почему один из них сегодня считается "мертвым" кодом**.

Давай разложим всё по полочкам.

### 1. Главное отличие от `String`: Мутабельность (Изменяемость)

Как мы обсуждали, `String` — это **Immutable** (неизменяемый) класс. Любая попытка изменить строку (`str + "a"`, `str.replace()`) приводит к созданию **абсолютно нового массива в памяти** и нового объекта. Старый объект становится мусором для GC.

`StringBuilder` и `StringBuffer` — это **Mutable** (изменяемые) классы. Они оба наследуются от общего абстрактного класса `AbstractStringBuilder`. Внутри них тоже лежит массив символов/байтов (`byte[] value`), но он **не помечен** ключевым словом `final`.

**Как это работает под капотом:**

1. При создании `new StringBuilder()` внутри создается пустой массив размером 16 символов (capacity по умолчанию).
    
2. Когда ты делаешь `.append("hello")`, символы просто записываются в этот же массив. Никаких новых объектов!
    
3. **Что если массив переполнится?** Если ты попытаешься добавить 17-й символ, сработает математика: класс создаст новый массив по формуле `(старая_емкость * 2) + 2` (то есть на 34 символа), быстро скопирует туда старые данные через нативный `System.arraycopy()` и удалит старый массив.
    

> **Совет Senior'а:** Если ты заранее знаешь, что склеишь строку примерно на 1000 символов, всегда пиши `new StringBuilder(1000)`. Это спасет JVM от создания нескольких промежуточных массивов и лишних вызовов `arraycopy` при расширении.

### 2. `StringBuilder` против `StringBuffer`: Битва эпох

Эти два класса делают абсолютно одно и то же. У них одинаковые методы (`append`, `insert`, `reverse`). Разница ровно одна, и она кроется в многопоточности.

#### `StringBuffer` (Старичок из Java 1.0)

- **Особенность:** Он **потокобезопасен (Thread-safe)**.
    
- **Как это сделано:** Все его основные методы (включая `append`) помечены ключевым словом `synchronized`. Это значит, что если два потока попытаются одновременно дописать текст в один `StringBuffer`, они выстроятся в очередь. Механизм захватит монитор (Monitor Lock) объекта.
    
- **Проблема:** Блокировки (синхронизация) — это **очень дорого** для процессора. В 99% случаев мы склеиваем строки внутри одного метода, в одном потоке. Нам не нужна никакая синхронизация! Но `StringBuffer` всё равно будет тратить такты процессора на захват и освобождение замка (монитора).
    

#### `StringBuilder` (Герой из Java 1.5)

- **Особенность:** Он **не потокобезопасен (Not thread-safe)**.
    
- **Как это сделано:** Из его методов просто удалили слово `synchronized`.
    
- **Результат:** Он работает в разы быстрее, чем `StringBuffer`, потому что не тратит время на блокировки.
    

### Архитектурный итог для собеседования

Если тебя спросят, что и когда использовать, правильный ответ звучит так:

1. **`StringBuffer` — это наследие прошлого (Legacy).** В современном коде его писать **нельзя**. Если тебе действительно нужно склеивать строку из нескольких потоков (что само по себе звучит как странная архитектура), лучше использовать современные потокобезопасные коллекции или атомарные операции.
    
2. **`StringBuilder` — это стандарт** для динамического формирования строк в циклах или сложных алгоритмах внутри одного потока.
    
3. **Обычный `String` (с оператором `+`)** — идеален для простого склеивания 2-3 переменных в одну строчку (например, в `log.info`). Как мы уже обсуждали, современный компилятор (через `invokedynamic`) сам оптимизирует этот плюс даже лучше, чем если бы ты писал `StringBuilder` руками.
