Термин **REST** часто используют как синоним для "любого API, которое отдает JSON по HTTP". На собеседованиях уровня Middle/Senior за такое понимание сразу снижают баллы.

REST — это строгий архитектурный стиль, созданный Роем Филдингом (одним из авторов протокола HTTP) в его докторской диссертации в 2000 году.

Давай разберем саму суть, а в следующем ответе перейдем к жестким вопросам с собеседований.

## 1. Расшифровка: Representational State Transfer

В переводе это **"Передача состояния представления"**. Звучит сложно, но технический смысл гениально прост:

- **State (Состояние):** У нас есть сущность на сервере (например, строка в таблице `users` базы данных). У нее есть текущее состояние (Имя: Иван, Баланс: 100).
    
- **Representational (Представление):** Клиент (мобилка или браузер) никогда не получает саму строку из БД или Java-объект. Сервер берет состояние и формирует его _представление_ в удобном текстовом формате (обычно JSON, реже XML).
    
- **Transfer (Передача):** Это представление передается по сети (через HTTP). Клиент читает JSON, меняет в нем баланс на 200 и отправляет это _новое представление состояния_ обратно на сервер. Сервер валидирует его и обновляет БД.
    

**Архитектурный итог:** Клиент и сервер обмениваются не командами (как в RPC / SOAP), а документами, отражающими состояние ресурсов.

## 2. 6 Ограничений REST (Констрейнты Филдинга)

Чтобы API официально считалось RESTful, оно должно строго соблюдать 6 правил (ограничений). Если нарушить хоть одно (кроме последнего), система перестает быть REST.

1. **Client-Server (Разделение клиента и сервера):** Жесткое разделение ответственности. Клиент занимается только UI и состоянием сеанса пользователя. Сервер занимается только бизнес-логикой и хранением данных. Они развиваются независимо.
    
2. **Stateless (Без состояния сервера):** Сервер **не должен** хранить у себя информацию о текущей сессии клиента (никаких `HttpSession` в памяти сервера). Каждый новый HTTP-запрос от клиента должен содержать абсолютно все данные для его понимания (например, JWT токен авторизации). Это позволяет балансировщику кидать запросы одного клиента на разные сервера (горизонтальное масштабирование).
    
3. **Cacheable (Кэшируемость):** Каждый ответ сервера должен явно помечаться как кэшируемый или некэшируемый (через заголовки HTTP, например `Cache-Control`). Если ответ кэшируемый, клиент имеет право использовать эти данные повторно без похода на сервер.
    
4. **Uniform Interface (Единообразный интерфейс):** Это сердце REST. Оно включает в себя 4 подправила:
    
    - _Идентификация ресурсов:_ Ресурсы идентифицируются через URI (например, `/users/42`).
        
    - _Манипуляция через представления:_ Клиент меняет ресурс, отправляя его измененный JSON.
        
    - _Самоописываемые сообщения:_ Запрос содержит всю мета-информацию (например, `Content-Type: application/json`).
        
    - _HATEOAS (Hypermedia):_ Сервер возвращает не только данные, но и ссылки на следующие доступные действия (мы обсуждали это в модели зрелости Ричардсона).
        
5. **Layered System (Слоистая система):** Клиент никогда не знает, общается ли он напрямую с конечным сервером, или с балансировщиком нагрузки, API Gateway или кэширующим прокси-сервером. Архитектура должна работать одинаково независимо от количества слоев сети.
    
6. **Code on Demand (Код по требованию — Опционально):** Единственное необязательное правило. Сервер может отправлять клиенту исполняемый код (например, скрипты JavaScript для браузера), чтобы расширить функционал клиента на лету. На бэкенде (Server-to-Server) это почти никогда не используется.

==Вопросы по REST==

На собеседованиях уровня Middle/Senior проверяют не знание терминов, а то, как вы решаете архитектурные противоречия. REST в теории красив, но на практике он часто сталкивается с суровой реальностью бизнес-требований.

Вот топ-4 "ловушек", на которых валят кандидатов.

### 1. Ловушка "Сложный поиск" (GET vs POST)

**Вопрос интервьюера:** _"Вам нужно сделать эндпоинт для поиска товаров. Пользователь может выбрать 20 фильтров, включая список из 500 ID категорий и длинный многоугольник координат на карте. Какой HTTP-метод вы используете?"_

- **Ответ Джуниора:** `GET`. Это же получение данных, значит нужен безопасный метод. Передам все 500 ID в Query-параметрах (`/api/products?categories=1,2,3...`).
    
- **Почему это провал:** Вы упретесь в лимит длины URL. Спецификация HTTP не ограничивает длину URL, но балансировщики (Nginx), файрволы и браузеры жестко режут URL длиннее 2048 (иногда 8192) символов. Запрос упадет с ошибкой `414 URI Too Long`.
    
- **Ответ Senior'а:** "Чистый REST здесь ломается. Я использую **`POST`**. Да, семантически POST предназначен для создания, но здесь я создам эндпоинт вида `POST /api/products/search` и передам все фильтры в формате JSON в теле запроса (Body). _Дополнительный плюс к карме:_ Если интервьюер душный приверженец спецификаций, упомяните новый драфт HTTP-метода **`QUERY`** (или `REPORT` из WebDAV), которые созданы специально для безопасного чтения с передачей Body, но на практике в Spring Boot все используют POST".
    

### 2. Ловушка "Действия вместо ресурсов" (RPC vs REST)

**Вопрос интервьюера:** _"У нас есть ресурс Пользователь. Нам нужно его забанить. Как будет выглядеть REST URL и метод?"_

- **Ответ Джуниора:** `POST /api/users/123/ban` или `GET /api/users/123/ban`.
    
- **Почему это провал:** Глагол `ban` в URL — это прямое нарушение REST (Uniform Interface). Это RPC-стиль (Remote Procedure Call).
    
- **Ответ Senior'а:** "В REST всё есть ресурс. Есть два правильных архитектурных пути:
    
    1. **Смена состояния:** Бан — это просто изменение статуса пользователя. Я отправлю `PATCH /api/users/123` с телом `{"status": "BANNED"}`.
        
    2. **Создание подресурса (Самый гибкий):** Бан можно рассматривать как отдельную сущность (например, с указанием причины и срока). Тогда я сделаю: `POST /api/users/123/bans` с телом `{"reason": "spam", "duration_days": 7}`. Это создаст ресурс "Блокировка", привязанный к пользователю".
        

### 3. Ловушка "Версионирование API"

**Вопрос интервьюера:** _"Как правильно версионировать REST API (v1, v2), чтобы не сломать старых мобильных клиентов при релизе новых фичей?"_

- **Ответ Джуниора:** "Просто добавлю в URL: `/api/v1/users` и `/api/v2/users`".
    
- **Почему это ловушка:** Это не ошибка, так делает 80% рынка (включая Stripe и GitHub). Но интервьюер ждет, что вы понимаете **минусы** этого подхода с точки зрения "чистого REST".
    
- **Ответ Senior'а:** "Существует 3 подхода, у каждого свои трейд-оффы:
    
    1. **URI Versioning (`/v1/users`):** Самый простой и популярный. Минус: нарушает REST, так как URL должен идентифицировать сущность, а не ее версию. Сущность-то одна и та же.
        
    2. **Custom Header (`X-API-Version: 2`):** URL остается чистым (`/api/users`), версия передается в заголовке. Минус: сложнее тестировать в браузере, сложнее настраивать кэширование на балансировщике.
        
    3. **Content Negotiation (`Accept: application/vnd.myapi.v2+json`):** Самый RESTful подход (так рекомендует GitHub в новых API). Мы просим сервер вернуть представление ресурса в конкретном формате (версии). Минус: самый сложный в реализации и понимании для клиентов".
        

### 4. Ловушка "Идемпотентность POST" (Double Submit)

**Вопрос интервьюера:** _"Мобильное приложение отправляет POST-запрос на оплату заказа. Сеть лагнула, клиент не получил ответ и отправил запрос повторно. Как сделать так, чтобы мы не списали деньги дважды?"_

- **Ответ Джуниора:** "Ну, перед списанием я сделаю `SELECT` в базу и проверю, оплачен ли заказ".
    
- **Почему это провал:** Состояние гонки (Race Condition). Два параллельных потока на бэкенде сделают `SELECT` одновременно, увидят, что заказ не оплачен, и оба спишут деньги.
    
- **Ответ Senior'а:** "POST не идемпотентен, поэтому я реализую паттерн **Idempotency Key**.
    
    1. Мобильный клиент генерирует уникальный UUID (Idempotency Key) перед отправкой и кладет его в HTTP-заголовок (например, `Idempotency-Key: 123e4567...`).
        
    2. При получении запроса бэкенд пытается атомарно сохранить этот ключ в базу (или Redis) с привязкой к заказу.
        
    3. Если это дубль, БД выдаст ошибку `Unique Constraint Violation` (или Redis вернет `false` на операцию `SETNX`).
        
    4. Бэкенд перехватит ошибку и просто вернет клиенту кэшированный успешный ответ от первого запроса (или статус `409 Conflict`), не выполняя бизнес-логику повторно".
