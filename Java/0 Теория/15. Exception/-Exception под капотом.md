На уровне Junior исключения — это просто блоки `try-catch-finally`. Но на уровне Middle/Senior интервьюер ждет от тебя понимания того, **как исключения работают на уровне байт-кода JVM**, сколько они стоят системе с точки зрения производительности и как они взаимодействуют с многопоточностью, которую мы только что обсуждали.

Давай разберем архитектуру исключений (Exceptions) без "воды" про базовый синтаксис.

### 1. Анатомия в Байт-коде (Exception Table)

Миф: _"Блок `try-catch` замедляет работу программы, даже если исключение не выбрасывается"_.

**Техническая реальность:**

На уровне байт-кода JVM (в `.class` файле) никаких блоков `try` и `catch` не существует. Компилятор превращает их в обычный линейный код и прикрепляет к методу специальную структуру — **Exception Table (Таблица исключений)**.

Она выглядит примерно так:

|**From (строка)**|**To (строка)**|**Target (обработчик)**|**Type (Класс ошибки)**|
|---|---|---|---|
|10|14|25|`java.io.IOException`|

**Как это работает:** Если код выполняется успешно, процессор просто игнорирует эту таблицу. **Оверхед равен нулю.**

Но если на 12-й строке происходит сбой, JVM прерывает выполнение, берет тип ошибки, идет в Exception Table, ищет подходящий диапазон и переносит указатель (Program Counter) на 25-ю строку.

### 2. Почему бросать исключения — это экстремально дорого?

Если сам `try-catch` бесплатный, то почему говорят, что исключения бьют по производительности?

Причина кроется в одном единственном нативном (С++) методе, который вызывается при создании объекта исключения: **`Throwable.fillInStackTrace()`**.

Когда ты пишешь `throw new RuntimeException()`, JVM вынуждена:

1. Приостановить текущий поток.
    
2. Пройтись по всему стеку вызовов (Call Stack) в памяти от текущего метода до самого низа (метода `main` или `run`).
    
3. Собрать имена классов, методов и номера строк.
    
4. Сформировать из этого массив элементов `StackTraceElement[]`.
    

Если стек глубокий (например, 100+ вызовов в Spring), создание одного исключения может занимать **в 100-1000 раз больше времени**, чем создание обычного объекта.

> **Senior трюк:** Если ты используешь исключения чисто для бизнес-логики (управления потоком выполнения), а не для логирования, ты можешь переопределить метод `fillInStackTrace()`, чтобы он ничего не делал. Выброс такого исключения будет стоить копейки.
> 
> Java
> 
> ```
> public class FastBusinessException extends RuntimeException {
>     @Override
>     public synchronized Throwable fillInStackTrace() {
>         return this; // Пропускаем сборку стека!
>     }
> }
> ```

### 3. Архитектурный холивар: Checked vs Unchecked

В Java есть два вида исключений (помимо фатальных `Error`):

- **Checked (Проверяемые) - `Exception`:** Компилятор заставляет тебя писать `try-catch` или `throws`.
    
    - _Задумка:_ Заставить разработчика обрабатывать ожидаемые сбои (нет файла, упала сеть).
        
    - _Проблема:_ Они ломают принцип OCP (Open-Closed Principle). Если метод на самом дне иерархии начинает бросать новое Checked исключение, тебе придется менять сигнатуры (добавлять `throws`) у всех десятков методов выше по стеку. Кроме того, Checked исключения **несовместимы с лямбдами и Stream API**.
        
- **Unchecked (Непроверяемые) - `RuntimeException`:** Компилятор их игнорирует.
    
    - _Современный стандарт:_ Вся современная экосистема (Spring Framework, Hibernate, Kotlin) отказалась от Checked исключений. Если падает база данных, Spring бросает непроверяемый `DataAccessException`. Идея в том, что бизнес-код всё равно не может "починить" упавшую базу прямо в методе, поэтому ошибке позволяют всплыть до глобального перехватчика (например, `@ControllerAdvice`).
        

### 4. Исключения и Многопоточность (Классика собеседований)

Раз уж мы говорили про потоки, вот как исключения ведут себя там. Это спрашивают почти всегда.

**Вопрос:** Что будет, если поток выбросит `RuntimeException`, а его никто не поймает?

**Ответ:** Поток **умрет**. JVM выведет StackTrace в `System.err`, но приложение продолжит работать (если есть другие потоки).

**Вопрос:** Как поймать исключение из упавшего потока?

**Ответ:** Через специальный обработчик:

Java

```Java
Thread t = new Thread(() -> { throw new RuntimeException("Бум!"); });
t.setUncaughtExceptionHandler((thread, exception) -> {
    System.out.println("Поток " + thread.getName() + " упал из-за " + exception.getMessage());
});
t.start();
```

**Вопрос с подвохом:** А что будет в пуле потоков (`ThreadPoolExecutor`)?

**Ответ Senior'а:** Зависит от того, как мы отдали задачу в пул!

1. Если через **`executor.execute(Runnable)`**: Исключение убьет рабочий поток. Пул это заметит, выбросит мертвый поток и создаст новый. (Это ресурсоемко).
    
2. Если через **`executor.submit(Callable/Runnable)`**: Ничего не упадет! Пул **проглотит** исключение, сохранит его внутри объекта `Future`, и поток останется жив. Ты узнаешь об ошибке только когда вызовешь `future.get()` — он выбросит `ExecutionException`, обернув оригинальную ошибку.
    
    _(Если разработчик забыл вызвать `.get()`, ошибка просто исчезнет бесследно — это частый баг на проде)._
