Базовая иерархия исключений — это архитектурный фундамент, который определяет, как именно приложение должно реагировать на разные классы сбоев.

Вся система исключений в Java строится вокруг одного родительского класса — **`java.lang.Throwable`**. Только объекты, наследующие этот класс, могут быть переданы в ключевое слово `throw` или пойманы в блоке `catch`.

Вот строгая техническая иерархия и правила работы с каждой ветвью.

### 1. Дерево наследования

Plaintext

```
Throwable
 ├── Error (Неконтролируемые фатальные сбои)
 │    ├── OutOfMemoryError
 │    ├── StackOverflowError
 │    └── NoClassDefFoundError
 │
 └── Exception (Сбои приложения)
      ├── RuntimeException (Непроверяемые / Unchecked)
      │    ├── NullPointerException
      │    ├── IllegalArgumentException
      │    └── IndexOutOfBoundsException
      │
      ├── IOException (Проверяемые / Checked)
      └── SQLException (Проверяемые / Checked)
```

### 2. Разбор ветвей (Как с ними работать)

#### Ветвь A: `Error` (Ошибки JVM)

Это системные сбои на уровне самой виртуальной машины Java.

- **Суть:** Указывают на то, что среда выполнения находится в критическом состоянии и дальнейшая работа программы невозможна или небезопасна.
    
- **Правило архитектуры:** Их **категорически не рекомендуется перехватывать** (писать `catch (Error e)`). Если у приложения закончилась оперативная память (`OutOfMemoryError`), твой код в блоке `catch` с вероятностью 99% тоже не сможет выполниться, так как для его работы JVM потребуется выделить память. Приложение должно упасть, а система мониторинга (или Kubernetes) должна его перезапустить.
    

#### Ветвь B: Проверяемые `Exception` (Checked)

Это классы-наследники `Exception`, но **не** наследующие `RuntimeException`.

- **Суть:** Возникают из-за внешних факторов, неподконтрольных JVM: отсутствие файла на диске, обрыв сетевого соединения, падение базы данных.
    
- **Правило архитектуры:** Компилятор (javac) жестко проверяет их на этапе компиляции. Разработчик обязан либо обернуть опасный код в `try-catch`, либо пробросить исключение выше по стеку через ключевое слово `throws` в сигнатуре метода.
    

#### Ветвь C: `RuntimeException` (Unchecked)

- **Суть:** Это баги в коде (Programming bugs). Обращение к `null`, выход за пределы массива, деление на ноль, передача невалидного аргумента.
    
- **Правило архитектуры:** Компилятор их не проверяет. Писать для них `throws` в сигнатуре метода бессмысленно. Код не должен пытаться восстановиться после `NullPointerException` — код должен быть написан так, чтобы это исключение вообще не возникало (через проверки `if (obj == null)` или `Optional`).
    

### 3. Механика блока `finally` и скрытые баги

Блок `finally` выполняется **всегда**, независимо от того, было выброшено исключение или метод завершился успешно (за исключением ситуации, когда вызван `System.exit()`, убивающий процесс ОС, или при жестком отключении питания).

Но на собеседованиях часто проверяют знание **аномалий перекрытия (Exception Swallowing)**:

Java

```
public int calculate() {
    try {
        throw new RuntimeException("Ошибка бизнес-логики");
    } finally {
        return 42; // АНТИПАТТЕРН!
    }
}
```

**Что произойдет:** Вызов этого метода вернет `42`. Исключение `RuntimeException` будет полностью "проглочено" и стерто из памяти. Оператор `return` (или `throw`) внутри блока `finally` всегда перекрывает любой результат или исключение из блока `try`.

### 4. Try-with-resources и Подавленные исключения (Suppressed)

Для работы с ресурсами (файлами, сокетами, соединениями с БД), которые реализуют интерфейс `AutoCloseable`, в Java 7 добавили синтаксис `try-with-resources`.

**Зачем он нужен на уровне архитектуры?** В классическом `try-catch-finally` при закрытии ресурса в `finally` метод `close()` сам может выбросить исключение. Если и блок `try`, и метод `close()` выбрасывают ошибки, классический код потеряет исходную ошибку из `try`.

Конструкция `try-with-resources` решает это через механизм **Suppressed Exceptions**:

Java

```
try (FileInputStream fis = new FileInputStream("file.txt")) {
    // Если здесь происходит ошибка (Ошибка А)
    fis.read(); 
} // Компилятор неявно вызывает fis.close()
  // Если при закрытии происходит ошибка (Ошибка Б)
```

**Результат:** Метод выбросит "Ошибку А" (главную, из-за которой всё упало). Но "Ошибка Б" не потеряется — JVM добавит её внутрь "Ошибки А" с помощью метода `Throwable.addSuppressed()`. При печати стектрейса ты увидишь обе проблемы.
