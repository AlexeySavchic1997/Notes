Возврат к GC — отличная идея. На собеседовании уровня Middle/Senior не просят просто перечислить сборщики. От тебя ждут понимания **трейдов (компромиссов)**. В инженерии не бывает "идеального" решения, всегда есть цена.

Чтобы звучать профессионально, твой ответ должен опираться на три фундаментальных метрики — так называемый **«Железный треугольник GC»**.

### Часть 1. Основные понятия (Словарь для собеседования)

Любой ответ про выбор GC ты должен начинать с этих трех терминов. Одновременно улучшить все три невозможно — улучшая одно, мы жертвуем другим.

1. **Latency (Задержка / Отклик):** Это длина пауз **Stop-The-World (STW)**. Метрика критически важна для REST API, финансовых систем, онлайн-игр. (Нам важно, чтобы пользователь не ждал ответа по 2 секунды).
    
2. **Throughput (Пропускная способность):** Доля времени процессора, которая тратится на полезную работу приложения (бизнес-логику), а не на сборку мусора. Метрика важна для фоновых задач, пакетной обработки (Batch) и расчета отчетов.
    
3. **Footprint (След в памяти / Накладные расходы):** Сколько оперативной памяти забирает _сам сборщик мусора_ для своих внутренних нужд (хранение графа ссылок, таблиц регионов, очередей).
    

**Дополнительные термины, которыми нужно козырять:**

- **Compaction (Уплотнение / Дефрагментация):** Процесс сдвигания выживших объектов вплотную друг к другу, чтобы убрать "дыры" в памяти.
    
- **Allocation Rate (Скорость аллокации):** Как быстро твой код создает новые объекты (в Мегабайтах в секунду).
    
- **Promotion (Повышение):** Перенос объектов из Молодого поколения (Young) в Старое (Old).
    

### Часть 2. Преимущества и недостатки каждого GC

#### 1. Serial GC (Последовательный)

Использует ровно один поток для сборки мусора.

- **Преимущества:** Минимальный Footprint. Он почти не потребляет память на свои нужды.
    
- **Недостатки:** Долгие STW паузы. Не использует многоядерность (остальные ядра процессора простаивают во время работы GC).
    
- **Когда применять:** На микро-инстансах с 1 ядром CPU и памятью до 200 МБ (например, Serverless-функции AWS Lambda).
    

#### 2. Parallel GC (Сборщик пропускной способности)

До Java 8 был по умолчанию. Использует все ядра процессора, но когда чистит память — полностью останавливает приложение.

- **Преимущества:** **Максимальный Throughput.** Он выполняет работу грязнее, но быстрее всех возвращает процессор приложению.
    
- **Недостатки:** Случаются долгие и непредсказуемые паузы STW (иногда по несколько секунд на больших Heap'ах), когда переполняется Старое поколение (Full GC).
    
- **Когда применять:** Фоновые демоны, генерация отчетов, обработка больших данных (Big Data / Spark). Там, где не важен отклик конкретному пользователю, а важно прожевать миллион записей за минимальное общее время.
    

#### 3. G1 GC (Garbage-First) — Золотая середина

Дефолт начиная с Java 9. Делит память на тысячи мелких регионов.

- **Преимущества:**
    
    - **Предсказуемые паузы:** Ты можешь задать флаг `-XX:MaxGCPauseMillis=200`, и G1 будет стараться (хоть и не гарантирует на 100%) не останавливать приложение дольше этого времени, очищая только самые "мусорные" регионы.
        
    - Параллельная фаза маркировки (поиск мусора происходит одновременно с работой приложения).
        
- **Недостатки:**
    
    - Высокий **Footprint**: G1 вынужден хранить "Remembered Sets" (кто на кого ссылается между регионами), что может отъедать до 10-15% от всего Heap.
        
    - Throughput чуть ниже, чем у Parallel.
        
- **Когда применять:** В 90% современных монолитов и микросервисов с REST API (Heap от 2 ГБ до 16 ГБ).
    

#### 4. ZGC (Современный Ultra-Low Latency)

Дефолт для систем реального времени. Всю тяжелую работу делает конкурентно.

- **Преимущества:**
    
    - **Гарантированный Latency:** Паузы STW **менее 1 миллисекунды**, даже если у тебя Heap размером в 16 Терабайт!
        
    - Справляется с огромными кучами без деградации.
        
- **Недостатки:**
    
    - **Снижение Throughput:** Поскольку GC работает _одновременно_ с приложением, он отбирает часть мощности CPU у бизнес-логики.
        
    - Если твое приложение создает объекты быстрее (Allocation Rate), чем ZGC успевает их конкурентно чистить, наступит "Allocation Stall" — приложение принудительно затормозится, чтобы GC успел доделать работу.
        
- **Когда применять:** Трейдинг, рекламные биржи (AdTech), игровые сервера, где задержка в 100 мс означает потерю денег.
