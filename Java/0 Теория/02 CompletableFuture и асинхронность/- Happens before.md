
Спецификация Java Memory Model (JMM) описывает `Happens-Before` не как физический процесс, а как **строгий математический контракт**. Если действие А `Happens-Before` действия Б, JMM гарантирует: результат действия А будет виден действию Б, и А выполнится до Б.

Помимо `volatile` (Volatile Variable Rule) и `synchronized` (Monitor Lock Rule), JLS (Java Language Specification) определяет еще несколько жестких правил. Для Senior-разработчика критически важно понимать их, чтобы не расставлять лишние блокировки там, где спецификация уже всё гарантирует.

## 1. Program Order Rule (Порядок выполнения в одном потоке)

Каждое действие в потоке `Happens-Before` каждого последующего действия в этом же потоке. Это кажется очевидным, но здесь кроется нюанс: процессор и JIT-компилятор **имеют право переупорядочивать инструкции** (Instruction Reordering), если это не меняет конечный результат выполнения текущего потока (_as-if-serial semantics_). Связь `Happens-Before` здесь означает лишь логическую видимость, а не физическую последовательность тактов CPU.

## 2. Thread Start Rule (Правило старта потока)

Вызов `Thread.start()` гарантированно `Happens-Before` любой инструкции внутри запускаемого потока (`run()`).

**Архитектурный профит:** Если основной поток подготавливает данные (создает объекты, заполняет коллекции, пишет в обычные переменные), а затем вызывает `start()` для рабочего потока, тебе **не нужно** делать эти переменные `volatile` или использовать `synchronized`. Рабочий поток гарантированно увидит все данные, инициализированные до вызова `start()`.

## 3. Thread Termination Rule (Правило завершения потока)

Любая инструкция внутри потока `Happens-Before` момента, когда другой поток обнаружит его завершение (например, через успешный возврат из `Thread.join()` или метод `Thread.isAlive() == false`).

**Архитектурный профит:** Когда рабочий поток завершает сложные расчеты и сохраняет результат в обычное несинхронизированное поле, основной поток, вызвавший `join()`, гарантированно увидит этот результат без кэш-промахов. RAM будет синхронизирована.

## 4. Transitivity (Транзитивность)

Если _A Happens-Before B_, и _B Happens-Before C_, то _A Happens-Before C_. Это фундамент, на котором строится знаменитый трюк **Piggybacking (Езда на закорках)**.

Если поток записывает данные в обычные переменные, а затем делает запись в **одну** `volatile` переменную, то другой поток, прочитав эту `volatile` переменную, автоматически получает "бесплатную" видимость всех обычных переменных. Тебе не нужно делать все поля класса `volatile` — достаточно сделать таким только последнее поле (флаг готовности).

## 5. Гарантии пакета java.util.concurrent (Скрытый Happens-Before)

Высокоуровневые классы JUC под капотом используют `volatile` и CAS, поэтому спецификация официально закрепляет за ними барьеры памяти:

- **Коллекции:** Помещение объекта в любую конкурентную коллекцию (например, `ConcurrentHashMap.put()`) `Happens-Before` его извлечения (`get()`) другим потоком.
    
- **Синхронизаторы:** Успешный вызов `CountDownLatch.countDown()` `Happens-Before` выхода из `latch.await()` в другом потоке.
    
- **Futures/Executors:** Передача задачи в `ExecutorService.submit()` `Happens-Before` начала ее выполнения. А завершение задачи `Happens-Before` успешного возврата из `Future.get()`.
    

> **Главный инсайт:** `Happens-Before` — это граф направленных связей видимости памяти. Если между потоком, пишущим данные, и потоком, читающим их, нельзя проложить непрерывный путь по этим правилам, возникает **Data Race**.
