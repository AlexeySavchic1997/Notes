Давай разберём Git «по косточкам» именно в реалиях командной Java-разработки. Git — это не просто хранилище кода, это инструмент управления параллельной работой всей команды. В Java-проектах (особенно с Maven/Gradle и фреймворками вроде Spring) возникают свои специфические ситуации.

Вот главные проблемы, с которыми ты столкнёшься, как их решать и как правильно читать историю.

### 1. Как читать логи и понимать, что происходит

Когда что-то сломалось, первое правило — посмотреть историю. Обычный `git log` выдаёт сплошную простыню текста, в которой сложно ориентироваться.

**Как читать лог правильно:** Используй команду (или настрой её как алиас `git lg`): `git log --oneline --graph --all`

- **Что она даёт:** Показывает дерево коммитов (граф) с линиями. Чётко видно, где ветки расходились (кто-то ушёл делать фичу) и где сливались (`merge`).
    
- **Как читать хэши:** Каждому коммиту присваивается уникальный SHA-1 хэш (например, `a1b2c3d`). Это абсолютный адрес коммита.
    
- **Указатель `HEAD`:** Это то, где ты находишься прямо сейчас. Если написано `HEAD -> feature-login`, значит, ты на последнем коммите этой ветки. Если `HEAD` указывает на конкретный хэш, а не на имя ветки — у тебя «оторванная голова» (detached HEAD), и новые коммиты могут потеряться.
    

**Спасательный круг — `git reflog`:** Если ты случайно удалил нужную ветку или сделал кривой `reset`, `git reflog` покажет журнал _твоих действий_ в локальном репозитории (даже перемещения между ветками и отменённые коммиты). Ты всегда можешь скопировать хэш оттуда и откатиться назад.

### 2. Главная боль: Конфликты слияния (Merge Conflicts)

Конфликт возникает, когда два разработчика изменили одну и ту же строчку кода, и Git просит тебя (как человека) принять решение.

В Java-проектах конфликты чаще всего бьют по трём местам:

1. **Исходный код (`.java`)**: Коллега переименовал метод, а ты в своей ветке добавил в этот же метод новую логику.
    
2. **Сборщики (`pom.xml` для Maven или `build.gradle`)**: Два человека одновременно добавили разные зависимости в конец блока `dependencies`.
    
3. **Конфиги (`application.yml` / `.properties`)**: Добавлены разные настройки приложения на одних и тех же строках.
    

**Как решать конфликты как профи:**

1. Git останавливает процесс и пишет `CONFLICT`. Открой IDE (например, IntelliJ IDEA делает это великолепно через окно _Merge Conflicts_ -> _Resolve_).
    
2. В сыром файле конфликт выглядит так:
    
    Java
    
    ```
    <<<<<<< HEAD
    public void processPayment(Order order) { // Твоя текущая версия
    =======
    public void processPayment(Order order, boolean useBonus) { // Версия из ветки коллеги
    >>>>>>> feature/bonus-system
    ```
    
3. Тебе нужно оставить правильный вариант (или объединить логику), удалив маркеры `<<<<<<<`, `=======`, `>>>>>>>`.
    
4. **Специфика Java:** Обязательно пересобери проект (`mvn clean install` или `gradlew build`), чтобы убедиться, что код компилируется. Очень часто конфликт разрешён текстуально, но синтаксически ломает импорты или вызовы методов.
    
5. Выполни `git add <файл>` и заверши всё `git commit`.
    

### 3. Проблема: "Я накосячил в последнем коммите"

**Ситуация А: Забыл добавить файл или опечатался в комментарии.**

- **Решение:** `git commit --amend`
    
- Добавляет изменения к предыдущему коммиту. _Важно:_ не делай этого, если ты уже отправил коммит на сервер (`git push`), иначе сломаешь историю коллегам.
    

**Ситуация Б: Сделал коммит, но понял, что пошёл не туда. Хочу отменить коммит, но сохранить написанный код.**

- **Решение:** `git reset HEAD~1`
    
- Откатывает историю на 1 шаг назад, но оставляет изменённые файлы у тебя в редакторе (в `Working Directory`).
    

**Ситуация В: Код уже залит в ветку `main` на сервере, и он роняет прод.**

- **Решение:** `git revert <hash>`
    
- Создаёт _новый_ коммит, который зеркально отменяет действия ошибочного. Это единственный безопасный способ отката для общих веток, так как он не переписывает прошлую историю.
    

### 4. Проблема: "Мусор" в репозитории и игнорирование файлов

Новички часто случайно коммитять скомпилированные классы (`.class`), папку `target/`, логи или, что ещё хуже, пароли к базе данных из `application-dev.yml`.

**Как исправить, если уже закоммитил:** Если папка `target/` улетела в репозиторий, простое добавление её в `.gitignore` постфактум **не поможет** (Git уже следит за ней). Нужно удалить её из индекса Git: `git rm -r --cached target/` Затем сделай коммит. Файлы удалятся из системы контроля версий, но физически останутся у тебя на диске.

### 5. Холивар: Merge против Rebase (расхождение веток)

Когда ты неделю писал код в ветке `feature`, а `main` ушёл далеко вперёд (коллеги слили свои задачи), тебе нужно подтянуть свежие изменения из `main` к себе.

- **`git merge main` (Слияние)**:
    
    - _Как работает:_ Берёт `main` и вливает в твою ветку. Создаётся специальный "merge commit" (ромбик на графе).
        
    - _Плюсы:_ Безопасно, сохраняет реальную хронологию.
        
    - _Минусы:_ История становится похожей на спагетти, если разработчиков много.
        
- **`git rebase main` (Перебазирование)**:
    
    - _Как работает:_ Отрывает твои новые коммиты, перематывает твою ветку до конца свежего `main` и "приклеивает" твои коммиты поверх.
        
    - _Плюсы:_ Идеально прямая и чистая история (тот самый `git log` читается как книга).
        
    - _Минусы:_ Переписывает историю. Если возникнет конфликт, тебе придётся решать его на _каждом_ твоём коммите по очереди, а не один раз, как при мердже.

Давай разберём под капотом, как это хранится и почему Git точно знает, что именно нужно сохранить, а где объявить конфликт.

### 1. Как Git хранит данные (Слепки, а не патчи)

Многие думают, что коммит — это «я добавил строчку 5 в файл A». На самом деле, под капотом Git — это простая ключ-значение база данных, которая хранит три типа объектов:

- **Blob (Блоб):** Это просто содержимое файла. Если у тебя есть файл `UserService.java`, Git берёт его текст, сжимает, вычисляет SHA-1 хэш от этого текста и сохраняет под этим хэшем. Имя файла блобу неизвестно, только контент.
    
- **Tree (Дерево):** Это папка. Она связывает имена файлов с хэшами блобов.
    
- **Commit (Коммит):** Указатель на корневое дерево (то есть на состояние всего проекта в этот момент), плюс метаданные: кто автор, когда сделано, и **какой коммит был предыдущим (родитель)**.

### 2. Почему Git не затирает чужой код: Магия 3-Way Merge

Представь ситуацию:

1. Вы с коллегой отпочковались от ветки `main` (коммит **Base**).
    
2. Коллега залил свои изменения в `main` (коммит **Theirs**).
    
3. Ты пытаешься влить свежий `main` в свою ветку (коммит **Mine**).
    

Если бы Git сравнивал только **Mine** и **Theirs** (двухстороннее сравнение), он бы сошёл с ума. У коллеги в строке 10 написано `int a = 5;`, а у тебя `int a = 10;`. Как машине понять, кто из вас прав? Может, ты изменил `a` на `10`, а коллега вообще эту строку не трогал? Или наоборот?

Вот тут Git и использует **Base** (общего предка) — тот самый слепок, от которого вы оба начали работу.

Git берёт файл из трёх точек (Base, Mine, Theirs) и проходит по нему построчно, задавая себе простые вопросы:

|Состояние Base|У коллеги (Theirs)|У тебя (Mine)|Что делает Git|
|---|---|---|---|
|`String status;`|`String status;`|**`String orderStatus;`**|**Берёт твоё.** Коллега не трогал строку со времён Base, а ты изменил. Твоё изменение важнее.|
|`String status;`|**`String paymentStatus;`**|`String status;`|**Берёт коллегино.** Ты не трогал строку, а он изменил. Git безопасно добавляет его код тебе.|
|`String status;`|`String paymentStatus;`|`String orderStatus;`|💥 **КОНФЛИКТ.** Вы оба изменили одну и ту же строку по-разному по сравнению с Base.|

### 3. Почему простое "перезаписывание" — это катастрофа

Если бы Git просто накатывал твои файлы поверх (как при копировании папок в Windows), произошло бы следующее: Допустим, в Base файле была функция `calculateTax()`. Твой коллега в своей ветке нашёл там баг и исправил его. Ты в своей ветке этот файл вообще не открывал, у тебя там всё ещё старая версия с багом (ведь ты делаешь фичу в другом классе). Если при слиянии твой "слепок" просто перезапишет чужой, ты **молча уничтожишь багфикс коллеги**, вернув старый код.

Именно благодаря тому, что Git смотрит на Base, он видит: «Ага, пользователь тут ничего не менял по сравнению с Base, а вот его коллега — менял. Значит, я должен взять версию коллеги, даже если пользователь вливает код в _свою_ ветку».

А как Git понимает, что я переименовал файл?

Yes

Если Git не отслеживает файлы, а только их содержимое (блобы), как он понимает, что я не удалил один файл и создал другой, а просто переименовал его (например, через git mv)?

Это один из самых изящных механизмов в Git! Ты абсолютно прав: Git не сохраняет метаданные вида «файл A был переименован в файл B». Если ты сделаешь `git mv old.java new.java`, под капотом Git запишет это просто как **удаление `old.java`** и **добавление `new.java`**.

Но когда ты вводишь `git status`, `git log` или делаешь слияние, Git радостно сообщает: `renamed: old.java -> new.java`. Как он это понимает?

Ответ кроется в **эвристике (heuristic rename detection)**, которая вычисляется _на лету_.

### Как работает алгоритм обнаружения переименований

Когда Git нужно показать тебе изменения (например, при `git diff` или `git status`), он проходит через несколько шагов:

#### Шаг 1: Точное совпадение хэшей (100% Rename)

Как мы уже знаем, файлы в Git хранятся в виде объектов _Blob_ (содержимое), у которых есть SHA-1 хэш.

1. Git собирает два списка: все **удалённые** файлы в этом коммите и все **новые** (добавленные) файлы.
    
2. Он смотрит на хэши их блобов.
    
3. Если ты сделал `git mv old.java new.java` и _не менял_ ни единой строчки кода внутри, хэш содержимого остаётся абсолютно тем же.
    
4. Git видит: удалился файл с хэшем `a1b2c3d` (имя `old.java`) и появился файл с точно таким же хэшем `a1b2c3d` (имя `new.java`).
    
5. **Бинго!** Git моментально связывает их и объявляет переименованием. Это вычисляется за миллисекунды, так как сравниваются только короткие строки хэшей, а не сам текст.
    

#### Шаг 2: Поиск похожих файлов (Similarity Index)

Но что, если ты переименовал файл **и** немного изменил в нём код (например, переименовал класс внутри `new.java`)? Хэши блобов теперь будут разными!

Здесь включается более сложный алгоритм:

1. Для каждого добавленного файла, который не нашёл точной пары, Git начинает побайтово сравнивать его содержимое со всеми удалёнными файлами из первого списка.
    
2. Он высчитывает **Индекс схожести (Similarity Index)**.
    
3. По умолчанию, если файлы совпадают более чем на **50%**, Git решает: «Окей, это не два разных файла, это один переименованный файл, в котором немного поправили код».
    
4. В логах ты увидишь что-то вроде `similarity index 78% / rename from old.java / rename to new.java`.
    

_Кстати, этот порог в 50% можно настраивать. Если вызвать `git diff -M70%`, Git будет считать файлы переименованными только если они совпадают на 70%._

### Почему такой подход лучше?

Архитектор Git, Линус Торвальдс, специально отказался от явного отслеживания переименований (как это было в SVN), и вот почему:

1. **Меньше багов:** Разработчики часто копируют файлы, удаляют старые, создают новые в IDE в обход консоли. Если бы Git полагался на строгую команду `git mv`, он бы постоянно терял историю тех файлов, которые переименовали через файловый менеджер (ведь IDE просто делает `rm` и `add`). Эвристика же найдет переименование, _как бы ты его ни сделал_.
    
2. **Обнаружение копий:** Точно такой же алгоритм позволяет Git находить дубликаты. Если ты скопируешь `Template.java` в `Report.java`, Git заметит, что добавился новый файл с таким же блобом, и при настройке `-C` (find copies) покажет тебе, что это копия.
    
3. **Независимость истории:** Имена файлов хранятся только в объектах `Tree` (деревьях папок). Коммит просто указывает на корень дерева. Это делает структуру данных Git невероятно простой и надежной, не засоренной метаданными о перемещениях.

А как быть с большими проектами? Git не тормозит?

Yes

Если Git каждый раз при diff или merge сравнивает содержимое всех удалённых файлов со всеми добавленными, разве это не вызывает дикие тормоза на огромных репозиториях, где за коммит могут переименовать сотни файлов?

Отличный вопрос! Если бы Git делал это «в лоб», сравнивая каждый удалённый файл с каждым добавленным (алгоритм сложности O(N×M)), то переименование 1000 файлов повесило бы компьютер на несколько минут, так как пришлось бы сделать 1 000 000 побайтовых сравнений файлов.

Но Линус Торвальдс и команда разработчиков Git предвидели это. Алгоритм обнаружения переименований — это не просто тупой перебор. Это **многоуровневая система фильтрации и оптимизаций**, которая отсекает 99% работы ещё до того, как начнёт читать содержимое файлов.

Вот как Git избегает тормозов:

### 1. Точные совпадения хэшей решаются мгновенно (O(N))

Как мы обсуждали на предыдущем шаге, если файл был переименован без изменений кода, его SHA-1 хэш остаётся прежним. Сравнение двух списков хэшей (например, через хэш-таблицы) занимает доли секунды даже для десятков тысяч файлов. Как только Git находит точное совпадение хэшей, он **убирает эти файлы из очереди на проверку**. В большинстве случаев (например, при перемещении целой папки в другое место) 95% файлов отсекаются на этом этапе.

### 2. Фильтрация по размеру файла

Для тех файлов, которые всё-таки изменились (хэши не совпали), Git начинает готовить матрицу сравнений содержимого. Но прежде чем побайтово сравнивать файлы, Git смотрит на их размер. Если старый файл весил 2 КБ, а новый весит 15 МБ, очевидно, что это не переименование. Git вообще не будет сравнивать их содержимое.

### 3. Сравнение базовых имен (Basename Optimization)

Если ты перенёс файл из `src/utils/math.js` в `lib/math.js` и немного изменил код, хэши не совпадут. Но имя файла (`math.js`) осталось прежним. В новых версиях Git сначала проверяет добавленные и удалённые файлы с одинаковыми именами. Если совпадение найдено и содержимое похоже, они исключаются из дальнейшего полного перебора.

### 4. Жёсткий лимит `renameLimit` (Предохранитель)

Даже со всеми оптимизациями может возникнуть ситуация, когда разработчик массово отрефакторил проект: переименовал 5000 файлов и в каждом изменил лицензионный заголовок. Хэши разные, размеры похожие. Тут матрица перебора может стать огромной.

У Git есть встроенный аппаратный предохранитель: настройка `diff.renameLimit` (и `merge.renameLimit`). По умолчанию этот лимит долгое время был равен **400** (в современных версиях Git его подняли до 1000+).

- Как это работает? Git считает размер матрицы: `Количество удалённых файлов × Количество добавленных файлов`.
    
- Если это число превышает лимит (или если файлов слишком много), Git **просто сдаётся**. Он не будет искать переименования, чтобы не тормозить. Он честно скажет в логе: «Я удалил эти 500 файлов и добавил вот эти 500 файлов. Искать переименования не буду, слишком долго».
    
- При слиянии (merge) это иногда вызывает конфликты, потому что Git решает, что старый файл удалён, а новый создан с нуля.
    

_Если ты видишь предупреждение `warning: too many files, skipping inexact rename detection`, ты можешь вручную увеличить лимит командой: `git config merge.renameLimit 999999` (если у тебя мощный процессор)._

Конфликт слияния (merge conflict) — это не ошибка и не поломка. Это абсолютно штатная ситуация. Конфликт возникает ровно в тот момент, когда алгоритм Git (тот самый 3-way merge) упирается в ситуацию, где математическая логика заканчивается и начинается **человеческая (бизнес) логика**. Git — очень осторожная система. Он отказывается угадывать, чтобы не сломать код, останавливает процесс и просит человека принять решение.

Вот 4 основные ситуации, из-за которых Git «поднимает лапки вверх» и объявляет конфликт:

### 1. Взаимоисключающие изменения одних и тех же строк (Классика)

Два разработчика в своих параллельных ветках изменили один и тот же участок кода, причём сделали это по-разному.

- **Пример в Java:** В базовой версии на строке 15 было написано `int timeout = 10;`. Ты в ветке `feature-A` поменял это на `int timeout = 30;` (увеличил таймаут). А твой коллега в ветке `feature-B` на той же 15-й строке написал `int timeoutLimit = 10;` (просто переименовал переменную). При попытке слияния Git видит, что базовой строки больше нет, а вместо неё две новые. Какая из них правильная? Git не знает. Конфликт.
    

### 2. Добавление нового кода в одно и то же место (Проблема списков)

Вы с коллегой не трогали старый код, но оба добавили новые строки в одну и ту же позицию в файле (например, в самый конец класса или массива).

- **Пример в Java:** Это вечная боль файлов `pom.xml` (Maven) или блока импортов вверху `.java` файла. Ты добавил зависимость `Spring Security` в самый конец списка `dependencies`. Коллега в своей ветке добавил `Lombok` тоже в самый конец списка. Git не понимает, в каком порядке их теперь вставить, чья зависимость должна быть выше, а чья ниже, и выдаёт конфликт.
    

### 3. Изменение файла против его удаления (Conflict: Modify/Delete)

Один разработчик активно редактирует файл, а второй в параллельной ветке решает, что этот файл больше не нужен (например, в рамках рефакторинга), и удаляет его.

- **Пример:** Ты потратил день, исправляя баги и дописывая методы в класс `OldPaymentProcessor.java`. А в это время лид-архитектор в ветке `main` вообще удалил этот класс, так как перевёл систему на новый API. При слиянии Git впадает в ступор: оставить твой свежеисправленный код (воскресив удалённый файл) или согласиться с удалением, навсегда уничтожив твой новый код?
    

### 4. Столкновение бинарных файлов

Git умеет умно (построчно) объединять только текстовые файлы. Если вы оба измените бинарный файл, Git даже не будет пытаться их "склеить", потому что для него это просто непрозрачный поток байтов.

- **Пример:** Вы с дизайнером одновременно обновили `logo.png` в ресурсах проекта. Или два разработчика случайно закоммитили обновлённый скомпилированный файл `app.jar`. Конфликт гарантирован: Git предложит тебе выбрать либо _целиком_ твой файл, либо _целиком_ файл коллеги.

Когда происходит конфликт, Git буквально ломает твой исходный код, вставляя в него специальные текстовые маркеры. Он делает это намеренно: если ты попытаешься скомпилировать такой Java-файл, компилятор выдаст синтаксическую ошибку. Это гарантия того, что конфликт не пройдёт незамеченным.

Java

```
public class PaymentService {

    public void processPayment(Order order) {
<<<<<<< HEAD
        // Твои изменения (Current Change)

=======
        // Изменения коллеги (Incoming Change)
        log.info("Processing international payment...");
```

### Анатомия маркеров конфликта

Git делит конфликтный блок на три части:

1. `<<<<<<< HEAD` — Начало блока с **твоим кодом**. `HEAD` означает твоё текущее состояние (ветка, в которой ты находишься).
    
2. `=======` — **Разделитель**. Выше него — твоё, ниже него — то, что прилетело из другой ветки.
    
3. `>>>>>>> feature/international-payments` — Конец блока и имя ветки, из которой пришли **чужие изменения**.
    

### Как это разрешать технически

У тебя есть два пути: "суровый" (через блокнот) и "современный" (через IDE).

#### Способ 1: Хардкорный (Руками в редакторе)

Тебе нужно превратить этот кусок текста обратно в валидный Java-код. Ты должен:

1. Оставить нужный код (твой, чужой или вообще написать третий, объединив их логику).
    
2. **Обязательно удалить** все строки с маркерами `<<<<<<<`, `=======` и `>>>>>>>`.
    

Например, если ты решил, что код коллеги правильнее (так как добавились налоги), ты просто стираешь верхнюю половину и маркеры:

#### Способ 2: Как делают профи (В IDE, например, IntelliJ IDEA)

Современные IDE прячут от тебя сырые текстовые маркеры и предоставляют удобный графический инструмент — **3-Way Merge Tool**. Когда ты нажимаешь "Resolve Conflicts", открывается окно из трёх колонок:

- **Слева (Local/Current):** Твой текущий код.
    
- **Справа (Remote/Incoming):** Код коллеги.
    
- **По центру (Result):** Итоговый файл, который пойдёт в коммит.
    

По бокам от строк есть стрелочки `>>` и `<<`. Тебе нужно просто кликать на них:

- Нажал `>>` слева — твой код перенёсся в центр.
    
- Нажал `<<` справа — код коллеги перенёсся в центр.
    
- Можно нажать обе — тогда в центре окажутся обе строчки (сначала твоя, потом его). Часто в центре приходится дописывать код руками, чтобы склеить две логики (например, объединить разные вызовы методов).
    

### Важный нюанс для Java-разработчиков!

В скриптовых языках (Python, JS) после удаления маркеров конфликт считается разрешённым. В Java это не так!

Текстуальное разрешение конфликта — это только половина дела. Допустим, ты выбрал версию коллеги с методом `gateway.chargeWithTaxes()`. Но ты в своей ветке вообще не импортировал этот `gateway` или у тебя старая версия интерфейса без этого метода. Текст файла будет выглядеть чисто, маркеров не будет, но **проект не скомпилируется**.

Поэтому золотое правило разрешения конфликтов в Java:

1. Удалил маркеры / склеил код в IDE.
    
2. **Обязательно запусти сборку:** `mvn clean compile` или `gradlew build`.
    
3. Убедись, что IDE не подсвечивает красным потерянные импорты.

Чтобы сделать это грамотно, нужно чётко понимать разницу между `git fetch` и `git pull`, а также концепцию «удалённых веток-призраков».

### 1. В чём разница: Fetch против Pull

- **`git fetch` (Безопасная разведка):** Эта команда связывается с сервером (например, GitHub или GitLab), скачивает все новые коммиты, файлы и ветки, которые там появились, и сохраняет их в твоей локальной базе Git. **Но она вообще не трогает твои рабочие файлы и твою текущую ветку.** Она просто обновляет твоё _знание_ о том, что происходит на сервере.
    
- **`git pull` (Слепое применение):** Это составная команда. Под капотом она делает ровно две вещи: `git fetch` + сразу же `git merge`. Она скачивает изменения с сервера и моментально пытается влить их в ту ветку, на которой ты сейчас находишься.
    

### 2. Главный секрет: Ветки `origin/main`

Когда ты клонируешь репозиторий, Git создаёт у тебя на компьютере скрытые копии серверных веток. Они называются _remote-tracking branches_ (отслеживающие ветки) и имеют префикс `origin/` (например, `origin/main`).

- Твой локальный `main` — это просто твоя личная песочница. Если ты не переключался на неё месяц, она отстаёт на месяц.
    
- Твой `origin/main` — это слепок того, как выглядел `main` на сервере в ту секунду, когда ты в последний раз делал `git fetch` или `git pull`.
    

Многие новички делают **4 лишних шага**: переключаются на локальный `main` (`git checkout main`), делают там `git pull`, возвращаются в свою ветку (`git checkout feature`) и делают `git merge main`. Это работает, но локальный `main` тебе для этой задачи вообще не нужен!

Тебе нужен свежий серверный код, и получить его можно быстрее и чище.

### Почему не сделать просто `git pull origin main`?

Команда `git pull origin main` (выполненная из твоей ветки `feature`) сделает то же самое — скачает `main` и сразу сольёт его с твоей веткой.

Многие так и делают для экономии времени, но у этого подхода есть минусы:

1. **Эффект неожиданности:** Ты запускаешь команду, и твои файлы внезапно меняются (или всё покрывается конфликтами), а ты даже не успел посмотреть, что именно там изменилось на сервере.
    
2. **Риск случайного ребейза:** Если у тебя локально настроен `pull.rebase = true`, `git pull` молча начнёт переписывать историю твоей ветки поверх `main`, к чему ты можешь быть не готов.
    

Делая `fetch`, ты всегда можешь остановиться перед шагом 2 и посмотреть, что именно написали коллеги, выполнив `git log origin/main` или `git diff HEAD..origin/main`. Разделение разведки (`fetch`) и атаки (`merge`) делает твою работу с Git абсолютно осознанной.

Главный инструмент для этого — команда `git diff`. Давай разберём, как читать эти изменения по шагам: от общего обзора до поштучного разбора строк.

### 1. Обзор: Какие вообще файлы изменились?

Читать портянку кода на 500 строк в консоли — плохая идея. Для начала тебе нужно понять масштаб трагедии: какие файлы затронули коллеги.

Используй команду: `git diff --name-status HEAD..origin/main`

- **Что она покажет:** Только список файлов и их статус (M - изменён, A - добавлен, D - удалён).
    
- **Пример вывода:**
    
    Plaintext
    
    ```
    M       src/main/java/com/app/PaymentService.java
    A       src/main/java/com/app/dto/Transaction.java
    D       src/main/java/com/app/utils/OldHelper.java
    ```
    

Ещё один удобный вариант — статистика в виде гистограммы: `git diff --stat HEAD..origin/main` Он покажет, сколько строк в каждом файле добавлено (зелёные плюсы) и удалено (красные минусы).

### 2. Детали: Как посмотреть конкретный код

Если ты видишь в списке файл, который ты тоже редактировал (например, `PaymentService.java`), тебе нужно посмотреть, что именно там изменилось.

Используй команду с указанием конкретного файла: `git diff HEAD..origin/main -- src/main/java/com/app/PaymentService.java`

**Как читать вывод Diff:**

- Строки, которые начинаются с `-` (обычно красные), — это код, которого **нет** в `origin/main`, но он есть у тебя.
    
- Строки, которые начинаются с `+` (обычно зелёные), — это новый код из `origin/main`, который прилетит к тебе при мердже.
    

> **Важно про порядок `HEAD..origin/main`:** Эта запись означает: «Покажи мне, что нужно сделать с моим кодом (`HEAD`), чтобы он стал таким же, как на сервере (`origin/main`)». Поэтому добавленный на сервере код будет с плюсом. Если ты напишешь наоборот: `git diff origin/main..HEAD`, то плюсами будет подсвечен _твой_ новый код относительно сервера.

### 3. Как посмотреть смысл изменений, а не только код

Иногда диффа мало. Коллега переписал метод, но зачем? Посмотреть историю коммитов, которые прилетят к тебе при слиянии, можно так: `git log HEAD..origin/main --oneline` Эта команда покажет список сообщений коммитов, которые есть в `origin/main`, но которых ещё нет в твоей ветке. Ты сразу поймёшь контекст: "Ага, Вася закоммитил 'Fix timeout issues', значит он трогал таймауты".

### 1. Почему `develop`, а не `main`? (Модель Gitflow)

В простых проектах (GitHub Flow) есть только `main` — это и рабочий код, и продакшен. В больших энтерпрайз-проектах вводится строгое разделение:

- **`main` (или `master`)**: Это святая святых. Код здесь должен на 100% соответствовать тому, что прямо сейчас крутится на "боевых" серверах (в проде). Сюда нельзя вливать полуготовые фичи.
    
- **`develop`**: Это главная интеграционная ветка. Сюда разработчики сливают свои готовые задачи. Когда в `develop` накапливается достаточно фич для нового релиза, он тестируется и только потом целиком вливается в `main`.
    

### 2. Почему мы не сливаем код в локальный `main` / `develop`?

Многие новички пытаются сделать так: переключиться на свой локальный `main`, влить туда свою фичу (`git merge feature`), а потом отправить всё на сервер (`git push`).

В реальной компании этот план провалится на этапе `push`. Главные ветки (`main` и `develop`) на корпоративных серверах (GitLab, Bitbucket, GitHub) **защищены (protected)**. Сервер просто отклонит твой пуш с ошибкой `Push rejected`, потому что напрямую "пушить" в эти ветки запрещено правилами безопасности.

### 3. Как выглядит правильный процесс (Pull Request / Merge Request)

Вся суть современной командной работы строится вокруг **код-ревью**. Твоя задача — не влить код в главную ветку самостоятельно, а **подготовить свою ветку так, чтобы сервер смог её влить безопасно** после одобрения коллег.

Правильный флоу выглядит так:

1. Ты работаешь в своей ветке `feature-login`.
    
2. Кто-то другой слил свою задачу в серверный `develop`.
    
3. Ты делаешь `git fetch origin`.
    
4. Ты вливаешь серверные изменения в свою ветку: `git merge origin/develop`.
    
5. Ты локально решаешь все конфликты (если они есть) и проверяешь, что проект компилируется.
    
6. Ты делаешь `git push origin feature-login` (отправляешь свою обновленную ветку на сервер).
    
7. В веб-интерфейсе ты создаёшь **Pull Request (PR)** из твоей `feature-login` в серверный `develop`.
    

Таким образом, локальный `main` или локальный `develop` тебе практически не нужны (ты можешь вообще их удалить у себя на компьютере). Ты всегда взаимодействуешь напрямую со связкой: **твоя рабочая ветка + слепок сервера (`origin/develop`)**.

### Что такое `origin`?

`origin` — это просто переменная (ярлык), в которой хранится URL-адрес удалённого сервера. Когда ты делаешь `git clone [https://github.com/company/project.git](https://github.com/company/project.git)`, Git думает: _"Мне лень каждый раз заставлять пользователя печатать эту длинную ссылку, назову-ка я этот сервер словом `origin`"_.

Ты можешь назвать сервер как угодно (например, `git fetch myserver`), но `origin` — это стандарт по умолчанию.

### Что такое `origin/main` и `origin/develop`?

А вот это как раз те самые **скрытые слепки (remote-tracking branches)**, о которых я говорил. `origin` отслеживает **вообще все** ветки, которые есть на сервере.

Если на сервере есть ветки `main`, `develop` и `feature-auth`, то после скачивания у тебя на компьютере в скрытой памяти появятся:

- `origin/main`
    
- `origin/develop`
    
- `origin/feature-auth`
    

Они лежат у тебя на жестком диске. Ты не можешь в них напрямую писать код (не можешь сделать `git checkout origin/main` и начать программировать), они существуют только для чтения, чтобы ты мог сравнить свой код с тем, что было на сервере во время последней синхронизации.

### Разница между командами `fetch` и `pull`

Теперь давай разберёмся, что именно скачивается при разных командах.

|Команда|Что именно она делает|
|---|---|
|`git fetch` (без аргументов)|Идёт на сервер `origin` и скачивает обновления для **ВСЕХ** веток, которые там есть. Обновляет твои `origin/main`, `origin/develop`, `origin/feature-auth` и т.д. Твои локальные рабочие ветки не трогает.|
|`git fetch origin develop`|Идёт на сервер и скачивает обновления **только** для ветки `develop`. Обновляет скрытый указатель `origin/develop`. Остальное не трогает. (Полезно на гигантских проектах для экономии времени).|
|`git pull` (без аргументов)|Делает `git fetch` для той ветки, в которой ты сейчас находишься, а затем **автоматически делает `git merge`**, вливая этот скачанный код прямо в твою рабочую директорию.|
|`git pull origin develop`|Скачивает с сервера ветку `develop` и **моментально вливает её в твою ТЕКУЩУЮ ветку** (даже если ты сидишь в `feature-login`).|

### Резюме: как это использовать?

1. Когда ты утром приходишь на работу, ты просто пишешь **`git fetch`** (или `git fetch origin` — это одно и то же по умолчанию). Git скачает все изменения коллег по всем веткам и обновит твои скрытые `origin/*` указатели.
    
2. Затем, если тебе нужно подтянуть в свою задачу изменения из `develop`, ты делаешь **`git merge origin/develop`**.
    

Эта двухходовочка даёт тебе полный контроль и защищает от сюрпризов, которые может преподнести `git pull`.
