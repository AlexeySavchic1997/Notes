Аннотация `@Transactional` — это, пожалуй, самая используемая и одновременно самая неправильно понимаемая аннотация в Spring. На собеседованиях уровня Middle/Senior вопросы по ней задают в 100% случаев, потому что ошибки в транзакциях стоят бизнесу реальных денег.

Чтобы понять `@Transactional`, нужно перестать воспринимать ее как магию и посмотреть на то, как она работает на уровне байт-кода и прокси-объектов.

### 1. Как это работает под капотом (Магия AOP Прокси)

Когда Spring видит класс с аннотацией `@Transactional`, он **не отдает** этот класс другим сервисам. Вместо этого он на лету (через библиотеку CGLIB или JDK Dynamic Proxies) генерирует класс-обертку (Proxy), который наследуется от твоего класса.

Если написать псевдокод того, что делает этот Proxy, он будет выглядеть так:

Java

```
// Сгенерированный Spring-ом прокси-класс
public class UserServiceProxy extends UserService {
    
    private final TransactionManager txManager;
    private final UserService target; // Твой реальный класс

    @Override
    public void createUser() {
        // 1. Берем соединение (Connection) из пула (HikariCP)
        // 2. Отключаем автокоммит: connection.setAutoCommit(false);
        TransactionStatus status = txManager.getTransaction(new DefaultTransactionDefinition());
        
        try {
            // 3. Вызываем реальный метод с бизнес-логикой
            target.createUser(); 
            
            // 4. Если всё ок — фиксируем в БД
            txManager.commit(status); 
        } catch (RuntimeException | Error e) {
            // 5. Если упало Unchecked исключение — откатываем!
            txManager.rollback(status);
            throw e;
        }
    }
}
```

**Важный архитектурный вывод:** Spring не управляет базой данных. Spring управляет _соединением_ (Connection) с базой данных на уровне JDBC.

### 2. Главная ловушка: Правила отката (Rollback Rules)

Посмотри внимательно на блок `catch` в псевдокоде выше. По умолчанию Spring откатывает транзакцию **ТОЛЬКО при `RuntimeException` (Unchecked) или `Error`**.

Если твой метод бросит проверяемое исключение (Checked Exception), например `IOException` или кастомное `BusinessException extends Exception`, Spring перехватит его, сделает **`commit()`** и данные сохранятся в базу! Это частая причина испорченных данных на проде.

**Как исправить:** На продакшене принято переопределять это поведение, чтобы транзакция откатывалась при ЛЮБОМ исключении:

Java

```
@Transactional(rollbackFor = Exception.class)
public void processPayment() { ... }
```

### 3. Проблема Self-Invocation (Вызов внутри класса)

Это классический вопрос на собеседовании. Что будет, если метод `A` вызовет метод `B` в том же классе, и только над методом `B` висит `@Transactional`?

Java

```
@Service
public class OrderService {
    
    public void createOrder() {
        // ... какая-то логика
        saveToDatabase(); // Вызов соседнего метода
    }

    @Transactional
    public void saveToDatabase() {
        // Сохранение
    }
}
```

**Ответ:** Транзакция **НЕ откроется**. Данные запишутся без транзакции в режиме auto-commit. **Почему?** Вспоминаем пункт 1. Магия работает только тогда, когда запрос проходит _сквозь Прокси-объект_. Когда кто-то извне вызывает метод `createOrder()`, он проходит через прокси. Но внутри метода `createOrder()` вызов `saveToDatabase()` (а точнее `this.saveToDatabase()`) идет напрямую к реальному объекту, минуя прокси!

**Как решить:**

1. Разнести методы по разным сервисам (рекомендуемо).
    
2. Заинжектить самого себя через конструктор (работает в новых версиях Spring) или `@Lazy` и вызывать метод через инжект: `self.saveToDatabase()`.

==Свойства транзакции==

Давай разберем все 4 параметра. У каждого из них есть свои "подводные камни", о которых любят спрашивать на системном дизайне и собеседованиях.

### 1. `propagation` (Управление границами транзакций)

Определяет, как метод должен вести себя, если он вызывается в контексте другой (уже существующей) транзакции. В Spring 7 типов `Propagation`.

- **`REQUIRED` (По умолчанию)**
    
    - _Логика:_ Если транзакция уже есть — присоединяется к ней. Если нет — создает новую.
        
    - _Суть:_ Самый частый выбор. Если метод А вызывает метод Б, они будут работать в рамках одного `Connection`. Если падает Б, откатывается всё (и А, и Б).
        
- **`REQUIRES_NEW`**
    
    - _Логика:_ Всегда создает **новую** транзакцию. Если уже есть активная — она ставится на паузу (Suspend).
        
    - _Ловушка на проде:_ В этот момент приложение держит **сразу два физических соединения (Connection)** из пула. Если таких вызовов будет много, пул соединений мгновенно исчерпается (Connection Pool Starvation). Используй только там, где результат вложенного метода должен сохраниться независимо от отката родителя (например, запись логов аудита).
        
- **`NESTED`**
    
    - _Логика:_ Создает точку сохранения (Savepoint) в рамках _текущей_ БД-транзакции (работает через `java.sql.Savepoint`).
        
    - _Суть:_ Если вложенный метод падает, транзакция откатывается **только до этой точки**, а родительский метод может перехватить ошибку и продолжить работу. (Поддерживается не всеми драйверами БД).
        
- **`MANDATORY`**
    
    - _Логика:_ Требует наличия активной транзакции. Если её нет — выбрасывает `IllegalTransactionStateException`.
        
    - _Суть:_ Защита "от дурака". Гарантирует, что важный метод (например, списание баланса) случайно не вызовут без транзакции.
        
- **`SUPPORTS`**
    
    - _Логика:_ Если транзакция есть — использует её. Если нет — выполняется без транзакции (в режиме auto-commit).
        
- **`NOT_SUPPORTED`**
    
    - _Логика:_ Ставит текущую транзакцию на паузу и выполняется **без** транзакции.
        
- **`NEVER`**
    
    - _Логика:_ Выбрасывает исключение, если кто-то вызвал этот метод внутри транзакции.
        

### 2. `isolation` (Уровни изоляции)

Изоляция решает проблему конкурентного доступа: что видит Поток 1, пока Поток 2 еще не закоммитил свои изменения?

По умолчанию стоит `Isolation.DEFAULT` — это значит, что Spring отдаст решение на откуп самой СУБД (в Postgres это `READ_COMMITTED`, в MySQL — `REPEATABLE_READ`).

Чтобы понимать уровни, нужно знать 3 классические аномалии БД:

1. **Dirty Read (Грязное чтение):** Транзакция А читает данные, которые Транзакция Б изменила, но еще _не закоммитила_. (Б откатится, а А будет работать с несуществующими данными).
    
2. **Non-repeatable Read (Неповторяющееся чтение):** Транзакция А читает строку дважды. Между чтениями Транзакция Б успевает изменить эту строку и закоммитить. А получает разные данные.
    
3. **Phantom Read (Фантомное чтение):** Транзакция А делает `SELECT COUNT(*)`. Транзакция Б добавляет новую строку. Транзакция А делает повторный запрос и видит "строку-призрак", которой раньше не было.
    

|**Уровень изоляции**|**Грязное чтение**|**Неповторяющееся чтение**|**Фантомное чтение**|
|---|---|---|---|
|**`READ_UNCOMMITTED`**|Возможны|Возможны|Возможны|
|**`READ_COMMITTED`**|**Защищено**|Возможны|Возможны|
|**`REPEATABLE_READ`**|**Защищено**|**Защищено**|Возможны|
|**`SERIALIZABLE`**|**Защищено**|**Защищено**|**Защищено**|

> **Архитектурный трейд-офф:** Чем выше уровень изоляции, тем больше блокировок (Locks) накладывает БД, и тем **медленнее** работает система. `SERIALIZABLE` в высоконагруженных системах превращает многопоточность в очередь, убивая производительность. Вместо него чаще используют `READ_COMMITTED` в паре с оптимистичными блокировками (Optimistic Locking, `@Version` в JPA).

### 3. `readOnly = true`

Это не просто флаг "для красоты" (по умолчанию `readOnly = false`). В высоконагруженных проектах это важнейший инструмент оптимизации. Указание `@Transactional(readOnly = true)` на методах, которые только читают данные (GET-запросы), дает три огромных плюса:

1. **Оптимизация Hibernate (Dirty Checking):** Если флаг включен, Spring переводит сессию Hibernate в режим `FlushMode.MANUAL`. Hibernate отключает механизм отслеживания изменений (Dirty Checking). Ему больше не нужно делать слепки (snapshots) каждого загруженного объекта и сравнивать их в конце транзакции. **Экономия CPU и оперативной памяти колоссальная.**
    
2. **Уровень драйвера БД:** Spring делает вызов `connection.setReadOnly(true)`. Некоторые базы данных (например, PostgreSQL) при получении этого флага применяют внутренние оптимизации производительности для SELECT-запросов.
    
3. **Маршрутизация (Master/Slave):** В сложных архитектурах с репликацией баз данных, балансировщики или умные DataSource (через `AbstractRoutingDataSource`) видят этот флаг и направляют такие транзакции на Slave-ноды (реплики), снимая нагрузку с Master-узла.
    

### 4. `timeout` и `timeoutString`

Устанавливает максимальное время (в секундах) для выполнения транзакции. По умолчанию `-1` (используется таймаут базы данных).

Java

```
@Transactional(timeout = 5) // 5 секунд
```

**Ловушка с таймаутом:** Джуниоры часто думают, что если транзакция длится дольше 5 секунд, Spring вызовет `Thread.interrupt()` и жестко "убьет" Java-поток.

**Это не так.** Spring не прерывает потоки. Таймаут работает иначе:

1. Spring транслирует этот таймаут на уровень JDBC-драйвера как `Statement.setQueryTimeout(5)`. Если SQL-запрос выполняется дольше, база данных сама оборвет запрос и бросит ошибку.
    
2. Перед выполнением _каждого нового_ SQL-запроса в рамках метода, Spring проверяет "дедлайн". Если 5 секунд прошло, Spring бросит `TransactionTimedOutException` и откатит изменения.
    

_Если у тебя внутри `@Transactional` есть долгий поход по HTTP в другой сервис, который висит 10 секунд, а SQL запросов больше нет, Spring НЕ прервет транзакцию ровно через 5 секунд. Он упадет только когда попытается сделать следующий коммит или запрос к БД._
