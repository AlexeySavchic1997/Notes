### 1. Краткие определения (Заучить для старта)

**IoC (Inversion of Control — Инверсия контроля)**

> **Определение:** Это архитектурный принцип, при котором фреймворк берет на себя управление потоком выполнения программы и жизненным циклом объектов. **Простыми словами:** Мы перестаем писать `new MyService()`. Мы отдаем контроль фреймворку (Spring). Фреймворк сам решает, когда создать объект, как его настроить и когда уничтожить. **Фраза-триггер:** На собеседовании обязательно упомяни **Голливудский принцип**: _"Не звоните нам, мы сами вам позвоним"_. Приложение не управляет фреймворком, фреймворк вызывает код приложения.

**DI (Dependency Injection — Внедрение зависимостей)**

> **Определение:** Это конкретный паттерн проектирования, который реализует принцип IoC. **Простыми словами:** Класс не должен сам создавать или искать объекты, от которых он зависит (например, репозиторий для базы данных). Он просто "объявляет" о своей нужде (через конструктор), а IoC-контейнер передает (внедряет) ему готовый объект при создании.

**Разница между ними:** IoC — это общая идея (Что делать?), а DI — это конкретный механизм реализации (Как именно это сделать?).

### 2. Частые вопросы на собеседовании (Ловушки)

Как только ты произнесешь эти определения, интервьюер начнет копать вглубь. Вот к чему нужно быть готовым:

#### Вопрос 1: "Почему внедрение через поле (`@Autowired` над переменной) считается антипаттерном?"

**Ответ Senior'а:** Полевая инъекция ломает сразу несколько принципов чистого кода:

1. **Невозможность Unit-тестирования без Spring.** Класс нельзя протестировать с помощью чистого Java (написав `new MyService(...)`), потому что поля приватные. Приходится поднимать тяжелый Spring-контекст или использовать костыли (Reflection).
    
2. **Мутабельность.** Поле нельзя сделать `final`, значит состояние объекта может быть изменено в рантайме.
    
3. **Скрытые циклические зависимости.** Контейнер позволит запустить приложение, и ошибка всплывет позже. _Правильный подход:_ Внедрение через **конструктор** (часто генерируется через `@RequiredArgsConstructor` из Lombok). Это гарантирует, что объект не будет создан без нужных зависимостей (Fail-Fast), и поля будут `final`.
    

#### Вопрос 2: "Что такое циклическая зависимость (Circular Dependency) и как Spring с ней борется?"

**Ситуация:** Бин `A` требует бин `B`, а бин `B` требует бин `A`. **Ответ:**

- Если инжект идет через **конструкторы**, Spring упадет при старте с ошибкой `BeanCurrentlyInCreationException`. (Это хорошо, архитектура должна упасть).
    
- Если инжект через **поля/сеттеры**, Spring сможет это разрешить благодаря **трехуровневому кэшу (Three-level cache)**. Он создаст "пустой" Бин А (без зависимостей), положит ссылку на него в ранний кэш, создаст Бин Б, внедрит туда ссылку на ранний А, а потом завершит создание А.
    
- _Как исправить без изменения архитектуры?_ Повесить аннотацию `@Lazy` на одну из зависимостей. Тогда Spring внедрит не реальный объект, а AOP-прокси, и разорвет цикл. (Начиная со Spring Boot 2.6 циклические зависимости запрещены по умолчанию вообще).
    

#### Вопрос 3: "В чем разница между `BeanFactory` и `ApplicationContext`?"

**Ответ:** Это два главных интерфейса IoC-контейнера в Spring.

- **`BeanFactory`** — это базовый интерфейс. Он работает по принципу _Lazy-loading_ (Ленивая инициализация). Бин создается только в тот момент, когда к нему впервые обратились. Используется там, где жесткая экономия ресурсов (IoT, старые мобильные устройства).
    
- **`ApplicationContext`** — это расширенный интерфейс (наследник BeanFactory). Он создает все Singleton-бины сразу при старте приложения (_Eager-loading_). Плюс он добавляет мощный функционал: поддержку AOP, публикацию событий (Event Publisher), интернационализацию (i18n). В 99% веб-приложений мы используем именно его.
    

#### Вопрос 4: "Можно ли реализовать IoC без DI?"

**Ответ:** Да. DI — не единственный способ. Другие реализации IoC:

1. **Service Locator** (Антипаттерн). Класс сам лезет в глобальный реестр и просит зависимости: `ServiceLocator.get(UserRepository.class)`.
    
2. **Шаблонный метод (Template Method).** Паттерн из ООП, где базовый абстрактный класс описывает алгоритм, а подклассы реализуют шаги. Здесь тоже работает "Голливудский принцип": базовый класс вызывает методы наследников.
