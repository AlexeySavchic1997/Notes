Паттерны проектирования (Банда Четырех, GoF) — это не готовый код, а архитектурные чертежи для решения типовых проблем. На собеседованиях уровня Middle+ от тебя не просят нарисовать UML-диаграмму. От тебя ждут понимания того, **какую боль решает паттерн** и как он применяется в реальном коде (особенно в Spring).

Все паттерны делятся на три группы. Давай разберем запрошенные тобой (и добавим парочку критически важных для бэкенда), разделив их по этим группам.

### I. Порождающие паттерны (Creational)

_Отвечают за то, как именно и где создаются объекты, пряча логику вызова `new`._

#### 1. Singleton (Одиночка)

- **Суть:** Гарантирует, что у класса есть только один экземпляр на всё приложение, и предоставляет глобальную точку доступа к нему.
    
- **Боль:** Создание пула подключений к БД или конфигуратора при каждом запросе "положит" память.
    
- **На проде (Spring):** Это дефолтный Scope для любого бина в Spring (`@Service`, `@Component`). Spring IoC-контейнер сам работает как гигантский реестр синглтонов.
    
- **Ловушка на собесе:** Если попросят написать Singleton на чистой Java, никогда не пиши простой `if (instance == null)`. В многопоточной среде это создаст два объекта. Пиши либо через `enum` (рекомендация Джошуа Блоха), либо через **Double-Checked Locking** с `volatile`.
    

#### 2. Factory (Фабрика)

Здесь часто путают _Фабричный метод_ и _Абстрактную фабрику_, но суть одна:

- **Суть:** Класс не вызывает `new КонкретныйКласс()`. Он просит Фабрику отдать ему объект, реализующий нужный интерфейс.
    
- **Боль:** Жесткая связанность (Tight Coupling). Если везде использовать `new`, то при замене библиотеки логирования придется переписывать весь проект.
    
- **На проде:** Везде, где решение о том, _какой именно_ класс создать, принимается в рантайме. В Spring главный пример — это интерфейс `BeanFactory`, который решает, какой именно Бин тебе отдать.
    

#### 3. Builder (Строитель)

- **Суть:** Позволяет создавать сложные объекты пошагово.
    
- **Боль:** "Телескопические конструкторы" — когда у тебя конструктор принимает 15 параметров (`String, String, null, null, int, false...`). Это невозможно читать и легко перепутать параметры одного типа.
    
- **На проде:** Никто не пишет паттерн Builder руками. Все используют аннотацию **`@Builder` из библиотеки Lombok**. Это стандарт индустрии.
    
    Java
    
    ```
    User user = User.builder()
                    .name("Ivan")
                    .role("ADMIN")
                    .build();
    ```
    

#### 4. Prototype (Прототип)

- **Суть:** Вместо создания нового объекта с нуля, мы копируем (клонируем) уже существующий объект.
    
- **Боль:** Иногда создание объекта стоит очень дорого (он лезет в БД, вычисляет хэши, читает файлы). Быстрее взять готовый и изменить в нем пару полей.
    
- **На проде:** Используется редко. Стандартный интерфейс Java `Cloneable` считается архитектурной ошибкой. Вместо него на проде пишут **Copy Constructors** (конструкторы копирования) или используют сериализацию в JSON и обратно для глубокого клонирования (Deep Copy).
    

### II. Поведенческие паттерны (Behavioral)

_Отвечают за то, как объекты общаются друг с другом и передают ответственность._

#### 5. Strategy (Стратегия) — Главный убийца `if-else`

- **Суть:** Выносит семейство алгоритмов в отдельные классы и делает их взаимозаменяемыми во время выполнения.
    
- **Боль:** Метод оплаты, который разросся до `switch` на 500 строк (если PayPal — одно, если Stripe — другое, если Крипта — третье). Каждый раз при добавлении новой оплаты приходится трогать этот огромный класс, нарушая принцип OCP (Open-Closed Principle).
    
- **На проде:** Это самый любимый паттерн Senior-разработчиков. Мы создаем интерфейс `PaymentStrategy`, делаем 3 класса-реализации. А в Spring просто инжектим их в виде мапы: `@Autowired Map<String, PaymentStrategy> strategies`. И дальше вызываем нужный алгоритм по ключу без единого `if`.
    

### III. Бонус: Что еще обязательно спросят на Middle/Senior?

Раз уж мы затронули базу, вот 3 паттерна, которые работают в Spring под капотом, и о них нужно упомянуть, чтобы показать системный уровень:

- **Proxy (Заместитель) - Структурный:** Объект-обертка, который контролирует доступ к оригинальному объекту. _Где используется:_ Это основа всего **AOP в Spring** (аннотации `@Transactional`, `@Cacheable`, `@Async`).
    
- **Observer (Наблюдатель) - Поведенческий:** Паттерн Издатель-Подписчик. _Где используется:_ `ApplicationEventPublisher` и `@EventListener` в Spring. Идеально для развязывания логики (создали пользователя -> бросили событие -> другой сервис поймал и отправил email).
    
- **Adapter (Адаптер) - Структурный:** Оборачивает несовместимый объект, чтобы он работал с твоим интерфейсом. _Где используется:_ Интеграция со старыми SOAP-системами или внешними API.
