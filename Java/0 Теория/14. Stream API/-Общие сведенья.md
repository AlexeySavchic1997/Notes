Stream API, появившийся в Java 8, навсегда изменил то, как мы пишем код. На собеседованиях уровня Middle+ от тебя не попросят просто отфильтровать список. Интервьюер будет копать в то, **как Stream работает с памятью**, что такое ленивые вычисления и почему `parallelStream()` может "положить" твой продакшен.

Давай разберем Stream API с архитектурной точки зрения.

### 1. Зачем нужен Stream API? (Философия)

До Java 8 мы использовали **Императивный подход**: мы писали циклы `for`, создавали временные списки, писали `if` внутри цикла. Мы говорили машине _КАК_ нужно сделать работу (шаг за шагом). Stream API принес **Декларативный подход**: мы говорим машине _ЧТО_ мы хотим получить на выходе, а Stream сам решает, как лучше итерироваться по данным.

**Главные фичи:**

1. **Внутренняя итерация (Internal Iteration):** Тебе больше не нужно писать цикл `for`. Ты отдаешь данные потоку, и он сам протаскивает их через функции.
    
2. **Бесплатная параллельность:** Заменить `stream()` на `parallelStream()` — это один клик, и код начинает использовать все ядра процессора (но с этим есть огромная ловушка, о ней ниже).
    

### 2. Как работает Pipeline (Конвейер)

Любой стрим всегда состоит из трех стадий. Если не будет хотя бы одной — он не отработает.

1. **Source (Источник):** Откуда берем данные (Коллекция, Массив, Файл, Генератор).
    
2. **Intermediate Operations (Промежуточные операции):** `filter`, `map`, `sorted`, `peek`. Они **всегда возвращают новый Stream**.
    
3. **Terminal Operation (Терминальная операция):** `collect`, `count`, `findFirst`, `reduce`, `forEach`. Возвращает конкретный результат (число, список, `Optional`) или ничего (`void`).
    

### 3. Главная магия: Ленивые вычисления (Lazy Evaluation)

Это самый важный концепт для собеседования. Промежуточные операции **не выполняются**, пока ты не вызовешь терминальную. Они просто строят "чертеж" (рецепт) того, что нужно будет сделать.

**Классический вопрос на собесе: Что выведет этот код?**

Java

```
List<String> names = List.of("Ivan", "Petr", "Alex");

names.stream()
     .filter(name -> {
         System.out.println("Фильтруем: " + name);
         return name.length() > 3;
     });
```

**Ответ:** Код не выведет **НИЧЕГО**. Терминальной операции нет, стрим даже не запустился.

**Магия Short-circuiting (Короткое замыкание):** А теперь добавим терминальную операцию `.findFirst()`:

Java

```
names.stream()
     .filter(name -> {
         System.out.println("Фильтруем: " + name);
         return name.length() > 3;
     })
     .map(name -> {
         System.out.println("Маппим: " + name);
         return name.toUpperCase();
     })
     .findFirst();
```

Как это будет работать под капотом (именно это ждет интервьюер):

1. Стрим не бежит по всему списку сразу! Он берет **первый элемент** ("Ivan").
    
2. Пропускает его через `filter` (длина > 3? Да). Выводит: "Фильтруем: Ivan".
    
3. Пропускает "Ivan" через `map`. Выводит: "Маппим: Ivan". Получает "IVAN".
    
4. Передает его в `findFirst()`.
    
5. `findFirst` говорит: _"Стоп! Я нашел первый элемент, мне больше ничего не нужно!"_. Стрим немедленно **прерывает работу**. "Petr" и "Alex" даже не будут затронуты. Это колоссальная экономия CPU при работе с миллионами записей.
    

### 4. Внутреннее устройство: Stateful vs Stateless

Промежуточные операции делятся на два типа, и это критически важно для понимания производительности.

- **Stateless (Без состояния):** `filter`, `map`. Они смотрят только на текущий элемент. Им плевать на остальные элементы. Они работают молниеносно и идеально распараллеливаются.
    
- **Stateful (С состоянием):** `sorted`, `distinct`, `limit`. Чтобы отсортировать стрим (`sorted`), стрим **обязан** дождаться, пока все элементы пройдут через предыдущие шаги, накопить их в памяти, отсортировать, и только потом пустить дальше. Такие операции ломают конвейер (создают узкое горлышко) и потребляют оперативную память.
    

### 5. Топ-3 ловушки на собеседованиях (Уровень Senior)

#### Ловушка 1: Повторное использование

**Вопрос:** Можно ли сохранить Stream в переменную и использовать дважды? **Ответ:** Нет. Стрим — это одноразовый конвейер. Если вызвать на нем терминальную операцию, он "закрывается". Попытка вызвать вторую терминальную операцию бросит `IllegalStateException: stream has already been operated upon or closed`.

#### Ловушка 2: Побочные эффекты (Side-effects)

**Вопрос:** Можно ли внутри `.forEach()` или `.map()` изменять внешние переменные? **Ответ:** Технически да, но архитектурно это **строго запрещено**. Функции внутри стрима должны быть "чистыми" (Pure Functions). Если ты изменяешь внешний `List` внутри `parallelStream()`, ты получишь Race Condition (состояние гонки) и потеряешь данные, так как стрим не использует синхронизацию. Для сборки данных нужно использовать ТОЛЬКО `.collect(Collectors.toList())`.

#### Ловушка 3: Убийца продакшена — `parallelStream()`

**Вопрос:** Почему мы не используем `parallelStream()` везде, ведь он быстрее? **Ответ Senior'а:** `parallelStream()` под капотом использует глобальный общий пул потоков — `ForkJoinPool.commonPool()`. Размер этого пула по умолчанию равен количеству ядер процессора минус 1. Если внутри параллельного стрима ты сделаешь блокирующий вызов (например, HTTP-запрос или долгий запрос к БД), ты **заблокируешь потоки общего пула**. В результате ВСЕ другие параллельные стримы во всем твоем Spring Boot приложении просто зависнут, ожидая освобождения потоков. `parallelStream()` можно использовать **только для чистых, долгих математических вычислений в памяти (CPU-bound задачи)**, но никак не для I/O операций (походов в сеть/базу).
