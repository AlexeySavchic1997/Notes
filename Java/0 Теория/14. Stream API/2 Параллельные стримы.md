Параллельные стримы (`parallelStream`) — это мощный инструмент, который может как ускорить выполнение задачи в несколько раз, так и полностью "положить" твой продакшен. На собеседованиях эту тему обожают, потому что она проверяет понимание многопоточности.

Давай разберем, как эта магия работает под капотом, и когда её категорически нельзя использовать.

### 1. Как это работает под капотом (Архитектура)

Параллельные стримы реализуют парадигму **Divide and Conquer (Разделяй и властвуй)**. Процесс делится на три этапа:

1. **Разделение (Splitting):** Под капотом коллекция использует интерфейс `Spliterator`. Он рекурсивно делит исходную коллекцию на равные части. Например, `ArrayList` делится идеально быстро (O(1)) — он просто бьет массив пополам, потом еще пополам. А вот `LinkedList` делится ужасно (ему нужно перебирать элементы), поэтому параллельный стрим на `LinkedList` часто работает медленнее обычного.
    
2. **Выполнение (Execution):** Разделенные куски отправляются на выполнение в специальный пул потоков — **`ForkJoinPool.commonPool()`**.
    
3. **Объединение (Combining):** Когда отдельные потоки заканчивают вычисления, стрим начинает "склеивать" их результаты обратно (через фазу Combiner в коллекторе или операции `reduce`).
    

> **Секрет Senior'а (Про Пул Потоков):** Глобальный пул `ForkJoinPool.commonPool()` один на всё ваше JVM-приложение. По умолчанию его размер равен **количеству логических ядер процессора минус 1**. (Если у тебя 8 ядер, в пуле будет 7 потоков. Восьмым потоком выступит сам вызывающий поток `main` или HTTP-поток Tomcat'а, который запустил стрим).

### 2. Пример кода (Как правильно и как опасно)

#### ✅ Правильное использование (CPU-bound задачи)

Параллельные стримы идеальны для тяжелой математики, шифрования, парсинга огромных текстов — то есть там, где работает только процессор и оперативная память.

Java

```
import java.util.List;
import java.util.stream.IntStream;

public class ParallelExample {
    public static void main(String[] args) {
        // Создаем список из 1 миллиона чисел
        List<Integer> numbers = IntStream.rangeClosed(1, 1_000_000)
                                         .boxed()
                                         .toList();

        long startTime = System.currentTimeMillis();

        // Запускаем параллельный стрим
        long result = numbers.parallelStream()
                .filter(n -> n % 2 == 0)      // Фильтруем четные
                .mapToLong(ParallelExample::heavyMathComputation) // Тяжелая математика
                .sum();                       // Терминальная операция (потокобезопасно склеивает результат)

        System.out.println("Результат: " + result);
        System.out.println("Время: " + (System.currentTimeMillis() - startTime) + " мс");
    }

    // Имитация сложного вычисления
    private static long heavyMathComputation(int number) {
        long sum = 0;
        for (int i = 0; i < 1000; i++) {
            sum += Math.pow(number, 2) % 12345;
        }
        return sum;
    }
}
```

#### ❌ Фатальная ошибка (Side-effects / Состояние гонки)

Джуниоры часто пытаются сохранить результаты параллельного стрима во внешнюю коллекцию, которая не является потокобезопасной.

Java

```
List<Integer> numbers = IntStream.range(0, 10000).boxed().toList();
List<Integer> evenNumbers = new ArrayList<>(); // Обычный несинхронизированный список

// УЖАСНЫЙ КОД:
numbers.parallelStream()
       .filter(n -> n % 2 == 0)
       .forEach(n -> evenNumbers.add(n)); // Race Condition!

System.out.println(evenNumbers.size()); // Выведет случайное число (например, 4802 вместо 5000), или бросит ConcurrentModificationException
```

_Правильное решение:_ Никогда не изменяйте внешнее состояние! Используйте `.collect(Collectors.toList())` — под капотом стрим сам безопасно склеит списки из разных потоков.

### 3. Главная ловушка на продакшене (I/O операции)

На собеседовании тебя обязательно спросят: _"Можно ли внутри `parallelStream` делать HTTP-запросы в другой микросервис или запросы в базу данных?"_

**Ответ: КАТЕГОРИЧЕСКИ НЕТ.**

Вспомни про `ForkJoinPool.commonPool()`. Допустим, у тебя 8 ядер (7 потоков в пуле). Ты делаешь `parallelStream` по списку из 100 пользователей, чтобы отправить им email.

1. Стрим берет первые 7 юзеров и отправляет их в пул.
    
2. Потоки вызывают `emailService.send()` и... засыпают (блокируются), ожидая ответа от SMTP-сервера по сети (допустим, 2 секунды).
    
3. **Итог:** Весь глобальный пул `ForkJoinPool` заблокирован! Если в этот момент другой кусок приложения попытается отсортировать параллельным стримом список товаров, он просто **зависнет намертво**, ожидая, пока освободятся потоки, занятые отправкой писем.
    

Для I/O операций (походы в сеть, файлы, БД) параллельные стримы не подходят. Для этого используют асинхронное программирование.
