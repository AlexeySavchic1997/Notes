Понимание жизненного цикла Entity (сущности) — это ключ к ответу на вопрос: _"Почему Hibernate иногда сохраняет данные в базу, хотя я не вызывал метод save()?"_.

Всё крутится вокруг **Persistence Context** (Контекста постоянства или «Кэша первого уровня»). Это специальная область памяти внутри `EntityManager` (или `Session` в Hibernate).

У любой сущности в JPA есть всего **4 возможных состояния**. Давай разберем их так, как этого ждут на собеседовании.

### 1. Transient / New (Новый / Транзиентный)

Это самое начало жизни объекта. Ты просто создал объект через оператор `new`.

Java

```
User user = new User();
user.setName("Иван");
```

- **Связь с БД:** Никакой. Этой записи нет в таблице.
    
- **Связь с Hibernate:** Hibernate вообще не знает о существовании этого объекта. Он не лежит в Persistence Context.
    
- **ID (Primary Key):** Обычно равен `null` (если ID генерируется базой данных).
    

### 2. Managed / Persistent (Управляемый / Персистентный)

Это самое важное состояние. Сущность попадает в него двумя путями: либо мы сохраняем новую сущность (`em.persist(user)` или `repository.save(user)`), либо достаем существующую из базы (`em.find()`, `repository.findById()`).

Java

```
@Transactional
public void updateName(Long id) {
    // 1. Достаем из БД. Теперь user в состоянии Managed
    User user = userRepository.findById(id).get(); 
    
    // 2. Меняем имя
    user.setName("Петр"); 
    
    // repository.save(user) вызывать НЕ НАДО!
}
```

- **Связь с Hibernate:** Сущность лежит в Persistence Context.
    
- **Магия Dirty Checking (Грязная проверка):** В этом состоянии Hibernate **непрерывно следит за объектом**. Как только транзакция завершается (перед `commit`), Hibernate сканирует все Managed-объекты. Если он видит, что ты через сеттер изменил поле (`setName`), он сам, автоматически, сгенерирует и выполнит SQL-запрос `UPDATE`.
    

### 3. Detached (Отсоединенный)

Сущность переходит в это состояние, когда Persistence Context закрывается (закончилась `@Transactional` транзакция), либо когда мы явно чистим кэш (`em.clear()`, `em.detach(user)`).

- **Связь с БД:** Запись в базе существует (и у объекта есть реальный ID).
    
- **Связь с Hibernate:** Hibernate **перестал следить** за объектом.
    
- **Подводные камни:**
    
    1. Если ты вызовешь `user.setName("Олег")` у Detached-объекта, в базу этот апдейт **не улетит**.
        
    2. Именно в этом состоянии возникает знаменитая ошибка `LazyInitializationException`. Объект отсоединен, Hibernate за ним не смотрит, а ты пытаешься вызвать `user.getOrders()` (которого нет в памяти).
        

**Как вернуть в Managed?** Через операцию `merge()` (в Spring Data JPA метод `save()` под капотом вызывает именно `merge`, если видит, что у объекта уже есть ID). Hibernate создаст новую Managed-копию объекта и скопирует туда данные.

### 4. Removed (Удаленный)

Ты явно сказал Hibernate удалить объект: `em.remove(user)` или `repository.delete(user)`.

- **Что происходит:** Объект всё еще лежит в памяти Java и у него есть ID, но Hibernate пометил его «на удаление».
    
- В момент завершения транзакции (при `flush()`) Hibernate сгенерирует SQL-запрос `DELETE` и физически удалит строку из базы. После этого объект в памяти Java станет просто "мусором" (вернется в подобие Transient состояния), пока его не соберет Garbage Collector.
    

### Шпаргалка: Как они перетекают друг в друга

- `new` -> **Transient**
    
- **Transient** -> _persist()_ -> **Managed**
    
- **Managed** -> _конец транзакции / clear()_ -> **Detached**
    
- **Detached** -> _merge()_ -> **Managed**
    
- **Managed** -> _remove()_ -> **Removed**
