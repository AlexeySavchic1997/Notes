Остановка потока в Java — это процесс **кооперативный, а не диктаторский**. Вы не можете просто «убить» поток извне (как процесс в диспетчере задач ОС). Вы можете только _вежливо попросить_ его остановиться, а он должен эту просьбу увидеть и корректно завершить работу.

Давайте разберем, почему это так, и как правильно использовать методы класса `Thread`.

## Как НЕ надо останавливать поток: `Thread.stop()`

В ранних версиях Java был метод `Thread.stop()`. Сейчас он помечен как `Deprecated` и его использование — архитектурное преступление.

**Почему его запретили?** Если поток А захватил `synchronized` монитор, начал переводить деньги (списал с одного счета, но еще не зачислил на другой), и в этот момент вы вызвали `A.stop()`, поток А мгновенно умирает. Но что хуже — JVM **автоматически отпускает все мониторы**, которые он держал. Поток Б заходит в критическую секцию и видит наполовину измененные, сломанные данные (нарушение консистентности). Тихий сбой, который невозможно отладить.

## Правильный путь: Механизм Interruption (Прерывание)

Вместо убийства Java использует внутренний `boolean` флаг (interrupt status), который есть у каждого потока.

### Механика работы `interrupt()`

Когда Главный поток хочет остановить Фоновый поток, он вызывает метод `фоновыйПоток.interrupt()`. Дальше всё зависит от того, чем именно сейчас занят Фоновый поток.

**Сценарий 1: Фоновый поток активно работает (считает математику)** Вызов `interrupt()` просто меняет `boolean` флаг внутри объекта фонового потока на `true`. И всё. Если фоновый поток написан глупо и не проверяет этот флаг, он будет крутиться вечно. _Правильный код фонового потока:_

Java

```
while (!Thread.currentThread().isInterrupted()) {
    // Делаем полезную работу небольшими порциями
    processNextChunk();
}
// Если вышли из цикла, значит нас попросили остановиться.
// Очищаем ресурсы и мягко завершаем метод run().
```

**Сценарий 2: Фоновый поток спит (заблокирован)** Что если фоновый поток висит в `Thread.sleep()`, или ждет лока в AQS (`LockSupport.park()`), или ждет ответа из сети? Он физически не может крутить цикл и проверять флаг `isInterrupted()`! Здесь магию делает сама JVM. Когда Главный поток вызывает `interrupt()`, JVM видит, что фоновый поток спит, и **принудительно будит его**, заставляя методы `sleep()`, `wait()` или `join()` выбросить ошибку — **`InterruptedException`**.

### Главная ловушка `InterruptedException`

Когда JVM выбрасывает `InterruptedException`, она **АВТОМАТИЧЕСКИ СБРАСЫВАЕТ флаг прерывания обратно в `false`**. Логика JVM такова: _"Я бросила исключение, значит разработчик его поймал и обработал сигнал, флаг больше не нужен"_.

Из-за этого новички часто пишут такой ужасный код (проглатывание прерывания):

Java

```
while (!Thread.currentThread().isInterrupted()) {
    try {
        Thread.sleep(1000); // Спим
    } catch (InterruptedException e) {
        // Ошибка поймана! Но флаг теперь false.
        System.out.println("Проснулись"); 
    }
} // Цикл пойдет на новый круг, поток НИКОГДА не остановится!
```

**Золотое правило многопоточности:** Если вы поймали `InterruptedException`, но не можете полностью остановить поток прямо здесь (например, вы внутри глубокого метода), вы **обязаны восстановить флаг**, чтобы код уровнем выше узнал о прерывании:

Java

```
catch (InterruptedException e) {
    // Восстанавливаем сброшенный флаг!
    Thread.currentThread().interrupt(); 
    return; // или break
}
```

## Обзор ключевых методов класса `Thread`

Класс `Thread` — это API управления системным потоком. Его методы делятся на несколько групп.

### 1. Методы проверки статуса прерывания (самые коварные)

- **`isInterrupted()`** — метод конкретного объекта (инстанса). Просто читает флаг. **Не сбрасывает** его.
    
- **`Thread.interrupted()`** — СТАТИЧЕСКИЙ метод. Проверяет флаг у _текущего_ потока (который вызывает метод) и **сбрасывает его в false**. Используется редко, когда нужно сделать сложную логику: _"Отреагировать на прерывание, но продолжить работу"_.
    

### 2. Жизненный цикл

- **`start()`** — делает системный вызов к ОС для создания TCB (Thread Control Block) и выделения стека, после чего вызывает метод `run()`. _Важно: если вызвать `run()` напрямую, новый поток не создастся, код выполнится в текущем потоке!_
    
- **`join()`** — заставляет текущий поток уснуть до тех пор, пока поток, у которого вызвали `join()`, не завершит свою работу. (Под капотом использует монитор `Object.wait()`).
    

### 3. Статические утилиты (влияют на ТОТ поток, который их вызывает)

- **`Thread.sleep(ms)`** — отдает процессор ОС, поток засыпает на указанное время.
    
- **`Thread.yield()`** — "вежливая уступка". Поток говорит планировщику ОС: _"Я готов отдать остаток своего кванта времени другим потокам, но если других желающих нет, я продолжу работать"_. Почти не используется в современном коде, так как планировщики ОС (например, CFS в Linux) сами прекрасно распределяют время.
    
- **`Thread.currentThread()`** — возвращает объект потока, в котором сейчас выполняется этот код.
    

### 4. Настройки потока (вызываются ДО старта)

- **`setDaemon(true)`** — делает поток демоном.
    
    - _Зачем:_ JVM завершает свою работу только тогда, когда умрет последний **non-daemon** поток. Демон-потоки (например, сборщик мусора или фоновые таймеры) не удерживают JVM от выключения. Если завершился `main` и остались только демоны — программа закрывается, обрубая демонов на полуслове.
        
- **`setPriority(int)`** — устанавливает приоритет от 1 (MIN) до 10 (MAX).
    
    - _Нюанс:_ Это просто "пожелание" для ОС. Планировщик Linux или Windows может полностью проигнорировать этот приоритет. Полагаться на него для бизнес-логики нельзя.
