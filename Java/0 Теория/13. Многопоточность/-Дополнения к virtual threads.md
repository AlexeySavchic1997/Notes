В основе выполнения виртуальных потоков лежит специализированный экземпляр `ForkJoinPool`. Выбор этого пула вместо классического `ThreadPoolExecutor` (который используется, например, в обычных пулах Tomcat) обусловлен архитектурой локальных очередей и алгоритмом **Work-Stealing (кражи работы)**, которые идеально подходят для миллионов короткоживущих задач.

## Архитектура: Очереди вместо единого узкого горлышка

В классическом пуле потоков все рабочие потоки смотрят в одну общую очередь задач (например, `LinkedBlockingQueue`). Когда задач миллионы, возникает жесточайшая конкуренция (contention) за блокировку этой очереди: чтобы взять задачу, поток должен заблокировать очередь для остальных. При масштабах виртуальных потоков это привело бы к катастрофическому падению производительности.

`ForkJoinPool` решает эту проблему разделением:

1. **Локальные очереди (Deques):** У каждого несущего потока (Carrier Thread) есть своя собственная двусторонняя очередь задач (Double-ended queue).
    
2. **Работа без блокировок:** Несущий поток всегда берет задачи (виртуальные потоки, готовые к выполнению) из "головы" своей собственной очереди. Поскольку он работает с ней один, тяжелые механизмы синхронизации не требуются.
    

## Алгоритм Work-Stealing (Кража работы)

Что происходит, если один несущий поток быстро выполнил все свои задачи и его локальная очередь опустела, а соседний поток завален работой? Вместо того чтобы простаивать и тратить ресурсы впустую, свободный поток становится "вором":

- Он заглядывает в очереди других несущих потоков пула.
    
- Он "крадет" задачу с противоположного конца (с "хвоста") чужой очереди.
    
- **Почему это эффективно:** Владелец очереди берет задачи с головы, а вор — с хвоста. Они физически обращаются к разным концам структуры данных и редко пересекаются, что сводит к минимуму блокировки процессора и сохраняет кэш эффективным.
    

Благодаря Work-Stealing, этот пул обеспечивает идеальную балансировку нагрузки на все ядра процессора без использования единого диспетчера.

## Жизненный цикл Виртуального Потока в пуле

Работа виртуального потока в этом пуле выглядит как бесконечный цикл парковки и возврата:

1. **Submit (Постановка):** При старте виртуального потока JVM упаковывает его как задачу (под капотом это объект `Continuation`) и кладет в локальную очередь одного из Carrier-потоков.
    
2. **Mount (Монтирование):** Carrier-поток берет задачу. JVM копирует данные виртуального потока (его стековые фреймы) из общей кучи (Heap) в реальный стек платформенного Carrier-потока. Начинается выполнение вашего кода.
    
3. **Unmount (Отмонтирование):** Как только код делает блокирующий I/O вызов (например, запрос к БД), JVM перехватывает его. Она сохраняет текущий прогресс (стек и регистры) обратно в кучу.
    
4. **Освобождение ядра:** Carrier-поток не ждет ответа от базы данных! Он мгновенно берет следующий готовый к выполнению виртуальный поток из своей очереди.
    
5. **Re-submit (Возврат):** Когда данные из сети приходят, JVM берет сохраненный в куче виртуальный поток и снова кидает его в `ForkJoinPool`. Его может подхватить уже **совершенно другой** Carrier-поток для продолжения работы.
    

## Скрытые лимиты и расширение пула

Хотя по умолчанию размер пула равен количеству ядер, JVM не жестко ограничивает пул этим числом. Пул управляется тремя внутренними свойствами:

- `jdk.virtualThreadScheduler.parallelism` — целевое количество активных потоков, выполняющих код (по умолчанию равно числу ядер).
    
- `jdk.virtualThreadScheduler.maxPoolSize` — жесткий максимум платформенных потоков (по умолчанию 256).
    
- `jdk.virtualThreadScheduler.minRunnable` — минимальное количество потоков, которые пул старается держать активными.
    

Значение `maxPoolSize` в 256 (а не равно числу ядер) существует как спасательный круг для проблемы **Thread Pinning** (пришпиленных потоков). Если виртуальный поток блокируется внутри блока `synchronized`, он блокирует свое ядро (Carrier Thread). Чтобы приложение не "встало", `ForkJoinPool` динамически порождает новые компенсационные платформенные потоки (до предела в 256), чтобы другие виртуальные потоки могли продолжить работу.

==Почему платформенные потоки не используют ForkJoinPool==

Классический пул потоков (`ThreadPoolExecutor`), который десятилетиями используется в Tomcat и других серверах, не использует архитектуру `ForkJoinPool`, потому что они создавались для решения **фундаментально разных задач**.

Всё упирается в размер задач (гранулярность), их предсказуемость и отношение к блокировкам.

### 1. Время выполнения задачи vs Время блокировки очереди

В классическом сервере (например, Tomcat) пул состоит из 200–500 платформенных потоков. Типичная задача (HTTP-запрос) — это "тяжелая" операция. Поток берет запрос, делает сложную бизнес-логику, обращается к базе данных, ждет ответа по сети 50 миллисекунд, формирует JSON и отдает ответ.

Поскольку на выполнение одного запроса уходят десятки или сотни миллисекунд, потоки обращаются к общей очереди за новыми задачами **очень редко**. Конкуренция (contention) за единую блокировку `LinkedBlockingQueue` на 200 потоках занимает наносекунды. Это время абсолютно теряется на фоне миллисекундного ожидания ответа от БД. Для таких задач сложная логика локальных очередей и кражи работы (work-stealing) стала бы избыточным оверхедом.

### 2. Порядок выполнения и справедливость (Fairness)

Классический `ThreadPoolExecutor` обычно работает по принципу **FIFO (First In, First Out)** — первый пришел, первый обслуживается. Это логично для веб-сервера: мы хотим обрабатывать запросы пользователей в том порядке, в котором они поступают.

`ForkJoinPool` ради производительности жертвует справедливостью:

- Свои локальные очереди потоки обрабатывают по принципу **LIFO (Last In, First Out)**, то есть как стек. Поток берет последнюю добавленную задачу, так как её данные, скорее всего, еще горячие и лежат в L1-кэше процессора.
    
- Кража задач у соседей происходит по принципу FIFO (с другого конца очереди). В результате в `ForkJoinPool` порядок выполнения задач совершенно непредсказуем. Для миллионов микрозадач это нормально, но для маршрутизации классических HTTP-запросов такой хаос не всегда приемлем.
    

### 3. Проблема спящих потоков

Классические платформенные потоки **блокируют ядро процессора**, когда ждут ввода-вывода (I/O).

- Если вы отправите 200 долгих запросов к БД в `ThreadPoolExecutor` из 200 потоков, все они просто заснут, ожидая данные. Очередь будет стоять, пока кто-то не проснется. Пул к этому готов, это его нормальное состояние.
    
- Если вы отправите 200 классических блокирующих задач в `ForkJoinPool` размером в 8 потоков (по числу ядер), все 8 потоков быстро заблокируются в ожидании I/O. Никакой кражи работы не произойдет, потому что все рабочие потоки спят. Пул парализуется.
    

`ForkJoinPool` раскрывает свою эффективность только тогда, когда потоки **вычисляют, а не спят**. Именно поэтому до появления виртуальных потоков `ForkJoinPool` (появившийся еще в Java 7) использовался исключительно для CPU-bound задач (параллельные стримы `parallelStream()`, рекурсивная обработка массивов).

### Резюме эволюции

- **`ThreadPoolExecutor` (Java 5):** Оптимизирован для небольшого количества (сотни) "тяжелых", блокирующихся, разнородных задач. Единая очередь здесь — это простой, предсказуемый и надежный диспетчер.
    
- **`ForkJoinPool` (Java 7):** Оптимизирован для CPU-вычислений, где задачи разбиваются на тысячи мелких подзадач, которые не ждут сеть, а постоянно нагружают процессор.
    
- **Виртуальные потоки (Java 21):** JVM научилась перехватывать блокировки I/O. Теперь, когда задача ждет сеть, она освобождает Carrier-поток в `ForkJoinPool`. Благодаря этому I/O задачи перестали "усыплять" пул, и мы смогли использовать сверхбыструю архитектуру `ForkJoinPool` для типичных веб-серверов.

==Проблемы использования VirtualThreads==

Подводя итог, виртуальные потоки — это мощная технология для масштабирования высоконагруженных серверов, но они не являются "серебряной пулей".

Вот сводный список главных проблем и подводных камней, с которыми можно столкнуться при переходе на них:

1. **Thread Pinning (Пришпиливание потоков)**
    
    - **Суть:** Если виртуальный поток делает I/O-запрос, находясь внутри блока/метода `synchronized` или при вызове нативного кода (JNI), он теряет способность "отмонтироваться".
        
    - **Последствия:** Блокируется не только виртуальный поток, но и базовый платформенный (Carrier Thread). Если так сделают несколько потоков, весь пул парализуется, и приложение зависнет (хотя CPU и память будут свободны).
        
    - _Примечание: В Java 23 проблему с `synchronized` практически полностью решили (JEP 491), но для Java 21 она остается критичной._
        
2. **Исчерпание памяти из-за `ThreadLocal`**
    
    - **Суть:** В классической архитектуре у вас, например, 200 потоков и 200 экземпляров переменных `ThreadLocal` (в них часто хранят Security Context, ID транзакций, парсеры).
        
    - **Последствия:** Виртуальных потоков могут быть миллионы. Миллион виртуальных потоков = миллион копий данных в `ThreadLocal`. Из-за этого приложение может стремительно упасть с `OutOfMemoryError`.
        
3. **Узкие горлышки инфраструктуры (Bottlenecks)**
    
    - **Суть:** Ваш микросервис теперь легко может принять 100 000 одновременных запросов. Но инфраструктура к этому не готова.
        
    - **Последствия:** Базы данных (PostgreSQL, Oracle) физически не тянут десятки тысяч соединений. Если размер пула соединений (HikariCP) равен 100, то 99 900 виртуальных потоков будут просто стоять в бесконечной очереди за свободным коннектом. То же самое касается лимитов (Rate Limits) любых внешних API, к которым вы обращаетесь.
        
4. **Падение производительности на CPU-bound задачах**
    
    - **Суть:** Виртуальные потоки созданы **только** для задач ввода-вывода (I/O), где нужно много ждать.
        
    - **Последствия:** Если вы попытаетесь использовать их для тяжелой математики, шифрования, обработки изображений или парсинга гигантских файлов, код будет работать _медленнее_, чем на платформенных потоках. JVM будет тратить лишние ресурсы на упаковку и распаковку виртуальных потоков без какой-либо пользы.
        
5. **Несовместимость или "токсичность" старых библиотек**
    
    - **Суть:** Вы перешли на Java 21, но ваш любимый старый HTTP-клиент, драйвер экзотической базы данных или брокера сообщений внутри себя до сих пор использует `synchronized` для сетевых вызовов.
        
    - **Последствия:** Подключение одной такой библиотеки вернет в ваше приложение массовый Thread Pinning. Придется переписывать код, искать аналоги или ждать обновления от мейнтейнеров.
        
6. **Проблемы с мониторингом и отладкой (Thread Dumps)**
    
    - **Суть:** Классический текстовый дамп потоков (Thread Dump), который раньше занимал 2 МБ и легко читался глазами, теперь может содержать миллион записей.
        
    - **Последствия:** Старые системы мониторинга и IDE могут зависнуть при попытке снять или проанализировать такой дамп. Приходится переходить на новые форматы (например, выгрузка через `jcmd` в формате JSON) и использовать специальные утилиты для анализа.
        
7. **Монополизация процессора (Starvation)**
    
    - **Суть:** Виртуальный поток освобождает несущий поток _только_ в момент I/O-операции (или принудительного `Thread.yield()`).
        
    - **Последствия:** Если вы напишете цикл `while(true)` с вычислениями внутри виртуального потока и без сетевых вызовов, этот поток захватит ядро и никогда не отдаст его другим виртуальным потокам, нарушая баланс выполнения.

==Каким образом виртуальные потоки отцепляются от несущих==

Виртуальный поток принимает решение об отмонтировании (unmount) не сам по себе, а потому что **стандартные библиотеки Java были переписаны** под капотом. Когда ваш код вызывает метод, который подразумевает ожидание, этот метод проверяет: если текущий поток виртуальный, он сохраняет свое состояние и освобождает несущий платформенный поток.

Вот исчерпывающий список ситуаций, в которых виртуальный поток отцепляется от ядра:

- **Сетевой ввод-вывод (Network I/O):** Ожидание ответа по сети (TCP/UDP). Сюда входят вызовы HTTP-клиентов, чтение данных из `Socket.getInputStream().read()`, ожидание ответа от базы данных, брокера сообщений или кэша (если драйверы не используют устаревший `synchronized`).
    
- **Синхронизаторы из `java.util.concurrent`:** Попытка захватить занятый `ReentrantLock`, ожидание разрешений в `Semaphore`, ожидание на `CountDownLatch`, а также вызов `CompletableFuture.get()`.
    
- **Блокирующие очереди:** Попытка взять элемент из пустой очереди (например, `LinkedBlockingQueue.take()`) или положить элемент в уже переполненную очередь.
    
- **Режим сна (Sleep):** Вызов `Thread.sleep(ms)`. Вместо того чтобы отдавать команду операционной системе усыпить платформенный поток, JVM просто ставит виртуальный поток "на таймер" в памяти и немедленно освобождает ядро для других задач.
    
- **Ожидание монитора (с оговорками):** Вызов `Object.wait()` отцепляет поток, но сам процесс входа в блок `synchronized` (до Java 23) вызывает проблему "пришпиливания" (Pinning), поэтому этот механизм не рекомендуется использовать.
    
- **Явная уступка:** Вызов `Thread.yield()`. Поток добровольно говорит планировщику: "Я готов уступить процессорное время, верни меня в очередь".
    

### Как происходит сама "магия" отцепления

В основе механизма лежит внутренняя структура **Continuation (продолжение)**. Как только стандартная библиотека (например, сокет или `sleep`) понимает, что нужно подождать, она вызывает нативный метод `Continuation.yield()`. Этот метод берет текущий стек вызовов виртуального потока (информацию о том, в каком методе мы находимся и какие там локальные переменные) и **копирует его из оперативной памяти платформенного потока в общую кучу (Heap)** Java.

Как только данные скопированы в кучу, платформенный Carrier-поток очищает свой стек и берет следующую задачу из `ForkJoinPool`.

### Важный нюанс: Процессорные вычисления

Поскольку отмонтирование срабатывает только на I/O-операциях или блокировках, виртуальные потоки **не поддерживают вытесняющую многозадачность (Preemption) по времени**, в отличие от потоков ОС. Если вы запустите тяжелый цикл `while(true) { calculate() }` с математикой или парсингом гигантского JSON (без сетевых вызовов и без `Thread.sleep`), виртуальный поток монополизирует несущий поток ОС и **никогда** от него не отцепится, пока не завершит вычисления.

==Решение Thread Pinning==

Проблема "пришпиленных" потоков (Thread Pinning) стала главным препятствием для внедрения виртуальных потоков в Java 21. Однако в новых версиях платформы этот архитектурный недостаток был успешно устранен.

**В какой версии решили проблему?**

Критическое исправление было доставлено в **Java 24** (релиз в марте 2025 года) в рамках **JEP 491: Synchronize Virtual Threads without Pinning**. На сегодняшний день это улучшение доступно по умолчанию во всех последующих версиях, включая актуальный LTS-релиз **Java 25** (вышел в сентябре 2025 года).

**Как именно решили проблему Pinning?**

В Java 21 проблема заключалась во внутренних механизмах JVM. Ключевое слово `synchronized` опирается на мониторы объектов.

- **До Java 24:** JVM жестко связывала захваченный монитор с _платформенным потоком операционной системы_ (Carrier Thread), а не с виртуальным. Если виртуальный поток блокировался внутри `synchronized`, JVM физически не могла его отмонтировать, так как при переключении платформенного потока на другую задачу сломалась бы логика эксклюзивного доступа.
    
- **С выходом JEP 491:** Архитектура управления мониторами была полностью переписана. Теперь монитор объекта привязывается к _идентичности самого виртуального потока_ независимо от ядра. Это позволяет виртуальному потоку спокойно отмонтироваться внутри блока `synchronized` или при вызове `Object.wait()`, освободить Carrier-поток, а при возврате данных — корректно продолжить работу.
    

**Доступно ли это обновление в Java 21?**

**Нет, бэкпорта не существует**. Изменения потребовали слишком глубокой переработки ядра JVM и системы управления памятью. Если ваш проект остается на Java 21 LTS, проблема Pinning для вас полностью актуальна. Вам по-прежнему придется вручную заменять `synchronized` на `ReentrantLock` и следить за тем, чтобы все библиотеки (например, драйверы БД) были адаптированы под старую модель виртуальных потоков.

**Где проблема Pinning ВСЁ ЕЩЁ актуальна (в Java 24/25+)?**

Хотя JEP 491 устранил 99% случаев пришпиливания в пользовательском коде, архитектурные ограничения JVM не позволяют отмонтировать поток в нескольких узких сценариях:

1. **Нативный код (JNI / FFM API):** Если виртуальный поток вызывает C/C++ код и блокируется внутри него, он намертво пришпиливает Carrier-поток. JVM не имеет контроля над нативной памятью и не может скопировать системный стек языка C в кучу Java.
    
2. **Блоки статической инициализации:** Выполнение долгих I/O операций внутри блоков загрузки классов (`static { ... }`) по-прежнему вызывает Pinning.
    
3. **Локальная файловая система:** В зависимости от ОС (например, специфические операции в Linux), если ядро не поддерживает неблокирующий ввод-вывод для конкретного вызова, JVM не сможет отмонтировать поток.
    

В современных проектах на Java 25+ больше не нужно маниакально переписывать старый код с `synchronized`, но мониторинг события `jdk.VirtualThreadPinned` через Java Flight Recorder все еще остается стандартом профилирования для отслеживания нативных блокировок.

==Проблема ThreadLocal и ScopedValues==

`ThreadLocal` был спроектирован в эпоху, когда потоки были дорогим ресурсом: их было мало (сотни), и они жили долго (в пуле). Для миллионов короткоживущих виртуальных потоков он превратился в механизм, стремительно пожирающий оперативную память.

Технология **Scoped Values** решает эту проблему, кардинально меняя подход к хранению контекста: она заменяет изменяемые, "вечные" переменные на **неизменяемые данные с жестко ограниченным временем жизни**.

## Почему ThreadLocal ломает память

У `ThreadLocal` есть три фатальных недостатка при работе с виртуальными потоками:

1. **Тяжеловесная структура:** Внутри каждого потока создается специальная хэш-таблица (`ThreadLocalMap`). Миллион потоков = миллион хэш-таблиц.
    
2. **Утечки памяти:** Если разработчик забыл вызвать `threadLocal.remove()` в блоке `finally`, объект остается в памяти навсегда.
    
3. **Дорогое наследование:** Чтобы передать контекст из родительского потока в дочерний (например, через `InheritableThreadLocal`), JVM вынуждена физически копировать данные из одной таблицы в другую.
    

## Как работают Scoped Values

Scoped Values полностью избавляются от хэш-таблиц и копирования за счет строгой лексической области видимости.

### 1. Жесткие границы времени жизни (Lexical Scope)

Вы не можете просто вызвать метод `set()`, как это было раньше. Значение задается только для конкретного блока кода (`Runnable` или `Callable`). Как только этот блок завершает выполнение, значение автоматически становится недоступным.

Java

```java
// Объявляем константу (обычно static final)
public static final ScopedValue<UserContext> USER = ScopedValue.newInstance();

// В точке входа (например, в HTTP-фильтре):
UserContext context = new UserContext("admin_user");

// Привязываем значение только к выполнению метода processRequest
ScopedValue.where(USER, context)
           .run(() -> processRequest()); 
```

Где-то глубоко внутри `processRequest` (или в вызываемых им методах) вы можете безопасно прочитать значение:

Java

```java
public void processRequest() {
    // Получаем значение без передачи его через аргументы методов
    UserContext ctx = USER.get(); 
}
```

**Результат:** Как только метод `processRequest` завершается, ссылка на `UserContext` уничтожается мгновенно. Сборщик мусора (GC) сразу освобождает память, и вам не нужно вызывать никаких аналогов `.remove()`.

### 2. Абсолютная неизменяемость (Immutability)

Получив значение через `USER.get()`, вы не можете его переопределить. Если внутри `processRequest` вам нужно запустить подзадачу с другим контекстом, вы создаете новую область видимости (Shadowing):

Java

```
ScopedValue.where(USER, new UserContext("system_user"))
           .run(() -> runSystemTask());
```

Внутри `runSystemTask` значение `USER` будет равно `"system_user"`. Как только задача завершится, в родительском методе оно снова будет `"admin_user"`.

### 3. Бесплатное наследование дочерними потоками

Это главное преимущество Scoped Values при масштабировании. Поскольку данные неизменяемы, JVM больше не нужно создавать копии контекста для каждого дочернего потока. Если родительский виртуальный поток запускает 10 000 дочерних подзадач, **все они безопасно читают один и тот же участок памяти** без блокировок и копирования массивов. Накладные расходы на память при передаче контекста снижаются до нуля.
