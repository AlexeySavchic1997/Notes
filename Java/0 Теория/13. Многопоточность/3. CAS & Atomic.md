Классы из пакета `java.util.concurrent.atomic` — это мост между абстракциями Java и аппаратными инструкциями процессора. Они позволяют изменять данные потокобезопасно, вообще не прибегая к блокировкам на уровне операционной системы (Lock-free парадигма).

Давай разберем эту механику до уровня процессора.

## 1. Что под капотом у AtomicInteger?

Внутри `AtomicInteger` нет никаких `synchronized` блоков или `ReentrantLock`. Вся его архитектура держится на двух китах:

1. **`private volatile int value;`** Значение хранится как `volatile`. Как мы разбирали ранее, это гарантирует, что любой поток, читающий это поле (через метод `get()`), мгновенно увидит самые свежие данные из RAM, минуя L1/L2 кэши.
    
2. **`VarHandle` (до Java 9 — `Unsafe`)** Это внутренний API виртуальной машины, который позволяет Java-коду выполнять низкоуровневые операции с памятью по конкретным адресам, обращаясь напрямую к инструкциям процессора.
    

## 2. Алгоритм CAS (Compare-And-Swap)

Когда ты вызываешь метод `atomic.incrementAndGet()`, под капотом выполняется алгоритм **CAS**.

CAS — это не просто концепция, это **одна атомарная машинная инструкция** (например, `LOCK CMPXCHG` в архитектуре x86). Поскольку это делает сам процессор на аппаратном уровне, никакой другой поток физически не может вклиниться в процесс ее выполнения.

Операция принимает три аргумента:

- **V (Memory Value):** Текущее реальное значение в оперативной памяти.
    
- **A (Expected Value):** Значение, которое поток прочитал до начала вычислений (ожидаемое).
    
- **B (New Value):** Новое значение, которое поток хочет записать.
    

**Логика работы процессора:**

- Если `V == A` (никто не изменил память, пока мы считали), процессор записывает `B` в память и возвращает `true`.
    
- Если `V != A` (какой-то другой поток успел вклиниться и изменить значение), процессор ничего не записывает и возвращает `false`.
    

**Как это выглядит в Java (Spin-loop):** Так как CAS может вернуть `false`, атомарные классы оборачивают его в бесконечный цикл (busy-wait или spin-loop).

Java

```
public final int incrementAndGet() {
    int current;
    int next;
    do {
        current = this.get();        // 1. Читаем V (volatile read)
        next = current + 1;          // 2. Вычисляем B
        // 3. Пытаемся атомарно подменить A на B
    } while (!compareAndSet(current, next)); 
    
    return next;
}
```

Если другой поток успеет инкрементировать счетчик между строками 1 и 3, `compareAndSet` вернет `false`. Наш поток не упадет в блокировку ОС — он просто пойдет на следующую итерацию цикла `do-while`, прочитает новое свежее значение и попробует снова. Это очень быстро, так как поток не снимается с ядра процессора.

## 3. Проблема ABA

Алгоритм CAS кажется идеальным, но у него есть архитектурная уязвимость — проблема ABA. CAS проверяет только **совпадение значений**, но не проверяет **историю их изменений**.

**Сценарий аномалии:**

1. Поток 1 читает значение `A` из памяти.
    
2. Поток 1 приостанавливается планировщиком ОС.
    
3. Поток 2 записывает новое значение `B`.
    
4. Поток 3 записывает обратно значение `A`.
    
5. Поток 1 просыпается, выполняет инструкцию `CAS(ожидаю A, пишу новую дату)`.
    
6. С точки зрения процессора текущее значение памяти равно `A`. CAS успешно отрабатывает!
    

**Почему это критично?** Для простого счетчика (`AtomicInteger`) проблема ABA не имеет значения — если баланс был 100, стал 50, а потом снова 100, прибавление единицы всё равно даст корректные 101.

Но эта проблема становится фатальной при написании **Lock-free структур данных** (например, `ConcurrentLinkedQueue`). В них значением часто выступает ссылка на узел (Node). Если Поток 1 хочет удалить `Node A`, а в это время Поток 2 удалил `Node A`, удалил `Node B`, и затем по какой-то причине снова положил старый объект `Node A` в начало очереди, его внутренние указатели `next` будут указывать уже на совершенно другие области памяти. CAS Потока 1 пройдет успешно (ссылка `A` совпала), и структура данных будет необратимо повреждена (потеряны связи между узлами).

## 4. Решение: AtomicStampedReference

Чтобы победить ABA, в Java был добавлен класс `AtomicStampedReference<V>`. Он решает проблему путем добавления **версионирования (Stamp)**.

Вместо одного значения он хранит пару: `[Ссылка на объект, Версия]`. Теперь CAS должен атомарно проверить сразу два условия:

1. Совпадает ли ожидаемая ссылка?
    
2. Совпадает ли ожидаемая версия (stamp)?
    

В сценарии ABA Поток 3, возвращая значение `A`, инкрементирует версию (например, с `1` на `3`). Когда Поток 1 проснется, он попытается выполнить CAS с ожидаемой версией `1`. Операция отклонится, и целостность структуры данных будет сохранена.
