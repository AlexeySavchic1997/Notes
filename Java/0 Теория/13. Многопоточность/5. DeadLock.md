**Deadlock (Взаимная блокировка)** — это состояние системы, при котором два или более потока навсегда блокируются на уровне операционной системы (переходят в состояние `BLOCKED` или `WAITING`), ожидая освобождения ресурсов (мониторов), которые удерживаются ими же самими.

Главная архитектурная проблема Deadlock в Java заключается в том, что **JVM не умеет автоматически разрешать дедлоки**. В отличие от баз данных (например, PostgreSQL), где специальный фоновый процесс находит кольцевые блокировки и принудительно "убивает" одну из транзакций с исключением, в Java потоки просто зависают навсегда. Процессор (CPU) при этом не грузится, но приложение (или его часть) перестает отвечать на запросы. Поможет только перезапуск (kill -9).

Для возникновения дедлока должны сойтись **4 условия Коффмана** (если нарушить хотя бы одно, дедлок невозможен):

1. **Mutual exclusion:** Ресурс может удерживаться только одним потоком.
    
2. **Hold and wait:** Поток уже захватил ресурс А и ждет захвата ресурса Б.
    
3. **No preemption:** Нельзя принудительно отобрать монитор у потока, который его уже захватил.
    
4. **Circular wait (Кольцевое ожидание):** Поток 1 ждет Поток 2, а Поток 2 ждет Поток 1.
    

### Классические сценарии на Production

Дедлоки на проде редко выглядят как явные `synchronized` блоки, написанные подряд. Обычно они скрыты под слоями бизнес-логики и фреймворков.

#### Сценарий 1. Нарушение порядка блокировок (Lock Ordering)

Классический пример — перевод денег между счетами. У нас есть метод:

Java

```
public void transfer(Account from, Account to, int amount) {
    synchronized (from) { // Блокируем счет отправителя
        synchronized (to) { // Блокируем счет получателя
            from.withdraw(amount);
            to.deposit(amount);
        }
    }
}
```

**Как это падает на проде:** Пользователь А переводит деньги Пользователю Б (Поток 1 выполняет `transfer(A, B)`). Ровно в эту же миллисекунду Пользователь Б переводит деньги Пользователю А (Поток 2 выполняет `transfer(B, A)`).

- Поток 1 захватывает монитор объекта `A`.
    
- Поток 2 захватывает монитор объекта `B`.
    
- Поток 1 пытается захватить `B` и блокируется.
    
- Поток 2 пытается захватить `A` и блокируется. Дедлок.
    

#### Сценарий 2. Скрытый дедлок пула соединений БД (Connection Pool Starvation)

Встречается в Spring-приложениях при неправильном управлении транзакциями. Допустим, размер пула соединений HikariCP равен 10. Приходит 10 одновременных запросов. Каждый запрос открывает транзакцию (берет соединение 1..10). Внутри бизнес-логики вызывается метод с аннотацией `@Transactional(propagation = Propagation.REQUIRES_NEW)`. Эта пропэгейшн требует **приостановить текущую транзакцию и открыть абсолютно новое соединение**. Но пул пуст (все 10 соединений заняты родительскими методами). Итог: 10 потоков держат по одному соединению и бесконечно ждут, пока пул выдаст им второе. Дедлок.

### Как решать и предотвращать дедлоки (Уровень Senior)

#### 1. Глобальный порядок блокировок (Разрыв Circular Wait)

Это решение для Сценария 1. Чтобы избежать кольцевого ожидания, все потоки в приложении должны всегда захватывать мониторы в строго определенном порядке. Например, сортировать объекты по их уникальному `id` (или хэш-коду) перед блокировкой.

Java

```
public void transferSafe(Account a, Account b, int amount) {
    // Всегда сначала блокируем счет с меньшим ID
    Account firstLock = (a.getId() < b.getId()) ? a : b;
    Account secondLock = (a.getId() < b.getId()) ? b : a;

    synchronized (firstLock) {
        synchronized (secondLock) {
            // ... перевод ...
        }
    }
}
```

Теперь, даже если переводы встречные (`A->B` и `B->A`), оба потока сначала попытаются захватить монитор с меньшим ID. Один захватит, второй будет ждать. Кольца не возникнет.

#### 2. Использование ReentrantLock с таймаутом (Разрыв Hold and wait)

Вместо жесткого `synchronized`, который заставляет поток ждать бесконечно, в критичных местах используют API из `java.util.concurrent.locks`.

Метод `tryLock(timeout)` позволяет попытаться захватить ресурс, и если не вышло — откатиться, отпустить уже занятые ресурсы и попробовать позже.

Java

```
Lock lockA = a.getLock();
Lock lockB = b.getLock();

if (lockA.tryLock(100, TimeUnit.MILLISECONDS)) {
    try {
        if (lockB.tryLock(100, TimeUnit.MILLISECONDS)) {
            try {
                // ... перевод ...
            } finally {
                lockB.unlock();
            }
        }
    } finally {
        lockA.unlock();
    }
}
```

#### 3. Диагностика "наживую" (jstack / jcmd)

Если дедлок уже случился на проде, и система висит, разработчик подключается к серверу по SSH и снимает дамп потоков.

Команда ОС: `jcmd <PID> Thread.print` или `jstack <PID>`.

JVM имеет встроенный детектор дедлоков. В самом конце сгенерированного лога будет четко написано:

Plaintext

```
Found one Java-level deadlock:
=============================
"Thread-1":
  waiting to lock monitor 0x00007f... (object 0x000...a, a Account),
  which is held by "Thread-2"
"Thread-2":
  waiting to lock monitor 0x00007f... (object 0x000...b, a Account),
  which is held by "Thread-1"
```

Это позволяет сразу найти классы и строки кода, где произошла взаимная блокировка.
