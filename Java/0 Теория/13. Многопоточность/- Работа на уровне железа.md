Системный поток (OS Thread) — это не абстрактная сущность, а физическое состояние процессора в конкретный момент времени и строго выделенный блок памяти, которым управляет ядро операционной системы. Процессор (CPU) сам по себе не знает о потоках — он просто выполняет инструкции по адресам, которые ему подсовывают.

## Анатомия системного потока

Чтобы ядро ОС могло поставить поток на паузу и затем возобновить его, оно должно сохранить его полный «слепок». Этот слепок состоит из трех фундаментальных частей:

- **Program Counter (PC):** Регистр процессора, хранящий адрес следующей машинной инструкции. Это «палец», которым CPU водит по вашему скомпилированному коду. Без него процессор забыл бы, на какой строке остановился.
    
- **Стек вызовов (Call Stack):** Изолированный кусок оперативной памяти (в Java по умолчанию 1 МБ на поток), где хранятся локальные примитивы, ссылки на объекты (сами объекты лежат в Heap) и адреса возврата из методов.
    
- **Stack Pointer (SP) и регистры общего назначения:** Stack Pointer указывает на вершину стека текущего метода, а в остальных физических регистрах процессора лежат промежуточные результаты вычислений (например, результаты сложения двух чисел до их записи в память).
    

## Механика переключения контекста (Context Switch)

Когда планировщик ОС (Scheduler) решает, что квант времени потока А истек и пора выполнить поток Б, запускается тяжелая и ресурсоемкая процедура:

1. **Аппаратное прерывание:** Таймер процессора посылает сигнал, выполнение пользовательского кода принудительно останавливается.
    
2. **Смена привилегий (Mode Switch):** Процессор переключается из User Space (где работает ваша Java-программа) в Kernel Space (режим ядра ОС). Это требует выполнения тяжелых системных вызовов (syscalls).
    
3. **Сохранение состояния (Save state):** Ядро берет текущие значения всех физических регистров CPU (включая PC и SP) и записывает их в оперативную память в специальную структуру — Thread Control Block (TCB) потока А.
    
4. **Восстановление состояния (Restore state):** Ядро находит в памяти TCB потока Б, считывает оттуда сохраненные ранее значения его регистров и жестко перезаписывает ими физические регистры процессора.
    
5. **Возврат в User Space:** Процессор видит в регистре Program Counter адрес инструкции потока Б и просто продолжает работу с этого места.
    

## Истинная цена переключения

Само по себе копирование пары десятков регистров в память занимает микросекунды. Настоящая проблема Context Switch кроется в косвенных потерях:

- **Сброс конвейера (Pipeline Flush):** Современные процессоры предсказывают ветвления и выполняют инструкции наперед. При смене потока весь этот предвычисленный прогресс сбрасывается.
    
- **Деградация кэшей (Cache Pollution):** Когда просыпается поток Б, в сверхбыстрых L1 и L2 кэшах процессора лежат данные потока А. Потоку Б приходится вытеснять их и тянуть свои данные из медленной оперативной памяти (Cache Miss), простаивая сотни тактов.
    

Именно поэтому создание 100 000 системных потоков убьет приложение: львиная доля времени CPU будет уходить не на полезную работу, а на бесконечное переписывание регистров и прогрев кэшей.

В стандартной виртуальной машине Java (HotSpot) до появления Virtual Threads **нет физического разделения** между «системным стеком» и «стеком Java». Это один и тот же непрерывный блок оперативной памяти (обычно 1 МБ), который выделяется операционной системой при рождении потока.

Java-поток — это абстракция (обертка) над нативным OS-потоком. Когда выполняется Java-код, фреймы методов кладутся на этот системный стек. Если Java делает системный вызов или использует JNI (вызывает C++ код), нативные фреймы ложатся поверх Java-фреймов в тот же самый стек. ОС видит только единый системный стек, в котором лежат перемешанные данные.

## Зачем нужен Stack Pointer (SP)

Стек — это просто пустая "труба" зарезервированной памяти. Сам по себе он пассивен. Процессор не знает, сколько памяти внутри этого мегабайта уже занято переменными, а сколько еще свободно.

**Stack Pointer (SP)** — это физический регистр внутри процессора, который работает как указатель уровня. Он всегда хранит точный адрес памяти, где заканчиваются полезные данные и начинается свободное место. Без SP процессор просто не знал бы, по какому адресу записывать новую локальную переменную так, чтобы не затереть старые.

## Синергия: как они работают вместе

Представим, что мы находимся внутри метода `A()`, который сейчас вызовет метод `B()`. Вот как взаимодействуют регистры и память на аппаратном уровне:

1. **Нормальное выполнение:** **Program Counter (PC)** хранит адрес текущей инструкции внутри метода `A()`. Процессор выполняет ее, и PC сдвигается на шаг вперед. **Stack Pointer (SP)** указывает на вершину стека, где лежат локальные переменные метода `A()`.
    
2. **Момент вызова:** Процессор доходит до инструкции `CALL B()`.
    
3. **Сохранение пути назад:** Процессору нужно будет вернуться в метод `A()` после завершения `B()`. Поэтому он берет текущее значение **PC** (адрес следующей строки в `A()`) и _записывает_ его в память по адресу, на который сейчас указывает **SP** (кладет в стек).
    
4. **Сдвиг вершины:** Так как в стек только что положили данные, процессор автоматически сдвигает **SP** (обычно уменьшает адрес), чтобы он снова указывал на свободное место.
    
5. **Прыжок в новый метод:** Процессор принудительно записывает в **PC** адрес начала метода `B()`. Теперь, на следующем такте, процессор начнет читать код метода `B()`.
    
6. **Выделение памяти (Frame Allocation):** Метод `B()` при старте сдвигает **SP** еще дальше, резервируя место в стеке под свои собственные локальные переменные.
    
7. **Возврат (Return):** Когда метод `B()` заканчивается, он возвращает **SP** на прежнее место (уничтожая свои локальные переменные). Процессор читает из стека сохраненный ранее адрес возврата, записывает его обратно в **PC**, и выполнение метода `A()` продолжается ровно с того места, где прервалось.
    

Без **PC** процессор не знает, _какую команду_ выполнять. Без **SP** процессор не знает, _где в памяти_ лежат данные текущего метода и куда сохранять историю вызовов.

## Thread Control Block (TCB): "Паспорт" потока

Когда JVM (через системный вызов) просит операционную систему создать новый поток, ОС выделяет в оперативной памяти тот самый 1 МБ под стек и создает для этого потока специальную структуру данных — **Thread Control Block (TCB)**.

TCB хранится в строго защищенной области памяти ядра (Kernel Space), куда пользовательский код (Java) не имеет доступа. В этом TCB записана вся мета-информация о потоке, включая:

1. Уникальный ID потока (TID).
    
2. Статус (готов к выполнению, заблокирован, спит).
    
3. **Слепок регистров:** Те самые сохраненные значения Program Counter (PC), Stack Pointer (SP) и других регистров на момент, когда поток в последний раз ставили на паузу.
    

ОС хранит все TCB в виде списка (или дерева) в своей памяти.

## Как происходит поиск и загрузка (шаг за шагом)

Представьте, что сработал аппаратный таймер (прерывание), и операционная система решила, что пора убрать поток А с ядра процессора и поставить туда поток Б (ваш Java-поток).

1. **Выбор планировщика (Scheduler):** Код ядра ОС просматривает список TCB и по своим алгоритмам выбирает поток Б, у которого статус _Ready_ (готов к выполнению).
    
2. **Извлечение адресов:** Ядро обращается к TCB потока Б. В этом TCB черным по белому записано: когда этот поток остановили в прошлый раз, его Stack Pointer смотрел на адрес `0x7FFF0010`, а Program Counter — на адрес `0x00401A3B`.
    
3. **Перезапись железа:** Ядро берет эти числа из TCB (из памяти) и физически переписывает ими реальные железные регистры SP и PC внутри процессора.
    
4. **Запуск:** Ядро передает управление обратно. Процессор смотрит в свой регистр PC, видит там адрес `0x00401A3B` и идет туда читать следующую команду. Он смотрит в SP, видит там `0x7FFF0010`, и теперь знает, что вершина стека находится именно там.
    

## Как стек попадает в кэши (L1/L2/L3)

Процессор **не загружает весь стек целиком** в кэш при переключении контекста. Это было бы слишком долго. Загрузка происходит лениво, "по требованию", благодаря аппаратному механизму.

1. Процессор читает команду из PC: например, `POP EAX` (взять значение с вершины стека и положить в регистр).
    
2. Процессор смотрит в регистр SP, чтобы узнать адрес вершины стека (`0x7FFF0010`).
    
3. Процессор стучится в кэш L1 и спрашивает: "У тебя есть данные по адресу `0x7FFF0010`?".
    
4. Сразу после переключения потока кэш L1 забит чужими данными (потока А). Происходит **Cache Miss** (промах кэша).
    
5. Процессор обращается к L2, затем к L3, затем идет в контроллер оперативной памяти.
    
6. Контроллер памяти берет из RAM кусок данных (обычно 64 байта, это называется **Cache Line**), в который попадает нужный адрес, и копирует его в L3, затем в L2, и наконец в L1.
    
7. Процессор берет число из L1 и кладет в регистр.
    

Когда поток только проснулся, первые сотни обращений к стеку вызовут цепочку _Cache Miss_, заставляя процессор простаивать, ожидая данные из медленной RAM. Это и называется "прогревом кэша" после переключения контекста.
