Разработчики Project Loom сделали гениальную вещь: они не стали создавать новые интерфейсы. Они встроили виртуальные потоки в старый добрый класс `java.lang.Thread` и интерфейс `ExecutorService`. Благодаря этому тебе не нужно переписывать половину приложения.

Вот 3 основных способа использования виртуальных потоков в коде, от простых скриптов до production-решений.

### Способ 1. Быстрый запуск (Thread Builder API)

В Java 21 появился удобный паттерн Строитель (Builder) для создания потоков. Это идеально подходит для разовых фоновых асинхронных задач.

```Java
public class VirtualThreadBasic {
    public static void main(String[] args) throws InterruptedException {
        // Способ А: Запустить безымянный виртуальный поток в одну строку
        Thread.startVirtualThread(() -> {
            System.out.println("Привет из " + Thread.currentThread());
        });

        // Способ Б: Использовать Builder (если нужно задать имя или обработчик ошибок)
        Thread vThread = Thread.ofVirtual()
                .name("db-fetcher-", 1) // Имя будет db-fetcher-1
                .start(() -> {
                    try {
                        // Имитируем I/O блокировку (поход в БД)
                        Thread.sleep(1000); 
                        System.out.println("Данные получены потоком: " + Thread.currentThread().getName());
                    } catch (InterruptedException e) {
                        Thread.currentThread().interrupt();
                    }
                });

        // Основной поток ждет завершения виртуального
        vThread.join(); 
    }
}
```

### Способ 2. Массовый запуск (Через ExecutorService)

Это **главный паттерн для продакшена**. Если у тебя есть сотни или тысячи независимых задач (например, отправить 10 000 email-ов или сделать парсинг 5 000 веб-страниц), ты используешь специальный Executor.

> **Важно:** Этот Executor **не пулит (не переиспользует)** потоки! Под каждую задачу `submit()` он создает абсолютно новый виртуальный поток, а после завершения задачи поток уничтожается.


```Java
import java.time.Duration;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.stream.IntStream;

public class VirtualThreadExecutor {
    public static void main(String[] args) {
        long start = System.currentTimeMillis();

        // Используем try-with-resources. 
        // При выходе из блока метод close() дождется выполнения всех 10 000 потоков.
        try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
            
            IntStream.range(0, 10_000).forEach(i -> {
                executor.submit(() -> {
                    try {
                        // Каждая задача "засыпает" на 1 секунду (имитация долгого HTTP-запроса)
                        // В платформенных потоках это вызвало бы OutOfMemoryError.
                        // Здесь Carrier Thread мгновенно берет следующую задачу.
                        Thread.sleep(Duration.ofSeconds(1));
                    } catch (InterruptedException e) {
                        Thread.currentThread().interrupt();
                    }
                });
            });
            
            System.out.println("Все задачи отправлены. Ждем...");
        } // Здесь происходит неявный executor.close()

        long time = System.currentTimeMillis() - start;
        // Код выполнится чуть больше чем за 1 секунду! (а не за 10 000 секунд)
        System.out.println("Выполнено 10 000 блокирующих задач за: " + time + " мс");
    }
}
```

### Способ 3. Замена Spring WebFlux (Синхронный код с I/O)

Посмотри, как элегантно теперь выглядит вызов нескольких микросервисов. Раньше нам приходилось использовать цепочки `CompletableFuture` или реактивный `Mono.zip()`. С виртуальными потоками мы пишем линейный код.

```Java
import java.util.concurrent.Executors;
import java.util.concurrent.Future;

public class SyncAsyncExample {
    
    public UserProfile fetchUserProfile(String userId) throws Exception {
        try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
            
            // Запускаем два долгих сетевых запроса ОДНОВРЕМЕННО в виртуальных потоках
            Future<String> userFuture = executor.submit(() -> fetchUserFromDb(userId));
            Future<String> ordersFuture = executor.submit(() -> fetchOrdersFromApi(userId));
            
            // Линейно ждем результатов. 
            // Поток НЕ простаивает на ядре процессора в ожидании .get()!
            // Он демонтируется в Heap и освобождает ресурсы ОС.
            String user = userFuture.get(); 
            String orders = ordersFuture.get();
            
            return new UserProfile(user, orders);
        }
    }

    private String fetchUserFromDb(String id) throws InterruptedException {
        Thread.sleep(1000); return "User Data";
    }
    private String fetchOrdersFromApi(String id) throws InterruptedException {
        Thread.sleep(1500); return "Orders Data";
    }
}
```

### Архитектурный Антипаттерн (Как НЕ надо делать)

Никогда не пытайся засунуть фабрику виртуальных потоков в `FixedThreadPool` или любой другой пул, ограничивающий размер.


```Java
// ❌ ГРУБАЯ ОШИБКА: Пул для виртуальных потоков!
ThreadFactory factory = Thread.ofVirtual().factory();
ExecutorService badExecutor = Executors.newFixedThreadPool(10, factory); 
```

Виртуальные потоки созданы для того, чтобы их количество измерялось миллионами. Их создание стоит копейки (как `new Object()`). Ограничивать их количество числом 10 — значит убить всю архитектуру Project Loom.

==Что можно и чего нельзя использовать с виртуальными потоками== 
Это, пожалуй, **самый важный архитектурный вопрос** при переходе на виртуальные потоки.

Ты уловил саму суть: чтобы виртуальный поток успешно "сбросился в Heap" (демонтировался) и освободил несущий поток (Carrier Thread), блокирующий вызов должен быть **"Virtual-Thread-Aware"** (осведомленным о виртуальных потоках).

Хорошая новость в том, что инженеры Oracle потратили несколько лет на то, чтобы переписать **почти всю стандартную библиотеку Java (JDK)**. Плохая новость в том, что остались две критические зоны, которые "прибивают" (Pin) виртуальный поток к несущему гвоздями.

Давай разделим все операции на безопасные (зеленая зона) и опасные (красная зона).

### 🟢 Зеленая зона: Безопасные операции (Сбрасывают в Heap)

Эти методы переписаны в JDK 21. Когда виртуальный поток вызывает любой из них, JVM перехватывает вызов на нижнем уровне, вызывает внутренний метод `Continuation.yield()`, сохраняет стек потока в Heap и освобождает ядро процессора. Несущий поток **не блокируется**.

1. **Многопоточные инструменты (JUC):**
    
    - `Future.get()` и `CompletableFuture.join()`
        
    - Любые блокировки из `java.util.concurrent.locks`: `ReentrantLock.lock()`, `ReadWriteLock`, `StampedLock`.
        
    - Синхронизаторы: `CountDownLatch.await()`, `Semaphore.acquire()`, `CyclicBarrier`.
        
    - Очереди: `BlockingQueue.take()` и `.put()`.
        
2. **Сетевой I/O:**
    
    - Стандартные сокеты: `Socket.getInputStream().read()`, `Socket.connect()`.
        
    - HTTP-клиенты: `java.net.http.HttpClient`, старый `HttpURLConnection`.
        
    - **JDBC Драйверы:** Практически все драйверы (PostgreSQL, MySQL) под капотом используют обычные Java-сокеты, поэтому вызов `statement.executeQuery()` безопасно демонтирует поток, пока БД готовит ответ.
        
3. **Управление потоком:**
    
    - `Thread.sleep()`
        
    - `Thread.yield()`
        

### 🔴 Красная зона: Опасные операции (Pinning / Привязка)

Если виртуальный поток вызывает блокирующую операцию, находясь в этой зоне, JVM физически не может отделить стек виртуального потока от стека ОС. **Несущий поток ОС блокируется вместе с ним.** Если у тебя 10 несущих потоков, и 10 виртуальных потоков попали в красную зону и ждут ответа от сети — всё твое приложение зависнет (Starvation).

1. **Блок `synchronized` и методы `Object.wait()`**
    
    - Это главный бич Project Loom. Если ты делаешь сетевой запрос или засыпаешь _внутри_ блока `synchronized`, несущий поток блокируется.
        
    - **Решение:** Заменять все долгие `synchronized` на `ReentrantLock.lock()`.
        
2. **Нативный код (JNI)**
    
    - Если блокировка происходит внутри C/C++ кода, вызванного через Java Native Interface. JVM не умеет управлять стеками C-кода, поэтому не может сохранить их в Heap.
        
3. **Файловый I/O на локальном диске (Частично)**
    
    - Чтение файлов с диска исторически очень сложно сделать неблокирующим на уровне ОС без потерь. В JDK 21 файловый I/O переписан, он пытается не блокировать ядро, но в некоторых специфичных системных вызовах может происходить кратковременный Pinning. Для диска это не так критично, как для сети (диск отвечает за микросекунды, а сеть — за секунды).
        

### Архитектурный пример: Как сломать систему (Pinning)

Смотри, как легко убить приложение, добавив всего одно слово `synchronized`.

Java

```Java
public class PinningExample {
    
    // ОШИБКА! Ключевое слово synchronized "прикалывает" виртуальный поток к ОС-потоку.
    public synchronized String fetchBad(String id) throws Exception {
        // Здесь виртуальный поток попытается демонтироваться, 
        // но JVM увидит synchronized-монитор и ЗАБЛОКИРУЕТ реальное ядро CPU!
        Thread.sleep(5000); 
        return "Data";
    }

    private final ReentrantLock lock = new ReentrantLock();

    // ПРАВИЛЬНО! ReentrantLock написан на Java, он умеет демонтировать потоки.
    public String fetchGood(String id) throws Exception {
        lock.lock();
        try {
            // Виртуальный поток безопасно сбросится в Heap. Ядро CPU свободно!
            Thread.sleep(5000); 
            return "Data";
        } finally {
            lock.unlock();
        }
    }
}
```

### 🛠️ Как отловить Pinning на продакшене?

Тебе не нужно угадывать, какие библиотеки под капотом используют `synchronized`, а какие нет. JVM сама может тебе об этом рассказать.

При запуске приложения добавь специальный флаг JVM: `-Djdk.tracePinnedThreads=full` (или `short`).

Когда любой виртуальный поток заблокирует несущий поток ОС, в консоль вылетит подробный StackTrace с указанием точной строчки кода, где это произошло:

Plaintext

```
Thread[#26,ForkJoinPool-1-worker-1,5,CarrierThreads]
    java.base/java.lang.VirtualThread$VThreadContinuation.onPinned(VirtualThread.java:183)
    ...
    com.example.MyService.badMethod(MyService.java:42) <== pinned by monitor!
```

Также эти события (Pinned Threads) отлично видны в профайлере **Java Flight Recorder (JFR)**.
