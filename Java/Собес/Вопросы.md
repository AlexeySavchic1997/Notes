### 🏗 Блок 1: Микросервисы и Архитектура (Questions 1-5)

На Middle/Senior позициях интервьюеры любят начинать с общих вопросов про микросервисы, чтобы понять ваше системное мышление.

**1. Why did you choose microservices over a monolith for your project?** _(Почему вы выбрали микросервисы, а не монолит для вашего проекта?)_

> "Microservices allow us to scale parts of the system independently. For example, we can scale the warehouse service without scaling payments. Also, if one service crashes, the whole system doesn't die. The trade-off is that it makes deployment and debugging much harder."

**2. How do you handle transactions between different microservices?** _(Как вы обрабатываете транзакции между разными микросервисами? — Это супер-популярный вопрос!)_

> "We cannot use standard `@Transactional` across different databases. Instead, we use the **SAGA pattern**. We use Kafka to send events between services. If one step fails, we send a 'compensation event' to undo the previous steps."

**3. What is the difference between synchronous and asynchronous communication? When do you use them?** _(В чем разница между синхронным и асинхронным взаимодействием? Когда вы их используете?)_

> "**Synchronous** communication means the client waits for the response. I use **gRPC** or REST for this, for example, when I need to get user data immediately. **Asynchronous** communication means the client sends a message and doesn't wait. I use **Kafka** for this, for example, for sending email notifications or logging."

**4. How do you secure microservice-to-microservice communication?** _(Как вы защищаете общение между микросервисами?)_

> "We usually use **JWT** (JSON Web Tokens). When a user logs in, the Auth service generates a token. Then, the client sends this token in the HTTP or gRPC header to other services. The services validate the token signature to trust the request."

**5. What is the difference between Authentication and Authorization in Spring Security?** _(В чем разница между Аутентификацией и Авторизацией?)_

> "**Authentication** checks _who_ the user is (for example, checking login and password). **Authorization** checks _what_ the user can do (for example, checking if the user has an 'ADMIN' role to delete a file)."

### 🌱 Блок 2: Spring Boot & PostgreSQL (Questions 6-12)

**6. What is the N+1 problem in Hibernate / Spring Data JPA and how do you fix it?** _(Что такое проблема N+1 и как её решить? — Самый частый вопрос по JPA)._

> "The N+1 problem happens when we load a list of parent entities (1 query), and then Hibernate makes an additional query for each child entity (N queries). This is very slow. To fix this, I don't use the default lazy loading in loops. Instead, I use **JOIN FETCH** in JPQL or the **@EntityGraph** annotation to load all data in one single database query."

**7. How does Spring Boot Auto-configuration work?** _(Как работает автоконфигурация в Spring Boot?)_

> "The `@SpringBootApplication` annotation includes `@EnableAutoConfiguration`. When the application starts, Spring checks the classpath (the libraries in our project). For example, if Spring sees the Postgres driver and database credentials in `application.yml`, it automatically creates a `DataSource` bean for us. We don't need to write boilerplate XML configuration."

**8. How do you find and optimize a slow query in PostgreSQL?** _(Как вы находите и оптимизируете медленные запросы в PostgreSQL?)_

> "First, I use the **EXPLAIN ANALYZE** command before my SQL query. It shows the execution plan. I look for **Sequential Scans** (Seq Scan), which means the database is reading the whole table. To fix this, I create a **B-Tree index** on the columns used in the `WHERE` clause. After that, the plan should change to an **Index Scan**, which is much faster."

**9. What is the difference between DELETE and TRUNCATE in PostgreSQL?** _(В чем разница между DELETE и TRUNCATE?)_

> "**DELETE** is a DML command. Because of MVCC, it doesn't remove data immediately; it just marks rows as 'dead tuples'. It is safe but slow for large tables. **TRUNCATE** is a DDL command. It physically drops the data files on the disk and creates new empty ones. It is extremely fast, but you cannot use a `WHERE` condition with it."

**10. What is a Connection Pool and why does Spring Boot use HikariCP?** _(Что такое пул соединений и почему Spring Boot использует HikariCP?)_

> "Opening a new physical connection to the database takes a lot of time. A Connection Pool creates several connections at startup and keeps them open. When a user makes a request, they borrow a connection from the pool and return it later. Spring Boot uses **HikariCP** by default because it is highly optimized, very fast, and consumes very little memory."

**11. What is the difference between Optimistic and Pessimistic locking?** _(В чем разница между Оптимистичной и Пессимистичной блокировками?)_

> "**Pessimistic locking** locks the real row in the database (using `SELECT ... FOR UPDATE`). No one else can read or update it. It is safe but slow. **Optimistic locking** does not lock the database. It uses a `@Version` field in the Java entity. Before saving, Hibernate checks if the version in the database is the same. If another user already updated the row, Hibernate throws an `OptimisticLockException`."

**12. How do you manage different environments in Spring Boot (dev, test, prod)?** _(Как вы управляете разными окружениями в Spring Boot?)_

> "I use **Spring Profiles**. I create separate configuration files, like `application-dev.yml` and `application-prod.yml`. When I start the Docker container in production, I pass an environment variable (like `SPRING_PROFILES_ACTIVE=prod`) to activate the correct database URL and passwords."

### 📨 Блок 3: Apache Kafka & gRPC (Questions 13-19)

**13. Can you explain the main concepts of Kafka: Topic, Partition, and Offset?** _(Объясните главные концепты Кафки: Топик, Партиция и Оффсет)_

> "A **Topic** is a category where we send messages. To make it fast, a topic is divided into **Partitions**. Partitions allow Kafka to process data in parallel. Inside a partition, every message gets a unique ID number called an **Offset**. Consumers use the offset to remember which messages they already read."

**14. What is the difference between Kafka and RabbitMQ?** _(В чем разница между Kafka и RabbitMQ? — Классический архитектурный вопрос)_

> "RabbitMQ is a traditional message broker (smart broker, dumb consumer). When a consumer reads a message, RabbitMQ **deletes** it. Kafka is a distributed commit log (dumb broker, smart consumer). It **saves messages on the disk** for a long time (for example, 7 days). This means multiple different microservices can read the exact same message independently."

**15. How do you scale consumers in Kafka? What is a Consumer Group?** _(Как вы масштабируете консюмеры в Кафке? Что такое Consumer Group?)_

> "We scale using **Consumer Groups**. A Consumer Group is a logical group of applications reading the same topic. If a topic has 3 partitions, I can start 3 consumers in the same group. Kafka will assign **one partition to each consumer**. This gives us perfect parallel processing."

**16. How do you guarantee message ordering in Kafka?** _(Как гарантировать порядок сообщений в Кафке? — Вопрос со звездочкой!)_

> "Kafka guarantees strict message order **only inside a single partition**, not across the whole topic! If I need to keep the order for a specific user's orders, I must use the user ID as the **Message Key**. Kafka hashes the key and guarantees that all messages with the same key will always go to the **same partition**."

**17. What is gRPC and why is it faster than traditional REST?** _(Что такое gRPC и почему он быстрее классического REST?)_

> "gRPC is a framework developed by Google. It is much faster than REST for two main reasons: First, it uses **HTTP/2** instead of HTTP/1. HTTP/2 supports multiplexing (sending multiple requests over one connection). Second, it uses **Protocol Buffers (Protobuf)** instead of JSON. Protobuf is a binary format, so the data is much smaller and faster to serialize."

**18. What is the difference between JSON and Protobuf?** _(В чем разница между JSON и Protobuf?)_

> "**JSON** is a text format. It is easy for humans to read, but slow for computers to parse. It also takes more network bandwidth. **Protobuf** is a strongly-typed binary format. We define a strict contract in a `.proto` file, and generate Java classes from it. It is much faster, smaller, and safer because the schema is strictly defined."

**19. What types of communication (streaming) does gRPC support?** _(Какие типы потоков поддерживает gRPC?)_

> "gRPC supports 4 types:
> 
> 1. **Unary** (like REST: one request, one response).
>     
> 2. **Server Streaming** (client sends one request, server sends a stream of data).
>     
> 3. **Client Streaming** (client sends a stream, server sends one response).
>     
> 4. **Bidirectional Streaming** (both client and server send streams of messages at the same time)."


### 🐳 Блок 4: Docker, Базы данных и Транзакции (Questions 20-26)

**20. What is the difference between a Docker Image and a Docker Container?** _(В чем разница между Docker Image и Docker Container?)_

> "A **Docker Image** is a read-only template. It contains the application code, libraries, and the operating system (like Alpine Linux). A **Docker Container** is a running instance of that image. You can start, stop, or delete a container, but the original image never changes."

**21. How do you optimize a Dockerfile for a Java application?** _(Как оптимизировать Dockerfile для Java-приложения? — Вопрос на опыт)_

> "I use **Multi-stage builds**. In the first stage, I use a heavy Maven or Gradle image to compile the code. In the second stage, I use a very small JRE image (like Alpine) and copy only the final `.jar` file. This makes the final image very small and much more secure."

**22. Can you explain the ACID properties in database transactions?** _(Можете объяснить свойства ACID в транзакциях? — Фундаментальный вопрос)_

> "ACID stands for four properties:
> 
> 1. **Atomicity:** All operations in a transaction succeed, or they all fail. No partial saves.
>     
> 2. **Consistency:** The database is always in a valid state after the transaction.
>     
> 3. **Isolation:** Concurrent transactions do not affect each other.
>     
> 4. **Durability:** Once a transaction is committed, the data is saved to the disk permanently, even if the server crashes."
>     

**23. What are the main Transaction Isolation Levels and what do they prevent?** _(Каковы основные уровни изоляции транзакций и что они предотвращают?)_

> "The default level in PostgreSQL is **Read Committed**. It prevents 'Dirty Reads' (reading uncommitted data from others). The next level is **Repeatable Read**. It prevents 'Non-repeatable Reads' (data changing during your transaction). The highest level is **Serializable**. It completely isolates transactions, preventing 'Phantom Reads' (new rows appearing in your search results), but it is very slow."

**24. What is a Composite Index and why does column order matter?** _(Что такое составной индекс и почему важен порядок колонок?)_

> "A **Composite Index** is an index on two or more columns (for example, `name` and `age`). The order is extremely important because of the **Left-most prefix rule**. If the index is on `(name, age)`, the database can use it to search by `name`, or by `name AND age`. But if we search **only** by `age`, the index will not work."

**25. Why might PostgreSQL ignore your index and do a Sequential Scan anyway?** _(Почему Postgres может проигнорировать ваш индекс и все равно сделать полное сканирование таблицы? — Любимый вопрос синьоров)_

> "The PostgreSQL Query Planner makes the final decision. It will ignore the index if:
> 
> 1. The table is **very small**. A sequential scan in RAM is faster than reading the index.
>     
> 2. The query has **low selectivity** (for example, reading 80% of the table).
>     
> 3. We use a function on the column, like `WHERE LOWER(name) = 'john'`, but we don't have a specific functional index for it."
>     

**26. How do you handle database migrations in your projects?** _(Как вы управляете миграциями базы данных в ваших проектах?)_

> "I use **Liquibase** (or Flyway). We write all schema changes in XML or SQL scripts. When the Spring Boot application starts, Liquibase checks the `databasechangelog` table and automatically applies the new scripts. This ensures that all developers and servers have the exact same database structure."

### 🧠 Блок 5: Java Memory, GC & System Design (Questions 27-33)

**27. What is the difference between Stack and Heap memory in Java?** _(В чем разница между Stack и Heap памятью в Java?)_

> "The **Stack** stores local variables (primitives) and method calls. Each thread has its own separate stack. It is very fast and small. The **Heap** stores all created objects. It is a large memory area shared between all threads. The Garbage Collector works only in the Heap."

**28. How does Garbage Collection work in Java (Mark and Sweep)?** _(Как работает сборка мусора в Java?)_

> "Modern GC uses the **Mark and Sweep** algorithm. First, in the **Mark phase**, it scans memory and 'marks' all objects that are still used by active threads. Second, in the **Sweep phase**, it deletes all objects that are not marked (unreachable objects). After that, it compacts the memory to prevent fragmentation."

**29. What is the G1 Garbage Collector?** _(Что такое сборщик мусора G1?)_

> "G1 stands for **Garbage-First**. It is the default collector since Java 9. Older collectors split the heap into huge blocks. G1 divides the memory into small blocks called **regions**. It finds the regions with the most garbage and cleans them first. This makes application pause times very short and predictable."

**30. Java has Garbage Collection. Can we still have a Memory Leak?** _(В Java есть сборщик мусора. Может ли у нас все равно произойти утечка памяти? — Любимый вопрос на логику)_

> "Yes, memory leaks can happen. A memory leak occurs when the application keeps a reference to an object, but never uses it again. Because the reference still exists, the Garbage Collector cannot delete it. The most common mistake is putting objects into a `static Map` or `List` and forgetting to remove them."

**31. What is the `volatile` keyword used for?** _(Для чего используется ключевое слово volatile?)_

> "The `volatile` keyword solves the **visibility problem** in multithreading. Normally, threads cache variables in the CPU cache for speed. If one thread changes the variable, another thread might not see the new value. `volatile` tells Java to read and write this variable directly to the **main memory**, skipping the CPU cache."

**32. Can you explain the CAP Theorem?** _(Можете объяснить CAP-теорему? — Главный вопрос по System Design)_

> "The CAP Theorem states that a distributed system can only guarantee **two out of three** properties at the same time:
> 
> 1. **Consistency:** All users see the exact same data at the same time.
>     
> 2. **Availability:** The system always returns a response, even if some servers are down.
>     
> 3. **Partition Tolerance:** The system works even if the network between servers is broken. Because networks always fail, we usually have to choose between CP (Consistency + Partition Tolerance) or AP (Availability + Partition Tolerance)."
>     

**33. What is the difference between Horizontal and Vertical scaling?** _(В чем разница между горизонтальным и вертикальным масштабированием?)_

> "**Vertical scaling** means buying a bigger server (more RAM, more CPU). It is easy, but it has a physical limit and creates a single point of failure. **Horizontal scaling** means adding more servers. We use a **Load Balancer** (like Nginx) to distribute traffic among them. For microservices, horizontal scaling is the standard approach."

### 🚀 Блок 6: Git Flow, Docker CLI & CI/CD (Questions 34-39)

**34. Can you explain Git Flow? How do you organize your branches?** _(Можете объяснить Git Flow? Как вы организуете свои ветки?)_

> "Git Flow is a popular branching strategy. We have two main branches: **`main`** (for production code) and **`develop`** (for the next release). When I work on a new task, I create a **`feature`** branch from `develop`. When the task is done, I create a Pull Request back to `develop`. If there is a critical bug in production, we create a **`hotfix`** branch directly from `main`, fix it, and merge it back to both `main` and `develop`."

**35. What is a Pull Request (or Merge Request) and what is your role in it?** _(Что такое Pull Request и какова ваша роль в нем?)_

> "A Pull Request is a request to merge my `feature` branch into the `develop` branch. It is the most important part of the code review process. Other developers look at my code, leave comments, and check if it follows our standards. I also actively review my colleagues' Pull Requests to help catch bugs early."

**36. What Docker commands do you use every day?** _(Какие команды Docker вы используете каждый день?)_

> "For my daily work, I use these basic commands:
> 
> 1. **`docker build -t app-name .`** — to build an image from a Dockerfile.
>     
> 2. **`docker run -d -p 8080:8080 app-name`** — to start a container in the background and open the port.
>     
> 3. **`docker ps`** — to see all running containers.
>     
> 4. **`docker logs -f <container_id>`** — to check the live application logs.
>     
> 5. **`docker stop <container_id>`** — to stop the container."
>     

**37. How do you run your microservice and a database together locally?** _(Как вы локально запускаете свой микросервис и базу данных вместе?)_

> "I use **Docker Compose**. It is a tool for running multi-container applications. I write a `docker-compose.yml` file where I define my Spring Boot app, PostgreSQL, and Kafka. Then I just run **`docker-compose up -d`**. It automatically creates a local network and starts all services together."

**38. What happens step-by-step in your CI/CD pipeline?** _(Что пошагово происходит в вашем CI/CD пайплайне?)_

> "When I push code to the repository, the pipeline starts automatically. **Step 1:** It compiles the Java code and runs Unit tests. If a test fails, the pipeline stops. **Step 2:** It builds a new Docker image. **Step 3:** It pushes the image to a Docker Registry (like Docker Hub or AWS ECR). **Step 4:** It deploys the new image to the Development or Test server."

**39. What is the difference between Continuous Delivery and Continuous Deployment?** _(В чем разница между Continuous Delivery (Непрерывная доставка) и Continuous Deployment (Непрерывное развертывание)?)_

> "In Continuous **Delivery**, the code goes through tests and is ready for production, but a human (like a manager) must click a button to approve and deploy it. In Continuous **Deployment**, the process is 100% automated. If all tests pass, the code goes to Production immediately without human intervention."
